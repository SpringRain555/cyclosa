# ADR-0015：關聯分四層，因為「出處五筆」可能只有兩個獨立來源

**狀態**：已採用。**四種畫法於 2026-09-07（Stage 7）實作並實際看過畫面。**
**日期**：2026-09-06（2026-09-07 補一條，見最後）

> 這份決定**來自 2026-09-05 的 UI 設計稿**，2026-09-06 才回寫進文件。
> 在那之前 `data-model.md` 只有一個扁平的 `edge.rel`。

## 背景

ADR-0005 訂了「每條邊必帶出處」，而 UI 上會顯示這條邊有幾筆出處。
設計稿在畫右欄的時候發現一個洞：

> 一條「五筆出處」的關聯，如果其中三筆是同一則的轉載，**可信度就是假的**。

而使用者看不出來 —— 畫面上寫著 5，那個 5 是真的，只是它不代表使用者以為的東西。
**這不是顯示 bug，是資料模型少了一個維度**：`edge.rel` 分不出
「A 引用 B」（衍生關係，機器可驗）與「A 收購了 B」（世界上的主張，要人判斷）。

同時還有兩種東西被硬塞進同一個欄位：實體投影出來的「共同提及」線，
以及演算法算出來的「相似度」。**那兩種都不是主張**，不該進人工裁決佇列 ——
但只要它們跟具名關係共用一個欄位，就沒有辦法把它們排除在佇列之外。

## 決定

**`edge` 新增 `layer` 欄位，四個值**：

| 層 | 是什麼 | 進裁決佇列？ | 預設畫法 |
|---|---|:--:|---|
| `derived` **衍生** | 轉載、翻譯、鏡像。**機器可驗**（雜湊、URL、重疊率）| **否** | 摺進來源節點（「＋3 轉載」），**根本不畫線** |
| `named` **具名關係** | 世界上的主張（「收購」「任職於」）| **是**，要引文 | 漸細（＝有方向），粗細＝可信度 |
| `comention` **共同提及** | 低於投影門檻的實體攤平成的線 | 否 | 線中點放方塊，方塊就是那個實體 |
| `similarity` **相似度** | 算出來的分數 | 否 | 等寬點線，沒有方向 |

**只有 `named` 需要人工裁決。** 另外三層各自有明確的產生方式，
而且都**可以重算** —— 它們不是判斷，是計算結果。

**獨立來源數的定義**：把一條邊的 `edge_evidence` 依照「它們的 `item` 之間有沒有
`derived` 關係」分群，**每一群算一個獨立來源**。UI 顯示「出處 5 筆 · 2 個獨立來源」。

## 考慮過但沒選的

| 方案 | 為什麼不選 |
|---|---|
| **維持單一 `edge.rel`** | 「獨立來源數」做不出來，可信度只能數出處筆數 —— 而那個數字會系統性地高估轉載多的主題（新聞類尤其嚴重）|
| **只分「要裁決／不要裁決」兩層** | 夠算獨立來源數，但四種畫法會塌成兩種：共同提及與相似度長得一樣，而它們的意義完全不同（一個是「這兩篇提到同一個人」，一個是「這兩篇內容像」）|
| **把層別做成 `rel` 的命名慣例**（如 `sim:*`）| 字串前綴不是型別。查詢要 `LIKE 'sim:%'`，而且沒有東西擋得住有人寫錯前綴 |
| **獨立來源數在寫入時算好存起來** | 它會隨新的 `derived` 邊出現而改變。**存起來的那一刻就開始過期**，而過期的可信度比沒有可信度糟 |
| **把 `derived` 也丟進裁決佇列** | 使用者要對「這篇是那篇的轉載」按確認，而那件事機器用雜湊就驗得出來。**把可驗證的東西送去人工裁決，會讓人開始不看內容就按確認** —— 然後真正需要判斷的那些也一起被亂按 |

## 代價

- **抽取時要判斷一條關聯屬於哪一層**，而那個判斷本身可能錯。
  緩解：`derived` 有客觀依據（雜湊／URL／重疊率），`similarity` 是自己算的，
  `comention` 是投影出來的 —— **只有 `named` 是 LLM 說了算，而它正好是要人裁決的那一層**。
- **四種畫法要各自實作與測試**，而且要在同一張圖上同時可讀。
- **獨立來源數是即時算的**，所以它是一個查詢成本。子圖查詢要一併帶回這個數字，
  否則側欄會為了顯示一行字再打一次 API。
- **`derived` 預設不畫線**意味著圖上看不到它們。使用者要看得到「這個節點摺了 3 個轉載」
  這件事本身，否則會以為資料漏了。

## 什麼情況要重新考慮

- **出現第五種既不是主張、也不是這三種計算結果的關聯**（例如「使用者標記為待辦」）——
  那時要問的是「它是不是根本不該當成邊」，而不是加第五層。
- **`derived` 的判定準確率低到使用者不信任獨立來源數** ——
  條件是實測（取 30 條有轉載的關聯，看分群對不對），不是「感覺不太準」。
- 若 `comention` 與 `similarity` 在真實資料上永遠被使用者關掉，
  那要問的是「它們該不該存在」，而不是怎麼畫得更好看。

## 2026-09-07 補：`comention` 有兩種長相

**這一條是實作時看著畫面才發現的，不是設計時想到的。**

上面那張表寫 `comention` 的預設畫法是「線中點放方塊」，
而那句話**只對了一半**。`comention` 這一層裝兩種東西：

1. **儲存的 `item → entity` 邊**（「這篇提到那個人」）
2. **投影出來的 `item — item` 線**（實體低於展開門檻時攤平的結果）

實體展開成節點的時候，第 1 種只是一條普通的等寬線 ——
**在它中點再放一個方塊，等於把同一個實體畫兩次**：
一次在線的末端（空心節點），一次在線的中間（方塊）。

判準是那條線有沒有 `via`：**有值就代表它是投影出來的**，`via` 就是被攤平的實體。
細節寫在 `data-model.md`，規則本身在 `domain/graph/render-rules.ts` 的
`edgeDrawingOf()`，由 `tests/domain/render-rules.test.ts` 守著。

**四層四種畫法這個決定沒有變** —— 變的是「`comention` 的預設畫法」
這句話需要一個條件。

## 先例

**`alephdata/followthemoney`（MIT，2026-09-06 實查）** 的 70 個 schema 裡有
**`Mention.yaml`** 與 **`Similar.yaml`** —— 它把「提及」與「相似」跟具名關係
（`Ownership`、`Employment`、`Directorship`…）分開建模。

**那是一個獨立於這份設計的收斂**，而且它來自一個真實在用的投查資料模型。
**借的是分類概念，不引它的 Python 套件**（這個專案零 Python）。
