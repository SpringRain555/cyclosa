# ADR-0005：雙層圖模型（文件＋實體），每條邊必帶出處

**狀態**：已採用（設計決定；實作尚未開始）
**日期**：2026-09-06

## 背景

**Obsidian 的圖被大量批評「好看但沒用」，而三條原因都是具體且可修的**：
關係層唯讀（沒辦法把剛想到的關係拖出來）、圖沒有型別（無法「只顯示人」）、
超過約 500 節點只是變擠。社群裡真正好用的例子（Excalibrain）靠的是**具名連結**。

另一邊是純算術：**一個被 *n* 份文件提到的實體，當節點要 *n* 條邊，
當邊上的標籤要 *n(n−1)/2* 條。交叉點在 *n*=3。**

第三件事最重要：這個工具與「一鍵生成關聯圖」的全部差別，就是**每條關聯都能回答
「憑什麼」**。少了那個，它退化成一張看起來很有道理的圖。

## 決定

1. **儲存永遠是雙層（bipartite）**：`item`（文件節點）與 `entity`（實體節點）
   各自是節點，`edge` 連接它們。
2. **「要不要把實體攤平成文件之間的連線」是顯示層的投影**，每個畫面各自算，
   **預設門檻 3**。這個門檻**不進資料庫** —— 改門檻不需要 migration。
3. **每條邊必帶出處**：`edge_evidence` 的 `quote` ＋ `char_start` ＋ `char_end`，
   指向某個 `item`。**沒有出處的邊只能是 `待查證`。**
4. **`origin`（`machine`／`human`）與 `status` 分開存**，寫入路徑對
   `origin='human'` 的列**只能新增不能改**。
5. **節點與邊都有型別且可篩選**（`entity.type`、`edge.rel`），
   使用者可以手動建立邊 —— 那是對 Obsidian 那三條批評的直接回應。

## 考慮過但沒選的

| 方案 | 為什麼不選 |
|---|---|
| **單層文件圖，實體當邊上的標籤** | *n*≥3 時線反而更多；而且實體本身不是物件 → 無法檢視、無法合併別名、無法「只顯示人」 |
| **單層實體圖，文件只當屬性** | 丟掉文件就丟掉出處。這條直接違反這個工具存在的理由 |
| **把投影門檻寫進資料庫** | 那是顯示決定。寫進去之後，改一個顯示偏好要跑 migration |
| **信心值直接顯示成小數給使用者看** | 一個 0.73 會被當成有根據的量測，而它不是。**連續分數只用於排序與粗略的視覺通道** |

## 代價

- **節點數大約變兩倍**，圖更容易擠 —— 這正是投影門檻要存在的原因，
  但門檻本身還沒有實測（`research/open-questions.md` Q1）。
- **實體去重變成必須做的工作**（同一個人的不同寫法、簡繁、譯名）。
  第一版只有 `aliases_json` ＋ 選填的 Wikidata QID，**沒有自動合併**。
- **強制出處讓機器產生的邊大部分停在 `待查證`**，使用者要花時間裁決。
  這是刻意的成本 —— 但它會讓第一次使用的體感比競品差。
- 「投影是每個畫面各自算」意味著同一批資料在不同畫面上長得不一樣，
  UI 要讓使用者知道自己正在看投影。

## 什麼情況要重新考慮

- **`open-questions.md` Q1**：第一個真實專題累積到 200 個以上節點時，
  把門檻做成可調，在 2 / 3 / 5 之間實際切換比較 ——
  交叉點是「線比較少」的門檻，**不一定是「看起來比較清楚」的門檻**。
- 若實體去重的人工成本高到使用者不願意用，那要重新考慮的是「自動合併」的
  邊界，而不是雙層本身。
