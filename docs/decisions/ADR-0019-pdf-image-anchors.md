# ADR-0019：PDF 用「頁碼 ＋ 頁內字元區間」，圖片用 W3C 的矩形選擇器

**狀態**：已採用（設計決定；實作尚未開始）
**日期**：2026-09-06

> **ADR-0010 明寫這是「另一個還沒做的決定，不在這份 ADR 的範圍」。**
> 這份就是那個決定。
>
> 2026-09-06 的範圍確認裡，使用者選了「第一版就要 PDF 閱讀與頁碼錨點、
> 圖片來源與矩形註記」，所以它從「以後再說」變成「Stage 6 與 Stage 10 的前提」。

## 背景

ADR-0010 定了純文字來源的錨點：**W3C Web Annotation 的 `TextQuoteSelector` ＋
`TextPositionSelector` 同時存，釘在不可變的快照上**。

PDF 與圖片套不進去，理由不同：

| | 為什麼套不進去 |
|---|---|
| **PDF** | 快照是二進位。`char_start` 相對於什麼？整份 PDF 的位元組位移對使用者毫無意義，而且抽文字的實作換版之後全文字元序列會變 |
| **圖片** | **根本沒有文字。** 沒有 quote 可以存 |

同時 REQ-0006 已經寫著第一版支援 PDF 與圖片，
而 `state-machines.md` 與 `data-model.md` 對它們的錨點一個字都沒有 ——
**兩份文件互相矛盾，而矛盾的那一半正好是要實作的那一半。**

## 決定

### PDF：頁碼 ＋ 頁內字元區間 ＋ 引文

**三件一起存**，跟純文字的兩件是同一個道理（快的那個 ＋ 抗漂移的那個）：

| 存什麼 | 性質 |
|---|---|
| `page`（1-based）| **穩定**。頁碼是 PDF 檔案結構的一部分，不是抽取結果 |
| `char_start` / `char_end` | **相對於那一頁的文字層**，不是相對於整份文件 |
| `quote` ＋ 前後文 | 抗漂移。抽取實作換版時用它重找 |

**錨點仍然釘在 `sources/` 的不可變快照上** —— 頁碼與頁內位移都是對「那一份 PDF」而言的，
`derived/` 重算不影響。

**解析順序**：先用 `page` ＋ 字元區間；對不上就在**同一頁內**用 quote 重找；
再對不上才擴大到相鄰頁；全失敗才標「找不到原文位置」並保留註記內容。

> **為什麼字元區間相對於頁而不是整份文件**：整份文件的位移會被前面任何一頁的
> 抽取差異推移，**一頁抽錯會讓後面每一頁的錨點全部漂掉**。
> 相對於頁的話，錯的只有那一頁。**失敗要能被局部化。**

### 圖片：W3C `FragmentSelector`，媒體片段的矩形

`#xywh=pixel:<x>,<y>,<w>,<h>`（W3C Media Fragments URI 1.0）。
**用 `pixel:` 而不是 `percent:`** —— 快照的原始尺寸是不可變的，
所以像素座標對它永遠有效，而百分比在四捨五入上會漂。

**圖片沒有第二重錨點。** 純文字與 PDF 都有「引文」當抗漂移的備援，圖片沒有等價物。
這是明知的不對稱：**圖片的錨點只要快照不變就永遠正確，而快照本來就不可變**，
所以它其實不需要備援 —— 需要備援的是那些會被重新抽取的東西。

### 三種來源共用同一個資料模型

`note` 表用**一個** `selector_json` 欄位，內容是 W3C 的選擇器陣列。
型別由 `type` 欄位分：`TextQuoteSelector` / `TextPositionSelector` / `FragmentSelector`
（PDF 的頁碼放在 W3C 允許的 `refinedBy` 巢狀結構裡）。

**不為三種來源開三張表。** W3C 模型本身就是為了這件事設計的 ——
它允許一個標註帶多個選擇器，而解析端依序嘗試。

## 考慮過但沒選的

| 方案 | 為什麼不選 |
|---|---|
| **PDF 錨在整份文件的字元位移** | 前面一頁抽錯，後面全漂。**失敗無法局部化** |
| **PDF 錨在 PDF 內部物件 ID** | 那是 PDF 產生器的實作細節。同一份文件用不同工具重存一次就全變 |
| **PDF 用座標矩形（像圖片那樣）** | 選文字的體感會變成「框一塊區域」，而使用者在讀 PDF 時是在選句子。**而且複製不到文字** |
| **圖片用百分比座標** | 四捨五入會漂，而且沒有換到不同尺寸的需求 —— 快照尺寸是固定的 |
| **圖片先做 OCR，再套文字錨點** | 把一個穩定的問題（像素座標）換成一個不穩定的（OCR 結果會隨模型改版而變）|
| **三種來源各開一張表** | 查詢「這個專題所有的點註」要 UNION 三張表，而那是最常見的查詢 |
| **第一版不做 PDF 與圖片** | 使用者 2026-09-06 明確要了。而且**REQ-0006 本來就寫著第一版要支援** —— 不做的話要改的是那份需求 |

## 代價

- **三種錨點各有各的解析路徑與失敗模式**，測試量是純文字版的三倍。
- **PDF 的文字層可能不存在**（掃描的 PDF）。那時候整份 PDF 只能當圖片處理，
  而 **UI 必須說清楚「這份沒有文字層，只能框選區域」** —— 不能讓使用者以為是工具壞了。
- **圖片沒有抗漂移備援**，所以它完全依賴「快照不可變」這條 ADR-0003 的規則。
  那條一旦被違反，圖片註記無聲全錯。
- **`pdfjs-dist` 是新的依賴**（Apache-2.0，2026-09-06 實查確認）。
  它不小，而且它自己帶 worker —— 打包設定會變複雜。
- **頁碼是 1-based 而程式裡幾乎所有東西都是 0-based**。這是一個會反覆出錯的地方，
  緩解只能靠「欄位名叫 `page` 而不是 `page_index`」與測試。

## 什麼情況要重新考慮

- **出現沒有文字層也不是圖片的來源**（影音）—— 那時要加的是新的選擇器型別
  （W3C 模型允許），不是換掉這套。
- **掃描 PDF 的比例高到「只能框選」變成主要體驗** ——
  那時要問的是要不要引 OCR，而那是一個新的決定（帶著它自己的「OCR 結果會漂」的代價）。
- 若 PDF 的錨點解析失敗率超過 1%，**先查是不是快照被動過**（違反 ADR-0003），
  再考慮改演算法 —— 這一條與 ADR-0010 相同。
