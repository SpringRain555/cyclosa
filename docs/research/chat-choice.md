# `chat` 角色：`json_schema: true` 這個宣告，量起來是什麼樣子

**日期**：2026-09-09（第二輪；**第一輪的數字已作廢**，見下一節）
**狀態**：八個本機模型量完。

---

## 這份文件為什麼存在

嵌入模型量完之後（`embedding-choice.md`），剩下一個從來沒有被量過的角色：`chat`。
它比嵌入更該量，理由有兩個：

1. **它決定使用者按下「擴展」之後看到什麼。** 嵌入選錯只是搜尋差一點；
   角度選錯是整個功能沒有價值（角度互相重複、或者根本不是從專題內容歸納出來的）。
2. **`capabilitiesOf` 對每一個 Ollama 模型都無條件宣告 `json_schema: true`。**
   理由是 Ollama 的 `format` 參數做的是伺服器端受限解碼 —— 那個宣告在**格式上**成立。

而 `EXTRACT_SCHEMA` 的註解裡記著一件反例：2026-09-08 第一次真的跑擴展時，
**五個實體全部被標成 `person`**，包含「bird dropping」與一個台灣的地名。
schema 的 `enum` 一個都沒攔到 —— **它保證了格式，沒有保證內容。**

---

## 第一輪的數字為什麼作廢

第一輪（v0.10.3）量出一張表，而那張表現在不能用。**三個原因都出在量測本身，
而不是模型**，所以整輪重跑了：

| 缺陷 | 後果 |
|---|---|
| `eval-chat.ts` **沒有送 `num_ctx`**，而出貨的送了 | 量測與出貨跑在不同的視窗大小上 |
| **三次重複送同一份正文** | 第二、三次大量命中 KV 快取 —— 那不是三個樣本，是一次量測加兩次回音 |
| 記分線是**手算**的 | 出貨是 180 秒、腳本是 300 秒，而分數要照前者 |

第二項的實測後果最直接：同一個請求、同一個模型、溫度 0，連跑三次的
`prompt_eval_count` 是 **13,296 / 10,186 / 6,702**，輸出跟著變成
**2,400 / 11,474 / 1,595** 個 token。

> **還有一次污染是環境的**：`TaskStop` 停掉一個背景量測之後，
> `node` 子行程沒有死，四十分鐘後它已經自己跑到清單裡的第二個模型，
> 一路佔著 GPU。同一份設定量到 204 秒與 84 秒，差的就是那個。

而更重要的是：**第一輪跑的時候，`EXTRACT_SCHEMA` 的兩個陣列還沒有上界**
（見 `lessons.md`「上限寫在正規化那一層，而模型看不到它」）。
那不只是數字不準，是**受測的東西不一樣**。

## 量什麼：六欄，全部機器判

| 量什麼 | 為什麼它決定得了事情 |
|---|---|
| **schema 有效率** | 硬需求。吐不出合法 JSON 的模型，這個任務直接不能用 |
| **失敗的樣子**（逾時 ／ 吐不出） | **處方相反**：跑太久換小模型，回 0 個字元就是不能用。合成一欄看起來一模一樣 |
| **引文命中率** | `locateQuote` 找不到的引文，**那條邊就不存在**（ADR-0005） |
| **輸出的 token 數** | 本機模型沒有金額成本，**token 就是秒數**。而它也是「視窗夠不夠」唯一的證據 |
| **角度之間的最大相似度** | 「多視角」如果全是同一個問題的改寫，這個功能就沒有價值 |
| **`seeds` 指到真的東西** | 模型可以編一個不存在的編號。編了就代表畫面上那一欄「依據」是假的 |

**六欄都不需要人去讀輸出。** 繁中品質要人判，那不在這一輪。

## 怎麼量

- **走真的會出貨的那幾支**：提示詞用 `application/expansion-prompts.ts`、
  正規化用 `domain/provider/`、引文定位用 `locateQuote`、
  `num_ctx` 用 `REQUIRED_CONTEXT_TOKENS` —— 跟擴展作業實際跑的是同一條路。
- **每個任務重複三次，而且每一次換一份文件。** 同一份跑三次的話，
  第二、三次大部分的提示詞都命中 KV 快取，而使用者每次面對的都是新文件。
- 抽取的文件是真的抓回來的頁面，取字數最接近 `MAX_TEXT_CHARS` 的前三篇
  （中文 12,753／6,670／6,214 字，英文 12,385／8,966／18,003 字）。
  > 第二、三篇明顯比較短 —— **語料裡接近上限的頁面就是這麼少**，
  > 而那讓「context 這一欄真的被用到」只成立在第一篇。這是已知的取捨。
- 溫度 0。`format` 帶整份 schema。
- 語料與 `embedding-choice.md` 同一批（`tools/research/fetch-eval-corpus.ts`）。
- **記分在另一支**（`tools/research/score-chat.ts`），而那條線是
  `import` 出貨的 `CHAT_TIMEOUT_MS`，不是抄一個 180 進去。

> 腳本給每次呼叫 300 秒是刻意的：**量到 295 秒比只知道「超過 180」有用** ——
> 它說得出差多少。但**記分一定要照出貨的那條線**，
> 否則表上會出現一個「通過」的模型，而使用者按下去只會拿到逾時。

（第一輪的結論是「該試更小、更新的 instruct 模型」）。

## 三個指標都沒有量到我想量的東西

這一節記的是**量測方法的失敗**，不是模型的失敗。它排在結果後面、發現前面，
因為不知道這件事的話，下面每一個結論都會被讀錯。

第一輪只有「角度彼此的最大相似度」一欄，想量的是「多視角有沒有真的多視角」。
第二輪把樣本讀了一遍，發現**那一欄跟品質是反相關的**：

| 模型 | 彼此 | 一條實際的角度 |
|---|---|---|
| `olmo-3:32b-think` | **0.681（最好）** | 「蜘蛛結網行為的演化如何與其**光合作用能力**的發展相關？」 |
| `translategemma:12b` | **0.802（最差）** | 「蜘蛛結網行為的演化在時間線上是怎麼發展的？是否有化石紀錄或基因證據…」 |

**胡說八道是很發散的。** 素材（`seeds`）是語料裡別的頁面的標題
（区块链、光合作用、Knowledge graph…），而有些模型把素材的主題當成了這個專題的角度 ——
角度之間確實不像，但它們也不是這個專題的。

於是加了第二欄「離題目」（角度與主題本身的餘弦）。**它量到的是句子長度**：
`qwen3.5:4b` 離主題最近（0.720），而它問「免疫系統中的病原體壓力是否影響了蜘蛛結網行為」；
`nemotron-cascade-2:30b` 離主題最遠（0.593），六條卻全部切題 ——
它的問句都以「接下來該查什麼…」開頭，長句把相似度稀釋掉了。

於是加了第三欄「飄向素材」（同一條角度對主題與對最像的素材標題比大小，
**兩邊用同一個向量，長度效應自己抵消**）。它只對 `nemotron` 有反應（3/18），
**而那正是質性上最好的那一組**。

**三種都失敗，而失敗的原因是同一個**：那些壞掉的角度是**混合體**。
「區塊鏈技術在蜘蛛結網演化研究中的資金流向如何影響研究進度？」
同時像主題也像素材，任何一種餘弦比較都打不出來。

所以這件事**改用人判，而且標明是人判的**。逐條讀每個模型的三條樣本：

| 模型 | 三條裡混進不相干概念的 | 是什麼 |
|---|---|---|
| `qwen3.5:4b` | **2** | 免疫系統的病原體壓力、板塊構造變動 |
| `olmo-3:32b-think` | **2** | 光合作用、大型語言模型 |
| `granite4.2:3b` | 1 | 區塊鏈技術 |
| `qwen3.5:9b` | 1 | 資料庫結構 |
| `granite4.2:8b`、`translategemma:12b`、`gemma4:31b`、`nemotron-cascade-2:30b` | 0 | —— |

> **n ＝ 3，而且是我讀的。** 這不是一個可以拿來排序的數字，
> 它只夠支持一句話：**這個失敗模式是真的，而且自動指標抓不到它。**
> 要變成可排序的東西，得先有一組標好答案的題目 ——
> 那是嵌入評測那邊做過的事（`embedding-eval-queries.jsonl` 先登記後量測），
> 而角度這一題還沒有。

## 六個發現

### 一、`json_schema: true` 對其中兩個是**錯的**

`nemotron-cascade-2:30b` 在抽取這一題上**六次全部回 0 個字元**，
每次只花 1–4 秒。不是逾時、不是格式錯 —— **是空的**。
而它在角度那一題上三次全部成功。

**追進去之後這一條變得更難看。** 拿同一份 schema、同一段系統提示，
只改正文長度（`tools/research/probe-schema-limit.ts`）：

| 正文長度 | 回應 | 回應物件裡有哪些欄位 |
|---|---|---|
| 200 字 | 515 字 ✔ | `done_reason=stop`、`eval_count=227` |
| 500 字 | 523 字 ✔ | `done_reason=stop`、`eval_count=234` |
| **800 字** | **0 字** | **只有 `model, created_at, message, done`** |
| 1200 字 | 0 字 | 同上 |
| 2000 字 | 0 字 | 同上 |

**斷在 500 到 800 個字元之間** —— 而它的 context 是 262144。
**這跟 context 一點關係都沒有。** 而且失敗時回來的物件**少了
`done_reason`、`eval_count` 與全部計時欄位**，那不是「模型答了一個空字串」，
是 Ollama 給了一個不完整的回應。

架構是 `nemotron_h_moe`（Mamba 與 Transformer 的混合 MoE）。
**合理的解釋是受限解碼在這個架構上沒有被完整支援**，
而那是 Ollama 那一層的事，不是模型「不夠聰明」。
但無論成因是什麼，對這個工具來說結論一樣：**它宣告 `json_schema: true`，而它做不到。**

`olmo-3:32b-think` 從來沒有在 180 秒內完成過抽取（實際要 278–292 秒）。

**我們的能力宣告對這兩個都說 `true`，而閘門看的就是那個宣告。**
使用者會通過設定頁的綠勾、通過勾選那一關、抓完全部網址，
然後每一份文件都拿到一個錯誤碼。

> **這一條沒有簡單的修法，所以先寫下來。** 「送一次試試看」要花掉一次真的呼叫
> 與一次模型載入（本機模型一次只常駐一個，所以那會把使用者正在用的模型擠出去）。
>
> 設定頁那顆「實際打一次」是現成的位置，**但它現在送的請求測不出這件事** ——
> 那個請求是「回一個 ok 欄位是 true 的物件」，遠在 500 字以下，
> **而 nemotron 在那個長度是過的**。要測得出來，那顆按鈕得送一份夠長的正文，
> 而那又回到「打開設定頁不該產生工作」那條原則的另一邊。**這是一個真的取捨，不是漏掉。**

### 二、我為引文命中率設計的那個風險**沒有發生**

跨全部模型、有輸出的每一次，引文命中率是 **49/50**。
`translategemma` 與 `gemma4` 都是 **100%（18/18 與 31/31）**。

**模型不會捏造引文。** 受限解碼加上「引文要是原文的一段」這個指示，
在這件事上是有效的。

**真正的失敗模式是「根本沒有輸出」** —— 逾時、空回應、或者一次
**55,467 個字元的非 JSON**（`translategemma` 的一次中文抽取，208 秒之後）。
最後那一次值得單獨記著：**`format` 帶了整份 schema，而受限解碼沒有守住。**

**這一段是這份文件最重要的更正**：量之前我以為要防的是幻覺，
量完之後看到的是可用性。**設計指標的時候猜錯了風險，而量測把它糾正過來。**

### 三、12B 打贏三個 30B，而且不是險勝

`translategemma:12b` 的抽取成功率 **5/6**，每次 28–40 秒。
三個 30B 分別是 3/6（44–151 秒）、0/6、0/6。

**大小在這件事上不但沒有幫助，而且有害** —— 慢就會撞到逾時，
而逾時是這一輪最主要的失敗原因。

### 四、**沒有任何一個模型兩件事都做得好**

| | 角度 | 抽取 |
|---|---|---|
| `nemotron-cascade-2:30b` | **最好**（相似度 0.689）| **完全不能用**（0/6）|
| `translategemma:12b` | **最差**（相似度 0.802）| **最好**（5/6）|

這是對「四項任務要不要各自有一個模型」那個問題的直接答案。
之前的建議是「`chat` 底下兩個任務預設共用一個模型，但留逐任務覆寫欄位」——
**量完之後，那個覆寫在這台機器上不是選配，是必要條件。**

（要記得一個成本：Ollama 一次只常駐一個模型，而擴展流程是
「角度 → 找來源 → 抽取」連著跑。兩個任務用不同模型，中間就要 unload／load 一次。）

### 五、`seeds` 這一欄**四個都不能信**，而且它對輸入很敏感

`seeds` 是角度的「依據」—— 模型要指出這條角度是從既有的第幾份長出來的，
而畫面上會顯示那幾份的標題。量到的有效率：

| 模型 | 有效／總數 |
|---|---|
| `nemotron-cascade-2:30b` | 15/18 |
| `gemma4:31b` | 4/19 |
| `translategemma:12b` | 0/18 |

**但這一欄不穩定，而那件事是追進去才發現的。** 換一組素材標題重跑
（`tools/research/probe-angle-seeds.ts`），同樣的兩個模型給出完全不同的東西：

```
translategemma:12b（有效範圍 1..8）→ [3] [] [] [0] [2] [4]
gemma4:31b        （有效範圍 1..8）→ [0,1] [0,1] [0] [1] [1]
```

`translategemma` 這次有三個是對的（3、2、4），而評測那一輪是 0/18；
`gemma4` 這次幾乎只吐 0 和 1 —— **看起來像在數陣列索引，不是在指素材編號。**

所以這一欄的結論**不是「某個模型比較誠實」**，是
**「這一欄四個都不能信，而且同一個模型換個輸入就變一種樣子」**。
`normalizeAngles` 會把無效的濾掉，所以畫面上不會出現錯的依據 ——
**代價是那一欄常常是空的**，而它本來是拿來回答「這條角度憑什麼提」的。

> 前一版這裡寫「`translategemma` 的 `seeds` 一個都沒對」。
> **那是只跑一輪就下的結論，而追進去之後它不成立。**
> 一個對輸入敏感的指標，單看一輪會得到一個有信心的錯誤答案。

### 六、中文系統性地比英文難，而那是 tokenizer 的差異在發作

| 模型 | 中文（12,753 字）| 英文（12,385 字）|
|---|---|---|
| `gemma4:31b` | 1/3 | 2/3 |
| `translategemma:12b` | 2/3 | 3/3 |
| `olmo-3:32b-think` | 0/3 | 2/3（但都超過 180 秒）|

**同樣的字元數，中文的 token 數是英文的 4–5 倍**
（Gemma：8,048 對 2,637）。這正是 `TASK_EXTRACT` 那個門檻裡量到的比例，
在這裡以「可靠度差異」的形式出現。

**這個工具的介面是繁中，而它最可能遇到的長文件也是中文。**
所以英文那一欄好看沒有用 —— 要看中文那一欄。

## 結論

**本機這四個模型都不夠好，所以這一輪不訂預設值。**

- `translategemma:12b` 抽取最可靠，但它的角度**是全表最重複的**（0.802）。
- `nemotron-cascade-2:30b` 角度最好，但**抽取完全不能用**。
- `gemma4:31b` 是唯一兩件事都「還行」的，但抽取只有 3/6，
  而 3 次成功裡有 1 次花了 151 秒 —— 使用者要盯著它兩分半。
- `olmo-3:32b-think` 在這兩件事上都不能用。

> **這一輪最有價值的產出不是排名，是「`json_schema: true` 這個宣告靠不住」。**
> 那條宣告寫在 `capabilitiesOf` 裡，對每一個模型都回 `true`，
> 而閘門（ADR-0006）就是靠它決定要不要停手。
> **量之前沒有任何辦法知道它是錯的。**

## 還沒做的

| 沒做 | 為什麼 |
|---|---|
| **更多候選** | 這四個是機器上剛好有的。12B 打贏 30B 這個結果指向「該試更小、更新的 instruct 模型」，而那要再拉 20–40 GB |
| 繁中品質的人工判讀 | 四欄都是機器判的。「這幾條角度好不好」要人看，而那要先有一組值得看的候選 |
| 逾時該不該調 | 180 秒是寫死的。中文長文件上它是主要的失敗原因，但**放寬逾時等於讓使用者等更久**，那是一個要一起看的取捨 |
| 設定頁能不能測出這件事 | 「實際打一次」現在送的是最小請求，**而最小請求測不出來**（nemotron 的角度是過的）|
