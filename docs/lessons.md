## `node -e` 的引號在 PowerShell 與 Git Bash 底下都會被吃掉

**日期**：2026-09-05

**症狀**：同一段 JS 用 `node -e` 執行，兩種 shell 各壞一種：

```
# Git Bash：反斜線被 shell 先吃掉一層
const p='...'+r.replace(/\/g,'/');
                        ^^^^^^
SyntaxError: Invalid or unexpected token

# PowerShell 5.1：內層的雙引號被吃掉，字串提早結束
like %FTS5% \).get();console.log('
Expected ',', got '<eof>'
```

**原因**：`node -e` 的內容要穿過兩層跳脫（shell 一層、JS 一層），而兩種 shell
對反斜線與引號的規則不同。**這不是寫錯，是這個用法本身就脆弱** ——
只要 JS 裡出現 `\`、`"`、`'` 其中之一就有機會壞，而且錯誤訊息指向 JS 語法，
看不出真正的原因在 shell。

**怎麼修的**：**把腳本寫成獨立的 `.mjs` 檔再 `node <檔案>`。**
臨時用的就寫進暫存資料夾。同一輪裡這個問題出現三次，換成檔案之後一次都沒再遇到。

**影響範圍**：全域

## PowerShell 5.1 的 `Get-Content -Raw` 把 UTF-8 讀成 ANSI，中文全毀

**日期**：2026-09-05

**症狀**：`Get-Content package.json -Raw | ConvertFrom-Json` 丟出
`Invalid object passed in, ':' or '}' expected`，而印出來的內容裡中文變成
`?祆??芸??犖?蝞∠?撌亙???Ｙ?`。**檔案本身完全正常** —— 同一個檔案 `node -p` 讀得好好的。

**原因**：PS 5.1 的 `Get-Content` 預設用系統 ANSI codepage（在這台機器是 Big5），
不是 UTF-8。UTF-8 的中文位元組被當成 Big5 解讀，於是字全錯，JSON 也就解析失敗。
**錯誤訊息說的是 JSON 壞掉，而 JSON 沒有壞。**

**怎麼修的**：讀 UTF-8 檔案時二選一 ——
`Get-Content <檔> -Raw -Encoding UTF8`，或乾脆用 `node -p "require('./x.json').y"`。

> 這條與 CONVENTIONS §8 的 BOM 規則**是兩件事**，很容易混。
> §8 管的是「寫檔要不要加 BOM」，這一條管的是「讀檔用什麼編碼解」。
> 一個沒有 BOM 的 UTF-8 檔案完全合法，而 PS 5.1 照樣會讀壞它。

**影響範圍**：全域

## 這兩份 agent 檔宣稱有一條檢查守著，而那條檢查對它們是關的

**日期**：2026-09-06

**症狀**：`AGENTS.md` 與 `CLAUDE.md` 從第一天就寫著「也會剝掉標記區塊之後比內容，
不一致就報 `agent-doc-content-drift`」。寫 ADR-0013 時去查那條檢查怎麼實作的，
才發現**這個專案的兩份檔案裡一個標記都沒有** —— 而驗證器的程式碼明寫
**只在兩份都帶標記時才比**。三個專案（`cyclosa`／`rubricator`／`tagcor-ledger`）
一個都沒有標記，所以那條檢查的**受檢對象是 0 個**。

**原因**：那個前提是**刻意加的、而且是量出來的** —— 沒有它的話，同步聲明必然互指、
必然不同，實測 2026-09-05 會對 31 個專案全部開火，等於零資訊量。
所以前提本身沒有錯，錯在**沒有人採用它**。

**怎麼修的**：在兩份檔案的標題與互指聲明外面補上
`<!-- agent-doc:sync-notice -->` … `<!-- /agent-doc:sync-notice -->`，
然後實跑驗證：剝掉之後兩份 hash 相同，而**故意改共用段落一個字就會不同**。

> **一條沒有人採用的 opt-in 檢查，跟一條死掉的檢查長得一模一樣。**
> 這是 2026-09-05 那三個靜默失效機制的變形，但成因不同 ——
> 那三條是「寫錯了所以永遠命中不到」，這一條是「寫對了但沒有對象」。
> 對前者，驗證的方法是拿真實資料跑一次；對後者，
> **要驗的是「有幾個專案在它的檢查範圍內」，而那個數字要有人負責讓它 > 0。**

**影響範圍**：全域

## 設計稿裡有 16 條決定沒有回寫進文件，而其中 3 條跟文件牴觸

**日期**：2026-09-06

**症狀**：準備開始寫程式，重讀整個專案時去看 Stage 0 的 UI 設計稿，
發現它裡面有一批**文件裡一個字都沒有**的決定 —— 關聯分四層、已否決是墓碑、
可信度三段等級與校準比例、已讀是長期狀態、整套顏色與 CVD 實測數字、
埠號、導覽結構、五條跳轉路徑。

更糟的是有 **3 條直接牴觸**。最嚴重的一條：

```
docs/architecture/state-machines.md  關聯 Edge：5 條轉移，已確認是終點
2026-09-05 設計稿                    「三個狀態，六條轉換」
                                     已確認 → 待查證   撤回確認     ← 原本缺這條
                                     已確認 → 已否決   改判         ← 原本缺這條
                                     已否決 → 已確認   改判         ← 原本缺這條
```

設計稿自己寫著「原本缺這條」—— **它知道它在修正文件**，但那個修正從來沒有回到文件裡。

**原因**：`state-machines.md` 是 **Stage 2（2026-09-06）**寫的，
而設計稿是 **Stage 0（2026-09-05）**產出的 —— **文件比設計稿晚，卻比它舊。**

因為兩者的產出流程完全分開：設計稿是跑 `/design` 產生的一個私有 artifact，
而文件是另外寫的。**沒有任何一步會強迫兩邊對照**，
於是「在設計過程中想清楚的事」與「寫進文件的事」各自長大。

`_meta\cards\cyclosa.md` 裡其實有一段「設計過程中定案、**要寫進 ADR** 的幾件」，
列了四條 —— **那段話本身就是這條教訓的證據**：有人知道它們該進 ADR，
記了一筆備忘，然後那筆備忘停在卡片裡沒有下一步。

**怎麼修的**：把設計稿整份讀出來（artifact 的內容在 `appifact-doc` 那個 script 區塊裡），
逐條與 `docs/` 比對，列成 16 條的對照表，**逐條跟使用者確認之後**回寫：
新增 ADR-0015～0020，改 `state-machines.md`／`data-model.md`／`overview.md`，
新增 7 份架構文件。

**這一輪的做法也記下來**：設計稿的**連結只放在卡片**，不進 repo（它是私有 artifact，
放進預期公開的 repo 只會是一條別人打不開的連結）；
但**內容全部要回寫**，而且每條註明「來自 2026-09-05 設計稿」。

> **一份存在於版控之外的設計，會靜默地跟文件分岔 —— 而且分岔的方向是「設計比較新」。**
> 這比反過來危險：讀文件的人（或 LLM）會照著一份**已經被推翻過的**規格寫程式，
> 而文件本身讀起來完全正常，沒有任何地方說「這一段已經過期」。
>
> 對策不是「不要用設計工具」，而是**設計收尾的最後一步是回寫**，
> 而且回寫完成之前不要開始實作。
> 這條與上面那條 opt-in 檢查是同一個家族：**都是「有人做了對的事，但沒有人接下一棒」。**

**影響範圍**：全域

## 一條版本界線寫著「兩個獨立理由」，而其中一個是假的

**日期**：2026-09-06

**症狀**：`docs/environment/versions.md` 的 Node 下界寫著：

> **下界 24 有兩個獨立的理由，任一個都足夠：**
> 1. `node:sqlite`（2026-09-05 在 v24.15.0 上實測過）
> 2. **Vite 8 要 Node 24。**

要寫 `package.json` 之前逐條實查，結果第二條不成立：

```
vite 8.2.2 · engines.node = ^20.19.0 || >=22.12.0
```

**Vite 8 不要求 Node 24。**

**原因**：第一條有實測、第二條沒有 —— 它大概是從「Vite 8 是新版所以要新 Node」
推論出來的，而那個推論寫下來的時候跟實測的那條**長得一模一樣**：
同一張表、同樣的語氣、同樣沒有標示來源。

**怎麼修的**：把第二條刪掉，並在原地留一段說明它為什麼曾經在那裡。
同一輪順便查出另外兩條：`typescript-eslint` 8.69.0（最新）的 peer 仍是
`typescript >=4.8.4 <6.1.0`（所以 TS 要 `~6.0` 不是 `^6`，更不能用已經是 latest 的 7），
以及 `three` 的範圍要抄 `3d-force-graph` 自己宣告的 `>=0.179 <1`。

> **「兩個獨立的理由，任一個都足夠」這種寫法會讓人更不想去查。**
> 它聽起來像是已經被交叉驗證過 —— 而實際上是一條實測 ＋ 一條推論被放在同一個清單裡。
>
> 對策：**版本界線的每一條都要標它的來源**（實測／官方宣告／推論），
> 而**推論不算理由**。一條沒有來源標示的理由，下一個人沒辦法判斷該不該信它。

**影響範圍**：全域

## PowerShell 5.1 把原生指令的 stderr 當成錯誤，於是驗證閘門對成功的指令報失敗

**日期**：2026-09-07

**症狀**：`Verify.ps1` 在「測試」那一步中斷，訊息是

```
node.exe : {"ts":"...","level":"warn","msg":"資料根尚未就緒",...}
At line:1 char:1
    + CategoryInfo          : NotSpecified: (...) [], RemoteException
    + FullyQualifiedErrorId : NativeCommandError
```

**而那 134 個測試全部通過。** 被當成錯誤的那一行是測試裡的 app 自己印的一則 warn。

**原因**：兩件事疊在一起。

1. PS 5.1 把原生指令**寫到 stderr 的每一行**都包成 `ErrorRecord`；
   配上 `$ErrorActionPreference = 'Stop'`，那就直接中斷腳本 ——
   **即使那個指令最後回傳 exit code 0**。
2. e2e 測試刻意製造失敗（指標檔壞掉、指到不存在的路徑），
   所以 app 的 warn 日誌本來就會出現，而且**它出現正代表測試在做對的事**。

**兩層都要修，只修一層都不夠**：

- 應用層：`CYCLOSA_LOG_LEVEL` 加一個 `silent`，`vitest.config.ts` 把它設成 `silent`。
  測試輸出本來就不該被 app 日誌淹掉。
- 腳本層：`Verify.ps1` 的 `Invoke-Check` 在呼叫原生指令時把
  `$ErrorActionPreference` 降成 `Continue`，**只信 exit code**。

**只修應用層不夠** —— 任何 lint 或測試工具都可能用 stderr 印進度，
下一支這樣的工具會再撞一次。**只修腳本層也不夠** —— 測試輸出照樣被淹沒。

> **這一條與 `Get-Content -Raw` 讀成 Big5 是同一個家族**：
> PS 5.1 的預設行為對「跟原生工具互動」這件事是敵意的，
> 而它的失敗訊息永遠指向被呼叫的那個工具，不是指向 PowerShell 自己。
>
> 判準：**看到 `NativeCommandError` 就先問「那個指令的 exit code 是多少」**，
> 而不是先去讀它印了什麼。

**影響範圍**：全域

## 一條裸的 `snapshots/` 把文件區的環境快照一起擋掉了，而且沒有任何徵兆

**日期**：2026-09-07

**症狀**：`Verify.ps1 -Report` 印出「寫出 `docs\environment\snapshots\2026-09-07.md`」，
檔案也真的在那裡 —— 但 `git status` 看不到它。
同一時間 `docs/index.md` 剛把那一格從 ⬜ 改成 ✅。

**如果沒發現，結果會是**：clone 下來的人照著索引去找那份文件，找不到。
而索引用權威的語氣說它存在 —— 正是這個專案花最多力氣在防的那件事。

**原因**：`.gitignore` 的 Cyclosa 段落有一條裸的 `snapshots/`。
它的用意是「萬一有人把資料根指錯地方，至少專題快照不會直接進版控」，
而**裸的目錄名在 gitignore 裡是全域比對** —— 它擋的是任何一層的 `snapshots/`，
包括 `docs/environment/snapshots/`。

**怎麼修的**：換成只擋資料根實際會出現的名字（`cases/`、`sources/`、`derived/`、
`.local-data/`），並在那一段寫明文件側的 `snapshots/` 為什麼不在清單上。
順便補上 `*.sqlite-wal`／`*.sqlite-shm` —— WAL 模式會產生那兩個檔。

> **這個失敗沒有錯誤訊息、沒有紅燈、也沒有任何指令會抱怨。**
> 它只在「有人去 clone 然後照著文件找檔案」的時候才顯現，而那通常是很久以後。
>
> 判準：**寫一條擋東西的規則時，問它會不會擋到同名的其他目錄。**
> `cases/`、`sources/`、`derived/`、`snapshots/` 這種通用名詞特別危險 ——
> 它們在文件區、測試 fixture、範例資料夾裡都可能再出現一次。
>
> 更一般地：**加完 gitignore 規則之後跑一次 `git status`，確認該看到的還看得到。**
> 只確認「該擋的擋住了」是一半的驗證。

**影響範圍**：全域

## 「一鍵啟動」的資料夾裡有兩個入口，而雙擊錯的那一個會安靜地打開記事本

**日期**：2026-09-07

**症狀**：使用者第一次手動驗收，回報「`Launch.ps1` 預設是以筆記本開啟」。

**原因**：Windows 對 `.ps1` 的**預設動作是「編輯」而不是「執行」** ——
這是作業系統層的關聯，跟腳本本身無關，也不是執行原則（ExecutionPolicy）擋的。
`Start Cyclosa.cmd` 存在的唯一理由就是繞過這件事，
而**它在檔案總管裡跟 `Launch.ps1` 並排，兩個看起來都像入口**。

`README.md` 寫著「雙擊 `Start Cyclosa.cmd`」—— 但那句話在 repo 裡，
**而使用者當下看的是檔案總管**。文件解不了「兩個檔並排」這個版面問題。

**怎麼修的**：三處都改，因為它們對應三個不同的看到時機 ——

- `Launch.ps1` **第一行**加一個方框註解：「跳出記事本不是壞掉，去雙擊那個 `.cmd`」。
  **記事本打開時第一眼就會看到它**，這是唯一一個「已經點錯之後」還救得回來的位置
- `README.md` 加一段明說不要雙擊 `.ps1`，並在表格裡標明 `Launch.ps1` 要從終端機跑
- `operations/release-checklist.md` 的手動驗收改成明確走 `.cmd`

> **一鍵啟動的失敗模式不是「跑起來出錯」，是「使用者點了、然後什麼都沒發生」。**
> 後者不會產生任何錯誤訊息、日誌或 exit code，所以**沒有任何自動檢查抓得到它** ——
> 它只在真人第一次雙擊的時候顯現。
>
> 判準：**做一鍵入口時，看的是「檔案總管裡有幾個檔看起來像入口」，
> 而不是「文件裡寫了哪一個」。**

**影響範圍**：全域

## 一張憑印象列的字串清單，在真實頁面上命中 0 次

**日期**：2026-09-07

**症狀**：`looksJsOnly` 靠一張單頁應用骨架標記的清單判斷「這一頁要 JS 才有內容」——

>
> 判準：**一條靠「比對已知字串」運作的規則，要有一支腳本能回答
> 「它在真實資料上命中幾次」**，而那個數字要有人負責讓它 > 0。

## 語言偵測判不出來的時候，不會說判不出來

**日期**：2026-09-07

**症狀**：`multilingual.md` 從第一天就寫著「**偵測不出來記 `und`，不猜**」，
而那句話假設 `franc` 判不出來時會回 `und`。量測 34 個真實頁面時：

| 頁面 | 內容 | `franc` 的答案 |
|---|---|---|
| 一個模型說明頁 | 69 個字的英文 | **`fra`**（法文）|
| 一個中文論壇的索引頁 | 使用者代號 ＋ 日期 ＋ 少量中文 | **`deu`**（德文）|

**原因**：`franc` 用三連字母頻率比對，**它一定會挑出最像的那一個**。
輸入太短或太碎的時候，「最像的」與「對的」沒有關係 —— 而它的回傳值
看起來跟一個有把握的答案一模一樣。

**這件事的代價不是標籤錯，是索引走錯路**：一份中文內容被判成拉丁語系
就只進 FTS5 `unicode61`，而它會把一整段沒有空白的中文當成一個 token。
**使用者查兩個字回 0 列，而畫面上沒有任何地方說語言判錯了。**

**怎麼修的**：在偵測器外面加兩道**用證據推翻標籤**的閘門
（`infrastructure/extract/language.ts`）：字數少於 100 直接 `und`；
`franc` 的答案與文字的 CJK 比例矛盾時也回 `und`。
**兩道都只把答案推向 `und`**，而 `und` 的內容兩條索引都建 ——
推翻的代價是多一份索引，漏掉的代價是查不到。

> **判準：一個「不確定就說不確定」的規則，要先確認那個元件真的說得出不確定。**
> 這一條與上面那條是同一次量測抓到的，而兩條的共通點是
> **「文件描述的是我們希望那個元件的行為，不是它實際的行為」**。

**影響範圍**：全域

## 一個舊版的 server 還跑在同一個埠上，而一鍵啟動會安靜地開到它

**日期**：2026-09-07

> 這條規則保護不了一個被 `Stop-Process` 打斷的寫入。**告訴使用者，讓他決定。**
>
> 判準：**任何「已經在跑了就用那一個」的邏輯，都要問「那一個是不是同一版」。**

## 273 個測試全綠，而畫面上有四個錯 —— 3D 的正確性不在資料裡

**然後把畫面截下來看，一次照出四個錯**：

> 而 `Runtime.consoleAPICalled` 與 `Runtime.exceptionThrown` 要自己接 ——

## 一個「正規」的 API 是多餘的，而且它會安靜地把畫面弄壞

**日期**：2026-09-07

**症狀**：一鍵切 2D 的實作是兩行 —— 告訴 Web Worker 少算一個維度，
再呼叫 `3d-force-graph` 的 `numDimensions(2)`。按下去**整張圖空白**，
沒有例外、沒有 console 訊息、DOM 與資料都正常。

**原因**：那支 API 會觸發套件內部的佈局重新初始化。
而這個專案**刻意把套件自己的力全部拿掉**（`charge`／`center` 設 `null`、
`link` 留著但強度設 0），改用 Worker 算位置 —— 重跑初始化之後，
套件那一側的狀態與我們寫進去的座標就對不起來了。

**真正的問題是它根本不需要被呼叫**：位置一直是我們自己寫的，
維度是 Worker 的事，套件那一側只負責畫。
**那一行是「因為它看起來是正規做法」而加的，不是因為需要。**

**怎麼修的**：拿掉那一行，改成「送訊息給 Worker ＋ 把鏡頭移到正對那個平面」。
理由寫進 ADR-0007 的補記 —— 因為下一個人看到套件有 `numDimensions()`
一定會問「為什麼不用」。

> **接管了一個套件的某個職責之後，那個職責對應的 API 就變成陷阱。**
> 判準：**問「我已經自己做了這件事嗎」，而不是「這支 API 是不是正規做法」。**

**影響範圍**：全域

## 一個欄位在某些列上永遠是同一個值，而畫面把它當成資訊顯示了

**日期**：2026-09-08

**症狀**：Stage 8 的關聯面板第一次截圖，一次照出兩個互相獨立的錯：

1. 一條共同提及線的標題旁邊寫著「**待查證**」，而正下方那一句寫著
   「這是算出來的結果……**所以沒有確認與否決**」—— 同一屏上兩句話互相矛盾。
2. 一條剛手動連好的線旁邊寫著「**可信度：強**」，讀起來像有東西評估過它。

**原因**：兩個都不是「算錯」—— 資料庫裡的值完全正確，
**錯的是那些值在那些列上是結構性的，不帶資訊**：

| 欄位 | 在哪些列上 | 它其實是什麼 |
|---|---|---|
| `status` | 機器建的非 `named` 邊 | 永遠是 `pending`（trigger 逼的），不是「等你查證」 |
| `confidence` | 人手動建的邊 | 永遠是 1，**那是為了讓線畫得夠粗**，不是量出來的 |

**345 個測試沒有一個抓得到**，因為每個欄位的值都是對的。

**怎麼修的**：把「哪幾欄有意義」變成一條**領域層的函式**
（`domain/graph/render-rules.ts` 的 `edgePanelFieldsFor`），由伺服器算完送出去。
它原本是面板裡的**四個 `v-if`** —— 而一條規則寫在四個地方，
就是四個各自會漂的地方，且沒有一個測得到。

> **一個欄位「值是對的」不代表「顯示它是對的」。**
> 存進資料庫的理由可能是「讓 schema 簡單」或「畫面上要有個數字可用」，
> 而那兩種理由都不是「使用者該看到它」。
> 判準：**這一欄在這一列上，有沒有可能是別的值？** 不可能，就別顯示它 ——
> **顯示一個結構性的值，會讓它看起來像測量結果。**

**影響範圍**：全域

## 文件裡明確否決過的做法，實作照樣寫了出來，而測試資料剛好讓兩者看不出差別

**日期**：2026-09-08

**症狀**：校準比例（ADR-0017）實作成**全域平均** ——
而那一份的「考慮過但沒選的」有一列就是
「校準比例用全域平均（不分段）｜ 全域平均對每一條關聯給同一個數字，等於沒有資訊」。
**寫的時候看過那份 ADR，仍然寫錯了。**

更糟的是**測試全綠**：那組測試餵進 30 條機器邊去湊樣本，
而它給每一條各自的 `rel`（`合成關係-0`、`合成關係-1`…）——
於是**分段與不分段在那批資料上得到一樣的數字**。
測試驗到了「滿 30 條才給比例」「一條邊只算一票」，卻驗不到分段本身。

**原因**：ADR 的「決定」那一節寫的是**要做什麼**，
而「考慮過但沒選的」寫的是**不要做什麼** —— 實作時讀前者、跳過後者，
就會漏掉一整類的約束。**而「不要做什麼」正是那些看起來最自然的做法**，
所以它們是最容易被寫出來的。

**怎麼修的**：改成分段（`rel` × 等級），
測試固定資料改成**全部落在同一段**，另外加一組驗「別的段不算進來」。

> 兩條可操作的規矩：
>
> 1. **實作一份 ADR 時，「考慮過但沒選的」要跟「決定」一起讀** ——
>    它是規格的一部分，不是背景說明。
> 2. **測試固定資料如果讓「對的做法」與「錯的做法」得到相同結果，那條測試沒有在測那件事。**
>    造資料時要問：**這批資料能不能區分我要驗的那兩種實作？**

**影響範圍**：全域

## 前一階段的「圖例」承諾了一個當時沒有路徑可以觸發的畫法

**日期**：2026-09-08

**症狀**：Stage 8 第一次按下「否決」再打開「顯示已否決的」，
那條線回到圖上，**但沒有打叉** —— 它跟已確認的線只差在灰色深了一階

## 合成資料描述了一個真實寫入路徑產生不出來的狀態

**日期**：2026-09-08

**症狀**：Stage 9 補上「可信度從出處數出來」（`scoreFor`）之後，
Stage 8 的三條測試同時紅了 —— 而**它們紅的理由跟新規則本身無關**：
合成資料裡 `edg-acquire` 手寫成「4 筆出處、2 個獨立來源、可信度 0.85（強）」，
而照新規則那是 0.5（中）。

**原因**：那個 0.85 是**手挑的**。挑的時候它只需要滿足一件事 ——
大於 0.7，這樣畫面上會顯示「強」。

那時沒有任何規則說「可信度應該是多少」，所以它不算錯。
但它描述了一個**真實寫入路徑產生不出來的狀態**，
而合成資料存在的全部理由就是**拿來當真實資料看**：
四種畫法的驗收、面板的截圖、端對端測試全部靠它。

更麻煩的是校準比例那一批：`seedNamed` 也是「1 筆出處 ＋ 可信度 0.85」，
於是**只要有東西對它重新提案，它的可信度就會被算回去、跳出那一段**，
而失敗的測試看起來會像是校準比例壞了。**症狀離原因很遠。**

**怎麼修的**：`graph-fixture.ts` 結尾對每條具名邊呼叫 `recomputeConfidence`
（**跟真實寫入路徑同一支函式**），並補一份出處讓 `edg-acquire` 有三個獨立來源
—— 那才是「強」在新規則下真正的樣子。校準比例的固定資料同樣改成
用 `scoreFor` 算出來的值，而不是一個手挑的數字。

> **固定資料的欄位如果將來會有一條規則來算它，那現在就該用那條規則算**，
> 即使規則還沒寫 —— 因為手挑的值會在規則補上的那一天變成一個
> **看起來像 bug 的差異**，而它其實是「這份資料一直是假的」。
>
> 判準很好用：**這一列資料，真實的寫入路徑產得出來嗎？**
> 產不出來的話，用它做的驗收就不是驗收。

**影響範圍**：全域

## `shell: true` 在 Windows 上不替「命令」那一段加引號

**日期**：2026-09-08

**症狀**：接 agent 子程序時，測試裡用 `node <假的 CLI>` 當 provider，
而它一律回 `PROVIDER_UNREACHABLE`。畫面上的訊息是
「連不上這個模型。檢查它是不是沒開，或指令不在系統路徑上」——
**而那支程式明明在，手動跑也正常。**

**原因**：`spawn(command, args, { shell: process.platform === 'win32' })`。
`shell: true` 時 Node 把命令與參數接成一個字串交給 `cmd.exe`，
而**命令那一段不會被加引號**。`process.execPath` 是
`C:\Program Files\nodejs\node.exe` —— 於是被拆成兩個詞，
`cmd.exe` 去找一個叫 `C:\Program` 的東西，回一個非 0 的結束碼。

`shell: true` 當初是為了 Node 20.12 起不再直接 spawn `.cmd`／`.bat`
（那是一個命令注入的修補）而加的，**而那個理由只適用於那兩種副檔名**。

**怎麼修的**：`needsShell(command)` 只對 `.cmd`／`.bat` 回 `true`。
使用者填的是 `.exe` 或一個絕對路徑時一律不經過 shell ——
那同時也少一條把設定字串送進 shell 的路。

> **「非 0 結束碼」被對映成一句人話的時候，那句人話會蓋掉真正的原因。**
> 這裡的「連不上」在語意上沒有錯，但它把人送去檢查 PATH 與服務狀態，
> 而問題在我們自己傳的參數。**子程序起不來時，第一件事是把實際下的命令列印出來。**

**影響範圍**：全域（凡是在 Windows 上 spawn 子程序）

## 一條「取最大值」的更新規則，輸入每次都是同一個常數，等於它從來沒有生效

**日期**：2026-09-08

**症狀**：`applyProposal` 的重跑路徑寫著
`if (proposal.confidence > existing.confidence) setConfidence(...)`，
**測試全綠，而且它測的正是這一行**（提案帶一個比較高的分數進來，看它有沒有生效）。

Stage 9 接上真實的呼叫端之後才看出來：每一次提案都是
「**一份文件、一句引文**」，所以 `proposal.confidence` 永遠是
`scoreFor({ 1 個獨立來源, 有引文 })` —— **一個常數**。
於是第二個、第三個獨立來源永遠不會讓分數動，
而「獨立來源越多越可信」正是那個分數唯一在說的事。

畫面上的症狀會是：「出處 3 筆 · 3 個獨立來源」與「可信度：弱」同時出現，
**而沒有任何地方看得出那兩行是矛盾的。**

**原因**：測試餵的是一個**任意的**分數，而真實呼叫端餵的是一個**固定的**分數。
那條測試證明的是「這一行 `if` 會執行」，不是「這條規則在系統裡有作用」。

**怎麼修的**：改成 `recomputeConfidence` —— **重算的時機是「這條邊的出處變了」，
不是「有人提了一個新分數」**。分數從那條邊現在真的有的出處算出來。
測試也改掉：不再傳一個編出來的分數，而是**多提一個來自新 `item` 的出處**，
斷言分數從「1 個獨立來源」的值變成「2 個獨立來源」的值。

> **一個參數如果在所有真實呼叫點上都是同一個值，那它不是參數。**
> 而用一個「任意值」去測它，會讓那條規則在測試裡活著、在系統裡死掉。
> 寫測試時要問的是：**真實的呼叫端會不會傳出這種輸入？**

**影響範圍**：全域

## 「部分失敗」在一支只認得兩個數字的函式後面又被併進「失敗」

**日期**：2026-09-08

**症狀**：第一次真的跑一次擴展。agent 找到 6 個學術來源，其中 5 個是付費牆
（工具照規則不繞過），剩下那一個抽出了 **1 個節點與 9 條關聯**。
而作業紀錄那一頁的狀態寫著 **`失敗`** —— 上面寫著失敗，下面列著它寫進去的東西。

所以呼叫端必須先把每條角度歸成「成功」或「失敗」兩堆。

> 「部分失敗是一等公民」寫在 `settleRun` 上，

## `immediate` 的 watch 宣告在它用到的 `ref` 上面 —— 症狀是**畫面上什麼都沒說**

**日期**：2026-09-08

左邊的清單正常、那一列還被正確地標成選取中，沒有錯誤面板，沒有紅字。

**原因**：加點註功能的時候，新的 `ref`（`pending`、`pendingRect`、`locatedId`）

`immediate` 代表那個 watcher 在 setup 期間就跑一次 ——

並在它旁邊寫下為什麼位置有意義。

> **一個「看起來完全正常、只是少做了一件事」的畫面，比一個壞掉的畫面難找得多。**
> `<script setup>` 讀起來像一份宣告清單，而它其實是**由上而下執行的程式** ——
> 在裡面搬動一段程式碼跟在函式裡搬動一行是同一種風險。

**影響範圍**：全域

## Bash 工具會把 `\\` 收成 `\`，所以 heredoc 裡的正規表示式會壞掉

**症狀**：用 `python - <<'PY'` 改檔案，腳本裡寫 `"/\\n{2,}/"` 想產生
TypeScript 原本就有的 `/\n{2,}/`，而 `assert old in s` 一直失敗 ——
即使那段字串在檔案裡明明存在。

**原因**：**單引號的 heredoc 應該是完全字面的**，而實際到達 Python 的
`\\n` 已經被收成 `\n`。Python 再把它解讀成一個真的換行字元，
所以比對的對象跟檔案裡那兩個字元不是同一個東西。

同一天另一個變形：i18n 的字串裡想寫兩個換行的跳脫序列，

```python
BS = chr(92)
pattern = '/' + BS + 'n{2,}/g'
```

> 這是 `lessons.md` 裡第三條同一族的教訓（前兩條是 `node -e` 的引號、
> 以及 `.join` 寫進 heredoc 變成真的換行）。**跨越三層引號的字串
> 不要靠肉眼推理它最後長什麼樣，把危險字元組出來。**
>
> 順帶一提：**這一條的初稿自己被同一個 bug 弄壞了** ——
> 寫進去的範例在檔案裡變成了真的換行。

## 「沒有引文」有兩種原因，而印同一句話會讓其中一種說謊

**日期**：2026-09-08

**症狀**：Stage 11 的證據包產生出來之後讀一遍，八條待查證的關聯底下
每一條都寫著「這一條沒有引文 —— **它是人直接建立的主張**，不是從某一段文字抽出來的」。

**那八條全部是機器提出的。**

**原因**：判斷寫成了「引文陣列是空的 → 那就是人建的」。
而那個推論在寫下的當天是對的 —— 當時腦子裡的例子只有「手動連線」那一種。

實際上「沒有引文」的兩種原因**意思相反**：

| 誰 | 沒有引文代表 |
|---|---|
| `origin='human'` | 正常。**出處就是建立它的那個人**（Stage 8） |
| `origin='machine'` | **不對。** 它確認不了 —— 資料庫的觸發器要求機器提出的關聯至少有一筆出處 |

於是一條機器提出、沒有出處的邊，在證據包裡看起來像有人替它背書。
**而證據包正是拿去給別人看的那一份東西。**

同一批還抓到第二個同形狀的：待查證那一組的結語寫著「它們帶著引文」，
**而那八條一條引文都沒有** —— 那句話也是無條件印出來的。

**怎麼修的**：兩處都改成看實際狀態（`origin` 與「這一組裡有沒有人帶引文」），
並各補一條測試。

> **把一句話寫死在一個它只在某些情況下為真的位置，測試不會紅** ——
> 那句話是文案，而文案沒有型別。這一族的錯只有把產生出來的東西讀一遍才看得到。
> Stage 8、10、10.5、11 各有一次人工驗收抓到測試抓不到的錯，**四次全部是這樣抓到的。**

**影響範圍**：全域

## `Start-Process` 開的子程序不會跟著父視窗死，而畫面上寫著它會

**日期**：2026-09-08

**症狀**：使用者問「一鍵啟動開的兩個視窗要不要關掉」。查下去發現的不是視窗數量的問題。

`Launch.ps1` 用 `Start-Process -WindowStyle Minimized` 起 server，而畫面上印著：

```
關掉這個視窗（或按 Enter）就會結束 Cyclosa。
```

**那句話只有按 Enter 那半是真的。**

**原因**：`Start-Process` 不加 `-NoNewWindow` 會給子程序**自己的主控台**，
而且不放進 job object。所以：

- 按 Enter → `Read-Host` 返回 → 後面那行 `Stop-Process` 跑得到 → 收得掉
- 按 X 關掉視窗 → PowerShell 直接死 → **`Stop-Process` 那一行永遠不會執行**，
  而子程序掛在另一個主控台上，`CTRL_CLOSE_EVENT` 也送不到它

實測確認過：從一個 PowerShell 這樣起一個 node，父程序結束之後子程序還活著。

留下來的是一個**最小化的**、佔著 7433 的 server —— 而下一次啟動會因為
單一實例偵測（ADR-0020）直接把瀏覽器指向它，所以**連「怎麼還開著」都不會被發現**。

**怎麼修的**：`-NoNewWindow`。子程序共用父視窗的主控台，
關掉視窗時 Windows 把 `CTRL_CLOSE_EVENT` 送給掛在上面的每一個程序。
一個視窗，兩條路都真的會結束。

> **2026-09-09 後續：這個修法本身在 v0.9.1 被換掉了**（ADR-0025）。
> 它換來的是**一個必須一直開著的黑框**，而使用者要的是沒有那個東西。
> 現在 server 用 `-WindowStyle Hidden` 起在自己的主控台上、啟動器做完就退場，
> 結束改由畫面上那顆按鈕負責 —— **那顆按鈕在寫這一條的時候還不存在。**
> 這一條記的教訓沒有變：**一句寫在畫面上的承諾也是一種介面**，
> 而現在那句話變成「要結束請用畫面右上角的『結束 Cyclosa』」。

> **一句寫在畫面上的承諾也是一種介面。** 這一條跟
> 「沒有引文＝人建立的」是同一族：**一句話寫死在一個它只有一半為真的位置**，
> 而沒有任何一條測試會紅 —— 它要嘛靠人按一次 X，要嘛靠人問一句。

**影響範圍**：全域

## 一條只守一個檔的規則，守的不是那條規則，是那個檔

**日期**：2026-09-08

**症狀**：使用者截圖給我看「來源網站」那一頁，上面有七條寫著
「幾乎都要機構授權。\*\*這是最常撞到的那一個。\*\*」這種東西 —— 畫面上一堆星號。

**而我當天稍早才為同一個錯加過一條守門測試。**

**原因**：那條測試寫的是

```ts
const FILE = join(REPO_ROOT, 'web', 'src', 'i18n', 'zh-TW.ts');
```

它抓到了 `i18n` 裡的六條，然後就停在那裡了。
而**同一個錯的另外七條在 `src/infrastructure/sources/catalog.ts` 的 `noteZh` 欄位裡** ——
那些字一路印到畫面上，跟 i18n 的那些沒有任何差別。

規則本來是「**會被印到畫面上的中文字串是純文字**」，
而寫下來的是「`zh-TW.ts` 裡沒有星號」。**兩者不一樣，而測試守的是後者。**

**怎麼修的**：把那條測試改成掃一份**名單**，而名單的判準寫在檔頭：
**「這些字會被當成純文字印出來嗎」**。所以 `domain/export/pack.ts` 不在名單上 ——
它產生的是 Markdown 檔案，`**…**` 在那裡是正確的輸出。

> **加守門測試的時候要問的不是「這個檔會不會再犯」，是「這條規則管的是什麼」。**
> 前者只會讓下一次的同一個錯換一個檔案出現。

**影響範圍**：全域

## 原生指令寫到 stderr 不等於失敗，而 `$ErrorActionPreference = 'Stop'` 會把它當成失敗

**日期**：2026-09-09

**症狀**：改完啟動器實跑一次，畫面停在

```
=== 檢查建置產物
  原始碼比產物新
node.exe : [plugin builtin:vite-reporter]
```

然後整支腳本以 1 結束，server 沒起來。**而 `npm run build` 手動跑是成功的。**

**原因**：`vite build` 成功的時候也會往 stderr 印一段
「有 chunk 大於 500 kB」的警告。PowerShell 5.1 在**輸出被導向**的時候
（從另一支腳本呼叫、或在會收集輸出的終端機裡跑）會把原生指令的 stderr
每一行包成 `ErrorRecord`；而 `$ErrorActionPreference = 'Stop'` 之下，
那個 ErrorRecord 是**終止性錯誤**。

於是一個警告變成「建置失敗」，而 npm 其實回了 0。
**在真的主控台裡雙擊不會發生** —— 沒有導向就沒有 ErrorRecord。
所以這是一種只在「被別人呼叫」時才出現的壞法。

**怎麼修的**：原生指令一律走 `Invoke-Native`：裡面把 `$ErrorActionPreference`
暫時放回 `Continue`，回傳 `$LASTEXITCODE`。**判準只有離開碼一個。**

> `tagcor-ledger` 的 `Launch.ps1` 早就寫過同一件事的另一半
> （「用 `2>&1` 收原生指令的輸出會拿到 ErrorRecord」），而**它記在那個專案裡**。
> 兩個專案各踩一次同一個坑，中間隔了三週。

**影響範圍**：全域（所有 `.ps1` 呼叫原生指令的地方）

## Ollama 上的模型名字不等於它是哪一個模型

**日期**：2026-09-09

**症狀**：要評測 `paraphrase-multilingual`，去抓
`sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` 的 model card
來確認前綴與維度 —— 那是同名家族裡最有名的一個。抓回來寫著 384 維。

然後 `ollama show paraphrase-multilingual` 回的是 **768 維、277.45M 參數、`num_ctx 128`**。
對不上。

**原因**：Ollama 那個 tag 底下裝的是 **`paraphrase-multilingual-mpnet-base-v2`**，
不是 MiniLM。兩個都叫「paraphrase-multilingual」，維度差一倍。

如果沒有對過參數量，這次評測會拿一份**錯的 model card** 去決定
「這個模型要不要加前綴、維度多少、上下文多長」，而三個答案都會錯。
更糟的是**它不會報錯** —— 向量照樣算得出來，分數照樣有一個數字。

**怎麼修的**：改成用 `ollama show` 回的**參數量與 `num_ctx` 去反查是哪一個模型**，
再抓那一個的 card。`num_ctx 128` 是決定性的線索 —— mpnet-base-v2 的
`max_seq_length` 就是 128，MiniLM-L12-v2 也是 128，但參數量差得遠（278M 對 118M）。

**怎麼不再犯**：`_meta\models.json` 每一列都記了它到底對應到哪一個 HF repo，
而不是只記 Ollama 的 tag。授權欄位也註明是從哪個 URL 的哪個欄位查來的。

> 這件事對這個專案特別要緊：嵌入模型是唯一實質不可逆的決定，
> 而「名字對了、模型不對」是一種**靜默**的錯 —— 跟 ADR-0009 講的
> 「兩個不同模型的向量照樣算得出餘弦」是同一種病，只是發生在更前面一步。

**影響範圍**：全域

## 自己的 robots 檢查擋住自己的量測腳本 —— 那是成功不是故障

**日期**：2026-09-09

**症狀**：嵌入評測要抓 34 頁 Wikipedia 當語料，走的是專案自己的 `Crawler`。
34 個請求**全部**回 `FETCH_ROBOTS_DISALLOWED`，一頁都沒抓到。

**原因**：第一版用的是 `https://zh.wikipedia.org/w/api.php?action=query&…`，
因為 API 直接吐純文字比跑 Readability 乾淨。但 Wikipedia 的 `robots.txt`
對 `User-agent: *` 寫著 `Disallow: /w/` 與 `Disallow: /api/`，
只放行 `action=mobileview` 與 `load.php`。

**當下的誘惑是去改檢查**（「這是官方 API，本來就該給程式用」）。
那個念頭要記下來，因為它聽起來很合理，而且只要改一行。

**怎麼修的**：改路徑不改檢查。`/wiki/<Title>` 與 `/zh-tw/<Title>` 都在放行範圍內，
所以第二版抓 HTML 再走 `decodeHtml` → `extractHtml`。
**換過來反而更貼近真實**：語料經過的是完整的匯入管線，
而不是一個吐好純文字的 API —— 量測走另一條路的話，量到的就不是使用者會遇到的東西。

> **一條從來沒有擋過任何東西的規則，跟一條寫壞的規則長得一模一樣。**
> 這是這條 robots 檢查上線以來第一次真的攔下請求，而攔的是我們自己。

## 一個沒有宣告需求的任務，「配不上就停手」那條規則對它等於不存在

**日期**：2026-09-09

**症狀**：ADR-0006 第 3 條是這個專案對 provider 最重要的一條規則 ——
「配不上就報 `PROVIDER_CAPABILITY_MISSING` 並停手，不靜默降級」。
它有兩個 `TaskRequirement`（`TASK_ANGLES`、`TASK_FIND_SOURCES`），
兩個都有閘門，兩個都有測試。

而 `chat` 底下其實有**三**件事要做，第三件是「從抓回來的正文抽實體與關係」——
**它沒有 `TaskRequirement`，所以也沒有閘門。**

**原因**：規則寫成「每個任務宣告需求」，而漏掉一個宣告**沒有任何症狀**。
不是檢查失敗，不是誤報，是**那個任務從來不在檢查範圍內**。
`grep TASK_` 看到兩個，而三份 schema 在另一個檔案裡 —— 兩邊沒有任何東西連著。

**代價有多具體**：抽取那一步吃 12,000 字的外部正文，而角度那一步只吃標題清單。
一個 8000 context 的模型會通過角度那一關、抓完全部網址，
然後在每一份文件上把正文截掉一半 —— **抽出來的關聯照樣帶引文、照樣進待查證。**
自動降級至少還有「降級了」這個事實可以顯示在畫面上；這個連事實都不存在。

**怎麼修的**：補 `TASK_EXTRACT`（`json_schema` ＋ 18000 context），
閘門放在勾選那一步（抓之前，不是每份文件一次）。
另外補一條守門測試把 `MAX_TEXT_CHARS`（application 層）與
`TASK_EXTRACT.minContextTokens`（domain 層）綁在一起 ——
**它們在不同的層，而分層之後改一個很容易忘了另一個。**

**同一次修掉的第二件**：`missingFor` 早就會回「旗標齊了、只是 context 不夠」，
而三個呼叫端都只帶 `flags` 出去 —— 畫面上顯示的是「缺少：（空白）」。
**它說了有問題，卻沒說是什麼問題。**

> 這是「零命中跟零誤報長得一模一樣」的更前面一步：
> **這裡連零命中都沒有，因為根本沒有那條檢查。**
> 通則是：**一條只作用在「已宣告項目」上的規則，漏掉宣告等於漏掉規則，
> 而漏掉不會有症狀。** 要抓這種漏，需要一條從**另一個方向**數的檢查 ——
> 就像 `D:\Projects` 的模型清冊後來加的 `model-owner-undeclared`。

**影響範圍**：全域

## 字元不是 token，而差多少取決於哪一個 tokenizer

**日期**：2026-09-09

**症狀**：要替「送 12,000 字正文給模型」定一個 context 門檻。
直覺是「中文一個字大約一個 token，抓 12,000 再加一點」。

拿同一段 12,000 字的中文，用 Ollama 的 `prompt_eval_count` 實測三個家族：

| tokenizer | token 數 | 每字元 |
|---|---|---|
| Gemma（`translategemma:12b`）| 8,048 | 0.67 |
| Nemotron（`nemotron-cascade-2:30b`）| 11,185 | 0.93 |
| **OLMo（`olmo-3:32b-think`）** | **14,383** | **1.20** |

**同一段字，最多與最少差 1.8 倍。** 那個直覺對其中兩個是錯的 ——
一個高估 50%，一個低估 20%。

同樣 12,000 字元的**英文**在 Gemma 底下只有 2,637 token（0.22）——
所以同一個門檻對英文來源是過度保守的，而那是刻意的：
**不夠大的下場是正文被截掉而不報錯。**

**怎麼修的**：門檻取最壞的那一個（1.20）再加提示詞與輸出，
而那個比例存成 `WORST_TOKENS_PER_CHAR`，由守門測試拿去換算。
**只用一個模型量出來的比例，不能當成「模型」的比例。**

**影響範圍**：全域

## 模型宣告的 context 上限，不是它實際被載入時的 context —— 而更多時候它根本沒宣告

**日期**：2026-09-09（同日修正過一次，見下方「這一條原本寫錯了」）

**症狀**：補完 `TASK_EXTRACT` 的 context 閘門之後跑評測，順手看了一眼 `ollama ps`，
載入的 context 是 **32768**；而 `/api/tags` 對 `nemotron-cascade-2:30b` 回的
`details.context_length` 是 **262144**。**閘門看的是後者，執行時用的是前者。**

**原因**：`context_length` 是**模型支援的上限**；Ollama 實際載入時用的是
`OLLAMA_CONTEXT_LENGTH`（使用者沒設就是內建預設）。兩個都叫 context，
一個是「這個模型最多能到多少」，一個是「這次載入實際開了多少」。

**而同一天稍後量到一件更糟的**：`gemma4:31b` 與 `translategemma:12b` 的
`details` 裡**根本沒有 `context_length` 這一欄**。`capabilitiesOf` 對缺欄位給 0，
而 0 的意思是「不知道」，`missingFor` 對不知道是**放行**的 ——
所以閘門對這兩個模型從頭到尾沒有任何意見。

> ### 這一條原本寫錯了
>
> 第一版把 262144 寫成 `gemma4:31b` 的宣告。**那是 `nemotron-cascade-2:30b` 的。**
> 錯誤來自同一次量測裡兩個模型的輸出被記混，而**沒有回去看原始回應**。
> 回去 `curl /api/tags` 逐一 dump `details` 才發現 gemma4 那一欄是缺的。
>
> 這個錯誤會傳染：它同時出現在 `capabilities.ts`、`chat-ollama.ts`、
> 守門測試與 ADR-0006 —— 因為後面四處都是抄第一處寫的。
> **一個沒查證的觀察被寫進註解之後，會以「已知事實」的身分擴散。**

**怎麼修的**：請求裡明確帶 `num_ctx` —— 不管對方宣告了什麼、有沒有宣告，
這次開多大由我們說了算。

**而第一版的 `num_ctx` 值也是錯的。** 它取了「閘門的門檻」（當時 18000），
於是把視窗從 Ollama 預設的 32768 **縮小**到 18000。門檻與視窗是兩件事：

| | 回答什麼 | 取法 |
|---|---|---|
| 門檻 `minContextTokens` | 這個模型**夠不夠格**接這個任務 | 輸入上界 ＋ 輸出預算 |
| 視窗 `num_ctx` | 這次請求**配置多大** | 同上 —— 但理由是算出來的，不是「跟門檻一樣」 |

把後者設成前者，等於把餘裕設成零。實測 `gemma4:31b` 抽一份 12,000 字的中文
用掉 87%，再多一點就滿，而**滿了之後 Ollama 回的是一份空字串**。
現在兩個都是 24,000，而那是 15,000（輸入上界）＋ 8,000（輸出預算）算出來的。

> **通則**：一個能力宣告如果來自「規格」，就要確認執行時真的照那個規格跑。
> 規格上的數字與執行時的數字**同名不同義**是很常見的，
> 而它們不一致的時候沒有任何一端會抱怨。
> **而「宣告不存在」比「宣告不準」更常見，也更容易被當成沒問題。**

**影響範圍**：全域

## 上限寫在正規化那一層，而模型看不到它

**日期**：2026-09-09

**症狀**：`translategemma:12b` 抽一份 12,000 字的中文，**吐出 24,930 個字元的非 JSON**，
花 97 秒（另一次是 55,467 個字元、208 秒）。`format` 帶了整份 schema，
而受限解碼**沒有守住**。

**原因**：`EXTRACT_SCHEMA` 的兩個陣列**沒有 `maxItems`**。
受限解碼保證的是**形狀**，而一個沒有上界的陣列**在任何長度都是合法的形狀** ——
文法從頭到尾沒有被要求管長度，模型於是一路吐到 context 用完，
回來的是一份被截斷的、解不開的東西（`done_reason: "length"`，內容常常是空字串）。

而 `normalizeExtraction` **一直都有**上限：`MAX_ENTITIES` / `MAX_RELATIONS` 各 20，
名稱 80 字、關係詞 40 字，引文超過 500 字 `locateQuote` 直接當找不到。
**那些丟棄全部發生在模型生完之後** —— 時間花了、視窗佔了，然後才丟。

機械上的原因只有四個字：`MAX_ANGLES` 是 `export` 的，所以 `ANGLES_SCHEMA`
一直帶著 `maxItems`，**角度那一步從來沒有失控過**；而 `MAX_ENTITIES` 那幾個
當時是私有的 `const`，`EXTRACT_SCHEMA` 那一層**拿不到**。

**怎麼修的**：把那四個常數 `export` 出來，寫進 `EXTRACT_SCHEMA` 的
`maxItems` / `maxLength` / `minLength`。同一個模型、同一份正文、同一個 `num_ctx`
冷啟動各跑兩次：

| schema | 輸出 token | 視窗用掉 | `done_reason` | 秒 | 結果 |
|---|---|---|---|---|---|
| 沒有上界 | 11,474 | **101%** | `length` | 97.0 / 92.6 | 24,930 字非 JSON |
| 有上界 | **1,627** | 46% | `stop` | **16.4 / 16.4** | 20 實體、20 關係 |

守門測試 `tests/guards/extract-context.test.ts` 釘住「兩邊的上限是同一個數字」。

> **通則**：**一個約束要寫在它會生效的那一層。** 寫在下游的，
> 上游不會知道；而上游不知道的時候，它做的是白工 ——
> 白工的成本在本機模型上就是使用者的秒數與顯示記憶體。
> 找這種缺口有一個現成的方法：**同一份程式裡有沒有一個「已經做對了」的兄弟**。
> 角度那一步就是抽取那一步的兄弟，而兩者只差一個 `export`。

**影響範圍**：全域

## 沒有帶的那個參數，也是一個決定

**日期**：2026-09-09

**症狀**：`chat` 的第二輪評測，八個本機模型裡有五個抽取時好時壞，
兩個完全交不出東西，秒數從 5 秒到 300 秒都有。看起來像是「這些模型不夠好」。

**原因**：請求裡沒有 `think` 這一欄。**那不是「用預設值」，那是「用對方的預設值」** ——
而新一代的模型多半預設開著思考，**包括沒有在 `/api/tags` 宣告 `thinking` 的那些**
（`granite4.2:8b` 的 capabilities 只有 `completion`，實測同一份正文開著是
18,628 個輸出 token／125 秒，關掉是 2,356／16 秒）。

八個模型裡**七個**只因為多了 `think: false` 就從時好時壞變成六次全過。

**怎麼修的**：`chat-ollama.ts` 明確送 `think: false`，守門測試釘著那一行。
而做這個決定的依據不是「快比較好」，是**對照組**：
`translategemma:12b`（真的不思考）開與關**一個 token 都沒有變** ——
所以送它不會有副作用。

反例也量到了：`olmo-3:32b-think` 關掉之後完全不動（每次剛好 10 個 token 然後空的）。
仍然寫死，因為它開著思考本來就是 0/6。**沒有加「空回應就拿掉那一欄重試」的退路** ——
那會讓結果來自一組跟畫面顯示不同的設定，正是 ADR-0006 第 3 條說的靜默降級。

> **通則**：**每一個沒有帶的參數，都是把那個決定交給對方**。
> 對方的預設會變、會跟它自己的宣告不一致，而且**不會有任何地方通知你**。
> 找這種東西有一個現成的方法：把請求印出來，逐欄問「這一欄是誰決定的」。
> 同一天在 `num_ctx` 上也踩過一次。

**影響範圍**：全域

## 一個聽起來合理的解釋，會以「已知事實」的身分擴散

**日期**：2026-09-09

**症狀**：v0.10.3 記著 `nemotron-cascade-2:30b` 抽取六次全部回 0 個字元，
而且逐段加長之後**斷在 500 到 800 個字元之間**。那個觀察是真的。

接在後面的是一句解釋：「架構是 `nemotron_h_moe`（Mamba 與 Transformer 的混合 MoE），
**合理的解釋是受限解碼在這個架構上沒有被完整支援**」。

**原因**：那句話**沒有被任何實驗分開過**。它只是一個聽起來合理的說法，
而它用敘述句寫進了研究文件、然後被抄進 ADR-0006 與 changelog。

同一支探針加上 `--no-think` 重跑：200 到 2000 字**全部正常**，
那個模型的抽取從 0/6 變成 6/6。**斷掉的是思考，不是文法。**

**怎麼修的**：三處都加了更正註記（不是默默改掉 —— 錯誤的傳播路徑本身是這一條的重點），
`probe-schema-limit.ts` 收 `--no-think`，讓下次能直接問出來。

> **通則**：觀察與解釋要分開寫，而且**解釋要標出它有沒有被驗證過**。
> 一個未經驗證的解釋比沒有解釋更糟：它會讓下一個人不再去查，
> 而且它擴散得比原始觀察快 —— 因為解釋比數字好記、好轉述。
>
> 同一輪還踩到兩次同樣的形狀：
> 「`/api/tags` 對 `gemma4:31b` 回 262144」（其實那是 nemotron 的）
> 與「同一個血緣，tokenizer 差兩倍」（其實是思考把 `prompt_eval_count` 灌水了）。
> **三次都是「從一次量測讀出一個結論，而沒有控制住變因」。**

**影響範圍**：全域

## `json_schema: true` 對每個模型都宣告 true，而其中兩個做不到

**日期**：2026-09-09

**症狀**：`capabilitiesOf` 對**每一個** Ollama 模型都回 `json_schema: true`，
理由寫在那一行旁邊：「伺服器功能：`format` 收整份 schema 並用受限解碼保證它」。
那句話在格式上是對的 —— 它是 Ollama 的功能，不是模型的能力。

而 ADR-0006 的閘門就是靠這個宣告決定要不要停手。

實測四個本機模型跑抽取那一題（12,000 字正文、`EXTRACT_SCHEMA`，各三次）：

| 模型 | 六次裡成功幾次 | 失敗長什麼樣 |
|---|---|---|
| `translategemma:12b` | 5 | 一次吐了 **55,467 個字元的非 JSON** |
| `gemma4:31b` | 3 | 逾時 |
| `olmo-3:32b-think` | **0** | 每次要 278–292 秒，而出貨的逾時是 180 |
| `nemotron-cascade-2:30b` | **0** | **每次回 0 個字元，只花 1–4 秒** |

**兩個模型的 `json_schema: true` 是錯的，而閘門看不出來。**
使用者會通過設定頁的綠勾、通過勾選那一關、抓完全部網址，
然後每一份文件都拿到一個錯誤碼。

**還有一次受限解碼直接沒守住**：`format` 帶了整份 schema，
而回來的是五萬多字的散文。

**怎麼修的**：**還沒有修。** 這一條先寫下來，因為修法本身有代價 ——
「送一次真的試試看」要花掉一次模型載入，而本機模型一次只常駐一個，
所以光是打開設定頁就會把使用者正在用的模型擠出去。
設定頁那顆「實際打一次」是現成的位置，**但這一輪的結果顯示最小的請求測不出來**：
`nemotron` 在角度那一題（比較簡單的 schema）三次全過。

> **通則**：一個「由平台提供、所以對每個模型都成立」的能力，
> 在平台那一層是真的，在模型那一層不一定。
> **能力宣告的粒度要跟真正會失敗的那一層對齊** ——
> 這裡失敗的是模型，而宣告寫在平台。

### 這張表後來幾乎整張作廢

同一天稍後量到：**那四種失敗裡有三種是同一個原因** ——
請求沒有帶 `think`，於是吃了模型自己的預設，而它們預設開著思考。
送 `think: false` 之後：

| 模型 | 原本 | 之後 |
|---|---|---|
| `nemotron-cascade-2:30b` | 0/6（1–4 秒回 0 字元）| **6/6** |
| `gemma4:31b` | 3/6（逾時）| **6/6** |
| `translategemma:12b` | 5/6（一次 55,467 字非 JSON）| 6/6 —— **而那一次是 `EXTRACT_SCHEMA` 沒有 `maxItems`**，見上面那一條 |
| `olmo-3:32b-think` | 0/6 | **0/6（關掉之後完全不動）** |

**這一條本身沒有作廢**：`json_schema: true` 確實是平台級的宣告，
而它確實擋不住「宣告說有而其實沒有」——`olmo-3` 兩種設定都交不出東西就是。
作廢的是**那張表對成因的歸因**，以及「兩個模型做不到」這個數字。

留著它是刻意的：**這一條的價值現在有一半在「它錯在哪」** ——
四種看起來不同的失敗，成因是同一欄沒有送出去的參數。

**影響範圍**：全域

## 設計指標的時候猜錯了風險，而量測把它糾正過來

**日期**：2026-09-09

**症狀**：替 `chat` 設計評測時，我把**引文命中率**列成最重要的一欄，
理由寫得很有說服力：`locateQuote` 找不到的引文那條邊就不存在，
所以這一欄直接量「模型有沒有捏造原文」。

量完之後：跨全部模型、有輸出的每一次，引文命中率是 **49/50**，
兩個主要候選都是 **100%**。**那個風險沒有發生。**

真正的失敗模式是**根本沒有輸出** —— 逾時、空回應、或者一次五萬字的非 JSON。
六次抽取裡失敗四次的模型有兩個，而它們失敗的方式都不是「引文不對」。

**怎麼修的**：指標留著（它證明了那個風險不存在，那也是結論），
但結論改寫成「這一輪要防的是可用性不是幻覺」。

> **這一條不是「量測設計錯了」。** 量了才知道要防什麼 —— 而如果只量了
> 引文命中率一欄，四個模型會全部拿到 86–100% 的漂亮分數，
> **然後我們會選一個六次裡有四次交不出東西的模型。**
> 多量一欄「schema 有效率」的成本幾乎是零，而它是那一輪唯一有鑑別度的欄位。

**影響範圍**：全域

## 設定多了一個軸，而每一個「拿那一個」的地方都還在拿舊的那一個

**日期**：2026-09-10

**症狀**：`chat` 從「一個模型」變成「一個預設 ＋ 逐任務覆寫」。
覆寫本身很小 —— 設定檔多一欄、`registry` 多一支 `chatFor(task)`。
接完之後兩個任務確實跑在不同的模型上。

**而閘門還在檢查預設那一個。** `missingFor` 拿的是 `providers.chat`
的能力宣告，那一行在覆寫存在之前是對的，之後仍然編譯得過、
仍然會執行、仍然會通過。

**原因**：多一個軸的時候，舊程式碼裡每一個「拿那一個」都還解析得出東西 ——
**它解析出來的只是不再是實際會跑的那一個。** 型別不會變，
名字不會變（`providers.chat` 讀起來仍然完全合理），
所以編譯器與測試都不會說話。

**代價有多具體**：把抽取覆寫到一個 10,000 context 的模型上，
設定頁那一格顯示的是預設模型（128k、綠的），擴展照常開始，
然後每一份文件的正文被截掉一半 —— 抽出來的關聯照樣帶引文、照樣進待查證。
**跟 2026-09-09 那個「沒有宣告的任務」是同一種結果，但成因相反**：
那一次是規則沒有涵蓋到那個任務，這一次是規則涵蓋到了、卻檢查了另一個對象。

**怎麼修的**：三件事，而第三件才是真正防得住下一次的：

1. `describeProviders` 逐任務 probe（同一個模型只打一次）
2. 角色層那一格改成逐任務結果的**合併**，不再自己算
3. **e2e 的斷言看的是送出去的請求裡的 `model`** ——
   不是回傳值、不是資料庫、不是錯誤碼。覆寫失效的時候那三樣全部正常，
   唯一不一樣的是那一欄。把 `chatFor` 改回 `chat` 之後那一組確實變紅（實際跑過）。

> **通則**：一個設定從「一個值」變成「一張表」時，
> 要找的不是「哪裡會壞」，是**「哪裡還在拿那一個值」** ——
> 而後者 grep 得到，前者只能用想的。
> 這次是 `providers.chat` 的四個呼叫端，其中兩個要改、兩個不用改
> （設定頁的「實際打一次」按的就是預設那一支）。
> **一個都不改也會全部通過**，所以那次 grep 是必要的，不是保險。

**影響範圍**：全域

## 一個「不知道」的預設值，掉進了「另一邊」的分支

**日期**：2026-09-10

**症狀**：語意檢索接完，假向量的端對端測試十條全綠。換成真的
`qwen3-embedding:4b` 跑三份文件三條查詢 —— **第三題答錯**（問光合作用，回蜘蛛）。

第一個念頭是「模型不夠好」。印出實際的餘弦分數才看到真相：
**那份文件根本沒有向量**，表裡只有兩條。模型的分數其實很乾淨
（蜘蛛那題 0.77 對 0.27）。

**原因**：切段的參數是 `chunkRuleFor(item.lang)`，而那份文件只有 97 個字 ——
**短於 `detectLanguage` 的 `MIN_SAMPLE_CHARS`（100），所以 `lang` 是 `und`。**
`isCjkLanguage('und')` 是 false，於是套上拉丁那組（`min 320`），
97 < 320，切出零段，沒有向量。

`und` 在這個 repo 裡是一個**明確定義過的「不知道」**：`indexTargets` 對它
**兩條索引都建**，正是因為不知道就不該挑一邊。而 `isCjkLanguage` 回的是布林，
**布林沒有第三個值** —— 所以「不知道」在那個分支裡自動變成「不是」。

**代價有多具體**：那份資料匯入成功、全文檢索查得到、只有語意檢索永遠找不到它。
**而回填會永遠回報「還有 1 份沒算」**（`processed` 每次 1、`written` 每次 0、
`remaining` 不動）—— 一個轉不完的迴圈。

**怎麼修的**：三處，而第一處才是根治的：

1. **切段參數改看 `cjkRatio(text)`，不看語言碼。** `cjkRatio` 自己的註解
   早就寫了通則 —— 「語言偵測會給出自信而錯誤的答案，所以路由要看得到證據，
   不能只看標籤」。那句話寫於 2026-09-07，而三天後我在隔壁又犯了一次。
2. 整份文件切不出一段時，**整份當成一段**。`min` 那條門檻是用來丟
   文件裡的碎片的，不是用來丟整份短文件的。
3. **回填迴圈自己收斂**（`remaining` 沒變少就停）——
   一個只在對方乖乖回話時才會停的迴圈，是靠對方守的規則。

> **通則**：一個型別上是布林、語意上有三個值的判斷，
> **「不知道」會靜靜地落進 `false` 那一邊**，而那一邊通常是「照另一種處理」。
> 找法是可靠的：`grep` 那個哨兵值（這裡是 `und`），
> 看每一個用到它的地方**有沒有替它寫一條分支**。

**影響範圍**：全域

## 十條假資料的測試全綠，而真的跑一次就錯了一題

**日期**：2026-09-10

**症狀**：語意檢索的 e2e 用一個確定性的假嵌入端點（關鍵詞 → 維度），
十條全過。那份測試是**對的**，它證明了接線是通的：
切段、寫 BLOB、逐批比對、名次合併、狀態標記，每一段都真的跑過。

而它證明不了的那一件，正好是壞掉的那一件：**真實文字會不會切出零段。**

假資料的每一份都是我寫的，而我寫的時候**照著門檻寫** ——
所以每一份都剛好越過 120 個字元。

**原因**：合成資料由「知道規則的人」產生，於是它**天生落在規則的正常路徑上**。
這跟 2026-09-07 那條「合成資料描述了一個真實寫入路徑產生不出來的狀態」
是同一枚硬幣的兩面：那一次合成資料**太寬**（造出跑不出來的狀態），
這一次**太窄**（避開了會出事的狀態）。

**怎麼修的**：修完缺陷之後補了三條回歸測試（`und` 的短中文、
整份切不出一段、真的空的才是零段），並且**把「用真的模型跑一次」
變成這一階段的收尾動作之一** —— 它花了不到一分鐘，而它是唯一
找得到那個缺陷的東西。

> **通則**：假 provider 測得到**接線**，測不到**輸入的形狀**。
> 一輪真的資料在收尾時跑一次的成本很低，而它問的是另一個問題。
> 這一條不推翻「假 provider 的 e2e 有價值」—— 那十條裡有六條
> 在把 `chatFor` 改回 `chat` 之類的突變下確實會紅。**兩種都要有。**

**影響範圍**：全域

## 外推的那個數字量的是另一件事

**日期**：2026-09-10

**症狀**：ADR-0026 訂「每份文件最多 6 段向量」，依據是
「5 萬條 2560 維 ＝ 69 ms，500 ms 的預算外推大約 35 萬條」。
Stage 13 用真的 5 萬筆量出來：18.5 萬條是 **2,176 ms**，
而在補上一個索引之前是 **48,456 ms**。

**原因**：那個 69 ms 是在**記憶體裡**量的。
488 MB ÷ 69 ms ＝ 7 GB/s —— 那是記憶體頻寬，不是任何資料庫的速度。
它回答的是「向量都已經在 `Float32Array` 裡了，算完要多久」，
而實際路徑是**從 SQLite 把 1.9 GB 的 BLOB 讀出來、每一列複製一份**。
**那一段比算術貴一個數量級，而它在那次量測裡整段不存在。**

ADR-0026 自己寫了「這個數字要在 Stage 13 用真的 5 萬筆重新量」，
而那句話當時被理解成「線性外推可能不準」。真正的問題不是線性 ——
**是那條線畫在另一張圖上。**

**怎麼修的**：`measure-scale.ts` 走的是應用層的入口
（`searchCase`、`subgraph`、`semanticCandidates`），不是自己組一段迴圈。
報告裡每一項都寫出「這個數字含哪幾段」（開資料庫、讀檔、網路往返）。

> **通則**：一個外推的數字要先問**它量的是哪一段**，再問線性對不對。
> 「快得不合理」是一個訊號 —— 7 GB/s 應該當場擋下那個結論。

**影響範圍**：全域

## 上界放在迴圈外面，而爆炸發生在迴圈裡面

**日期**：2026-09-10

**症狀**：`/subgraph/size` 走 3 跳要 1.5–4.6 秒（預算 50 ms）。
加了「超過 8,000 個節點就停」之後重量，**中位數那個焦點反而更慢**
（1,555 → 2,681 ms），另外兩個也只降了一半。

**原因**：上界寫在**跳與跳之間**。而那個焦點第 2 跳結束時只有 1,922 個節點
—— 遠低於 8,000，所以檢查放行；然後第 3 跳一口氣帶進 **32,170 個**。
**爆炸整個發生在一跳之內，而檢查點在一跳之外，它看不到。**

（更慢是因為多做了一次 `visible.size` 的比較與一次分支，
在一個本來就要跑幾秒的迴圈上那是雜訊 —— 重點是它**沒有省到任何東西**。）

**怎麼修的**：前緣分段（一段 400 個），每段之後檢查一次。
**4,566 → 317 ms。** 同一個修法也讓子圖本身的樞紐 2 跳從 1,484 降到 288 ms。

> **通則**：一個上界要放在**「量會增加的那個地方」**，不是放在
> 「一個看起來是一輪的地方」。判準是問「兩次檢查之間，那個量最多能長多少」——
> 如果答案是「整個資料集」，那個檢查點就是錯的。
>
> 而這一條之所以被抓到，是因為**修完有重量一次**。
> 不重量的話，「加了上界」看起來完全像是修好了。

**影響範圍**：全域

## 一個下界長得跟一個實際值一模一樣

**日期**：2026-09-10

**症狀**：走訪加上界之後，`/subgraph/size` 回的 `counts` 變成
「走到停下來為止看到幾個」—— 而那是**下界**。

> 加上界的時候，**「說出自己停了」跟「真的停下來」是同一個修法的兩半**，

>
> 更廣一點：**一個從來沒有被讀過的欄位，改名跟刪掉是同一件事** ——
> 而兩者都不會有任何地方報錯。

## 三個缺口，全部長在兩份文件的交界處

**日期**：2026-09-10

**症狀**：「怎麼正常開啟與關閉這個程式」這個問題查下去，找到三個缺口。
其中兩個是真的壞的，而且都不像 bug：

1. 「結束 Cyclosa」在**正在看一個執行中的作業**時按下去，程式不會結束 ——
   而畫面已經顯示「Cyclosa 已經關掉了」
2. 被強制結束的作業永遠停在「執行中」，連取消都取消不掉，
   而且讓**之後每一次搜尋**都掛一句「有作業還在跑」
3. 五條啟動路徑只有一條擋得住第二個實例

**原因**：生命週期這件事**沒有一份文件的範圍涵蓋它**。它散在四個地方 ——
ADR-0020（埠與單一實例）、ADR-0025（啟動器退場）、`README.md` 的指令表、
`Launch.ps1` 的註解。四份各自都對，而缺口全部落在它們之間：

| 缺口 | 落在哪兩份之間 |
|---|---|
| 一 | 「結束」與「SSE 進度通道」 |
| 二 | 「結束」與「Run 狀態機」 |
| 三 | 「啟動器做的檢查」與「server 自己做的檢查」 |

第一個的技術成因是 Fastify 的 `forceCloseConnections` 預設 `'idle'`：
**收得掉閒置連線，收不掉進行中的請求**。實測 1 ms vs 3000 ms 還沒 resolve。

**而測試不可能抓到它**：`app.inject` 不開真的 socket，而那條路的終點是
`process.exit` —— 一個會殺掉測試行程的函式，沒有人會為它寫測試。

**怎麼修的**：先畫圖（新增 `docs/architecture/app-lifecycle.md`），
畫的過程本身就是那次檢視。然後把關閉序列抽成一個**不碰 process 的函式**，
用**真的連線**測它，並注入一次真違規確認會紅。

> **通則一**：**沒有人畫過的那條線上，每一個交界都是一個候選缺口。**
> 一份文件的範圍是它的權威範圍，也是它的盲區邊界 ——
> 而 bug 不會落在盲區中間，它落在邊界上。
>
> **通則二**：**一個終點是 `process.exit` 的程式路徑不會有測試**，
> 因為那條測試會殺掉自己。要測它就得先把 `exit` 之前的東西抽出來 ——
> 而那件事值得為每一個「關掉／重啟／自我結束」的路徑做一次。

**影響範圍**：全域

## 掃孤兒的時候，「排隊中」不是孤兒

**日期**：2026-09-10

**症狀**：為了修上一條的缺口二，新增了一個「開專題時把沒收尾的作業掃掉」的
動作。它掃 `排隊中` 與 `執行中` 兩種 —— 而一條既有的 e2e 當場變紅：
一個剛產生完切入角度、**正在等使用者勾**的擴展作業被標成了已取消。

**原因**：擴展的 `排隊` 不是「排到它就會開始」，是**「在等你勾」**。
而那個狀態**撐得過重新啟動** —— `chooseAngles` 只看資料庫裡的
`status === 'queued'`，不問記憶體裡有沒有這個 run。

更糟的是它**不只在重啟時發作**：等你勾的作業本來就不在記憶體的執行表裡，
所以掃描在**同一個行程裡**就會把它當成孤兒。使用者按下「擴展」、
看到六條角度、還沒勾，然後那份清單就消失了。

`state-machines.md` 早就寫著這件事（「擴展的排隊是在等你勾」），
而我在寫掃描的時候把「沒有人在跑它」讀成了「沒有人要它」。

**怎麼修的**：只掃 `執行中`。並補一條專門釘這件事的測試。

> **通則**：**「沒有行程在後面」不等於「沒有人在等它」。**
> 一個狀態是不是孤兒，要問的是「有沒有東西會再讓它前進」——
> 而使用者是那個東西之一。清理動作的判準寫成「誰會讓它前進」，
> 不要寫成「現在有沒有在動」。

**影響範圍**：全域

## 一支零呼叫點的 API 底下藏著兩個缺陷，而它們互相遮住了

**日期**：2026-09-11

**症狀**：Stage 15 把「封存／重新開啟」接上按鈕 —— 那支 API 從 Stage 5 就在，
`web/src/api.ts` 裡也有 client。**接上去之後兩條 e2e 立刻紅**：

```
封存之後清單上的狀態就是已封存
  AssertionError: expected undefined to be true
```

**原因**：兩個獨立的缺陷，而它們疊在一起看起來像一個。

1. **轉移表上沒有 `新建 → 已封存`**。只有 `已就緒 → 已封存`，
   所以一個剛建好、還沒匯入任何東西的專題**封存不了** ——
   使用者只剩下刪除這一條路。
2. **專題狀態會卡在 `蒐集中`**。它在作業開始時被寫成 `蒐集中`、
   結束時寫回 `已就緒`，而**兩邊都在行程裡**。行程沒機會跑完第二步就死掉，
   那一列就永遠留著 —— 而 `蒐集中` 也封存不了。

第二個特別值得記，因為它是 **v0.14.0 那次修復漏掉的另一半**：
那一次修的是 `run.status`，而專題狀態是另一個欄位、另一條路。
更糟的是**正常關閉會把作業寫成 `已取消`**，於是孤兒掃描找不到東西可掃、
在 `orphans.length === 0` 直接早退 —— **那條剛修好的路反而繞過了這個修復。**

還有第三件：轉移不合法時一律回 `CASE_ARCHIVED`，
所以「作業還在跑的時候按封存」得到的訊息是**「這個專題已封存」**，
而它明明沒有。一個會說謊的錯誤碼躲了十個 Stage，
因為**沒有任何一個按鈕會讓使用者走到那條路上**。

**怎麼修的**：補 `新建 → 已封存`；把「放回 `已就緒`」從
`orphans.length === 0` 的早退**外面**跑；`CASE_ARCHIVED` 拆成兩個碼。
四條測試釘住掃除的四種情形，其中一條專門走「作業已經是已取消」那條路。

> **通則**：**沒有人呼叫過的程式碼裡沒有事實。**
> 一支端點、一張轉移表、一個錯誤碼，只要沒有任何介面走得到它，
> 它寫的就只是一個意圖 —— 而意圖不會在測試裡變紅。
>
> 這跟 Stage 7「圖例承諾了一個沒有路徑可以觸發的畫法」是同一件事，
> 那是第一次，這是第二次。**判準是「有沒有一條使用者走得到的路」**，
> 不是「這段程式碼有沒有被寫出來」。
>
> 推論：**接一顆新按鈕到一支既有 API 上，要當成「第一次實作」來驗**，
> 不是「接個線」。這一次三個缺陷全部是在接線的那十分鐘裡冒出來的。

**影響範圍**：全域

## 要爬的那個站，禁止爬蟲 —— 而我們自己就有一個會照做的爬蟲

**日期**：2026-09-11

**症狀**：Stage 15 的範例專案要一份語料。授權查完了（著作權法 §9
＋ 政府資料開放授權條款，兩個依據都成立），正要去抓 `law.moj.gov.tw` 的條文頁時
順手看了一眼 `robots.txt`：

```
User-agent: *
Disallow: /
```

**整個站不准爬。**

**原因**：**查授權與查可不可以抓，是兩件事，而我差點只做了第一件。**
著作權法說那些字沒有著作權 —— 那是關於**內容**的。
robots.txt 說不要爬 —— 那是關於**取得方式**的。
兩者都成立的時候仍然不能爬。

而這個專案的處境讓它更尖銳：Cyclosa 自己有一個會讀 robots.txt 並且照做的爬蟲，
`FETCH_ROBOTS_BLOCKED` 這個錯誤碼就是為它存在的。
**用爬來的語料去當它的範例專案，方向剛好是反的。**

**怎麼修的**：改走 data.gov.tw 上公告的官方大量下載端點
（`sendlaw.moj.gov.tw`，該站沒有宣告 robots 限制，6 MB 的 zip 裡有全部法律）。
那不是爬取 —— 那是資料提供者自己指定的散布管道。

> **通則**：**先問「這個站有沒有給一條正式的路」，沒有再問能不能爬。**
>
> 順序反過來就會先看到一份抓得動的 HTML，然後才想起要去看 robots ——
> 而那時候已經寫了一支解析器，沉沒成本會開始幫你找理由。
>
> 這條的形狀跟「先登記查詢集再跑模型」一樣：**把會讓你動搖的資訊排在後面，
> 不是靠意志力，是靠順序。**

## 語料的組裝腳本抓到我把出處掛在錯的節點上

## 一個元素同時負責捲動與行長，於是捲軸跑到畫面中間

**日期**：2026-09-11

**症狀**：使用者回報「網頁有些地方沒有自適應長寬」，附了五張寬螢幕截圖。
設定頁的捲軸浮在畫面約 2/3 的位置，右邊一大片空白。

**原因**：三件事寫在同一個規則上。

```css
.settings {
  overflow-y: auto;     /* 我是捲動容器 */
  max-width: 760px;     /* 我也是行長限制 */
  margin-inline: auto;  /* 我還負責置中 */
}
```

**而 `margin-inline: auto` 會把 flex 子項的 `stretch` 取消掉** ——
它不再是「填滿再置中」，而是「由內容決定寬度」。
量出來：模型分頁 760px、來源網站分頁 785px，**同一頁的寬度跟著內容跳**。

第二個後果是捲軸跟著內容跑，所以它出現在畫面中間而不是視窗邊緣。

同一輪還量到兩件：

- **頂列沒有任何縮排控制。** flex 子項預設 `min-width: auto`，
  所以一個長專題名會把「設定」與「結束 Cyclosa」推出畫面 ——
  而那兩顆是那一列上最不能不見的（一個是出口，一個是關機）
- **各任務模型那張表四欄的最小寬度加起來 728px**，而那一頁的內容寬只有 712px。
  它在**任何**視窗寬度下都塞不進去，症狀是整個設定頁固定橫向溢出 31px

**怎麼修的**：捲動與行長拆成兩層（外層填滿並捲動、內層 `max-width` ＋ 置中）；
頂列每一格 `flex: none`，只有專題名可縮並加刪節號；寬表格包一個橫捲容器，
順帶把那一欄的 `max-width` 從 34ch 收到 26ch，讓它在常見寬度下根本不用捲。

**怎麼驗的**：用無頭瀏覽器的 CDP 逐一套 `setDeviceMetricsOverride`，
量 **5 個頁面 × 8 種長寬**（含直立的 900×1440、768×1024），
判準是「整頁不橫捲」「沒有元素右緣超出視窗」「結束鍵的右緣在畫面內」。
修之前設定頁在每一個寬度都溢出 31px，修之後 40 種組合全過。

> **通則一**：**截圖不是量測。** 截圖會被視窗邊緣裁掉，
> 而「被裁掉」跟「真的溢出」在圖上長得一模一樣 ——
> 我一開始差點照著截圖去改左欄的內距，而那裡根本沒有問題。
> 版面的判準要寫成數字（`scrollWidth`、`getBoundingClientRect().right`），
> 才分得出這兩件事。
>
> **通則二**：**一個元素負責兩件事的時候，先問那兩件事會不會要求不同的寬度。**
> 捲動要的是「填滿視窗」，行長要的是「不超過 760px」——
> 它們從一開始就不是同一個寬度，寫在一起只是還沒撞到。
>
> **通則三**：**用最長的那個值去量。** 頂列的失敗只在長專題名下出現，
> 用預設的短名字量一百次也量不到。

**影響範圍**：全域

## 「複製再刪」的兩個失敗點共用一個 catch，而它清掉的是完整的那一份

**日期**：2026-09-13

**症狀**：沒有人遇到過。`D:\Projects` 全域檢視逐處審四個專案的遞迴刪除時讀出來的：
`moveDataRoot` 跨磁碟區時 `cp` 完再 `rm` 舊的，兩步包在同一個 `try`，`catch` 一律 `rm` 新位置。

**原因**：`catch` 的清理只對第一個失敗點（複製到一半）是對的。第二個失敗點（刪舊的途中，

寫 `catch` 的時候想的是「失敗了就回到開始之前」，但刪除是回不去的那一步。

**怎麼修的**：兩步分開接。複製失敗清新位置；複製完成之後刪舊失敗只記 warn、照常改指標檔，

在舊程式上確認是紅的才修。

> **通則**：一個 `try` 裡有兩個以上會改檔案系統的步驟時，`catch` 的清理要問「失敗在第幾步」。
> 過了刪除那一步，就沒有「回到開始之前」可以回，只能**保住現在最完整的那一份**。

**影響範圍**：全域（任何「複製再刪」的搬移都一樣。tagcor-ledger 的「搬移資料路徑」有同一個形狀，同日一起修；

> 包括兩天後的自己。

**影響範圍**：全域（任何「探一下活不活著」的健檢都是這個形狀：回 200 的驗證頁、登入頁、停車頁都會讓它通過）

## 工具守著 robots，而我在終端機裡直接打了那個網址

**日期**：2026-09-18

**症狀**：為了替 Q7（反爬蟲驗證頁怎麼認）收一份真實樣本，我用 `curl` 打了
`dblp.org/search/publ/api?...`，拿到 200 ＋ Anubis 的驗證頁，並照著它寫了判斷規則。
規則寫完、要把探針放回內建清單時，改用 `Crawler` 實跑同一個網址 —— 回的是
`FETCH_ROBOTS_DISALLOWED`。`dblp.org/robots.txt` 是 `User-agent: *` ＋ `Disallow: /`，
**整站不准**，所以那個請求本來就不該送出去。

**原因**：**「診斷」不是一個豁免。** 這個專案有一條規則叫「擷取管線是唯一出口」，
它防的正是這件事 —— 節流、robots、雜湊、manifest 只存在於那一層。而規則寫的是程式，
沒有寫我：我在終端機裡打的那一次，等於自己開了第二條路。
v0.20.0 那次「三條探針實際打過」也是同一個形狀（那一次還連內容都沒看）。

**後果**：兩次對一個明確禁止抓取的網站送了請求（各一次）。
文件上更糟的是**結論的形狀**：dblp 被寫成「驗證頁擋住了它」，而真正的事實是
「它的 robots.txt 從一開始就說不要來」—— 前者聽起來像技術障礙，後者是對方的明示意願。

**怎麼修的**：探針放回 `catalog.ts`，而註解寫的是實跑的結果（robots 不准，請求沒送出去）；
`fetch-policy.md` 與 Q7 的結論都補一句「robots 比驗證頁那一層更早」。

> **通則**：**要看一個外部網站回什麼，就走這個工具自己的擷取路，不要用 `curl`。**
> 走自己的路有三個好處，而它們都不是形式：規則會被執行、行為與使用者遇到的一致、
> 而且**結果可以直接當成驗證紀錄**。真的要用 `curl`（例如程式還沒寫好），
> **先抓 `robots.txt` 看一眼** —— 那一份是公開的、抓它本身一律允許。

**影響範圍**：全域（任何「我先手動查一下這個網站」的動作）

## 宣稱支援一種協定，而從來沒有對著那種端點跑過

**日期**：2026-09-18

**症狀**：使用者給了一把第三方代理（OpenAI 相容）的金鑰。設定頁「實際打一次」
回的是 `PROVIDER_JSON_UNSUPPORTED`，而**同一次的格式量測寫著「這個端點支援 json_schema」**。
兩句話互相矛盾。直接對端點打一次就看到原因：

```
HTTP 400 invalid_json_schema
'additionalProperties' is required to be supplied and to be false.
```

**原因**：OpenAI 的嚴格模式對每一個物件節點要求 `additionalProperties: false`。
**格式量測用的探針 schema 寫了**，而**三份真的 schema（角度、抽取、找來源）一份都沒寫**。
所以量測永遠是綠的，真的呼叫永遠 400。

**這個洞從 v0.18.0 活到現在（一個月），而原因寫在當時的文件第一段**：
「這台機器上沒有任何線上服務的金鑰，所以一個線上端點都沒有量。」
量得到的唯一那個（本機 Ollama 的 `/v1`）對這兩條寬鬆 —— **它一直是綠的，
而它證明的只有「本機那條路會動」**。

**後果不只是壞掉，是它說錯了誰的錯**：程式對「`schema` 模式下被 400」的解釋是
「量測舊了，端點大概改了規格，去重新檢查」。使用者會照著那句話去按重新檢查，
而那一按又會是綠的（探針過），於是問題看起來在對方那邊。

**怎麼修的**（v0.22.1）：`strictify()` 在送出去之前補那兩條，
**不動那三份 schema** —— 端點的要求在邊界上處理，寫進 schema 會連帶收緊本機那條路。
測試釘住「三份真的 schema 原樣不合格、strictify 之後合格」。

> **通則一**：**一個「支援某某協定」的宣稱，只有對著那個協定的真實端點跑過才成立。**
> 自家的相容實作（這裡是 Ollama 的 `/v1`）證明的是「我們的程式會動」，
> 不是「別人的端點會收」—— 而兩者的差別正好落在別人比較嚴格的那幾條上。
>
> **通則二**：**探針與真正要送的東西不一樣的時候，探針會說謊。**
> 這裡的探針 schema 是手寫的、而且剛好寫對；真的 schema 是另外三份。
> 探針要嘛用真的那幾份，要嘛就要有一條測試逼它們在同一個形狀上一致。

**影響範圍**：全域（任何「我們支援 X 協定」的宣稱，以及任何用簡化樣本做的健檢）

## 「不支援」是對著我們在用的那條路量的，不是對著功能真正的入口

**發生了什麼**（2026-09-19）：使用者問「OpenAI 相容端點不能上網嗎」。這個專案對那一種端點只送過 Chat Completions，

## 「讓它自己死掉了留得下線索」—— 而它真的死掉的那一次，一個字都沒留下

**發生了什麼**（2026-09-19）：使用者按「儲存並測試」之後伺服器不見了，`server.log` 的最後一行是啟動。
日誌檔的程式碼註解寫得很清楚：一鍵啟動的伺服器沒有主控台，所以日誌同時寫一份到檔案，**「讓它自己死掉了留得下線索」**。
而那個設計只接住**經過 logger 的**那幾行 —— 一個程式自己死掉的兩條主要的路（沒接住的錯誤、原生層的中止）都不經過 logger，
Node 把它們印到 stderr，而 stderr 在隱藏的主控台裡沒有人看。那句話寫下之後，從來沒有人讓程式真的死一次看看檔案裡有什麼。

> **通則**：一個「出事時留得下線索」的設計，要用**它宣稱要接住的那種出事**驗一次 —— 讓程式真的當掉，然後去看那個檔案。
> 驗的是正常路徑的話，它只證明了正常路徑會寫日誌。

**影響範圍**：所有「出事時會怎樣」的宣稱（日誌、復原、孤兒掃描、結束序列）
## 驗收用的是另一條服務，所以那條預設的路從來沒被走過

**發生了什麼**（2026-09-23）：Stage 19 的「規劃對話」預設走 Claude Code，而它**從來沒有成功跑過一次** ——
子程序的工作目錄（沙箱）沒有先建出來，`spawn` 直接失敗，而 Claude Code 那一支把 spawn 的錯誤報成
`PROVIDER_NOT_CONFIGURED`（「沒設定」）。Stage 19 的端對端測試與實跑驗收都用本機 Ollama（它不看工作目錄），
所以一個「預設路線完全不能用」的洞，在一份全綠的測試與一次逐張看過的截圖驗收底下活了三天。

> **通則**：一個功能有好幾條服務可以走的時候，**驗收要走預設的那一條**（或至少為它做一個假的）。
> 挑「跑得起來的那一條」驗收，等於驗了一條使用者不會用的路。

**影響範圍**：所有「這個任務可以走 A／B／C」的功能（規劃對話、找來源、抽取、初讀）

## 子程序起不來，把整個伺服器帶走了 —— 而測試抓不到，因為測試的路徑比較短

**發生了什麼**（2026-09-23）：Stage 20 的蒐集在實跑時讓伺服器整個消失。v0.24.3 裝的當機紀錄這次留下了原因：
`read ENOTCONN`，來自 `spawn` 裡建立 stdio 管線的那一段。實測之後確定：**Windows 上子程序的工作目錄超過 258 字元時，
`spawn` 回一個 `ENOENT`（看起來像「找不到指令」），同時 stdout 與 stderr 兩條管線的 socket 各丟一個 `read ENOTCONN`** ——
而那兩個 `error` 事件沒有人掛監聽，於是變成沒接住的例外，行程結束。

**端對端測試一路全綠**：測試的沙箱在 `tmp/vitest/…` 底下，路徑短；實跑的 scratch 資料根深了 140 個字元，就超過了。
工作目錄不存在、指令不存在**都不會**觸發那兩個管線錯誤 —— 只有太長的會，所以「子程序起不來」的既有測試也照不到它。

> **通則**：**子程序起不來是那一次呼叫的失敗，不該是伺服器的死因** —— 每一個 spawn 的 stdio 都要接住錯誤
> （這裡收成一支 `spawnPiped`）。而路徑長度這一類「環境相關的邊界」，測試環境的值往往比使用者的小很多：
> 短路徑的綠燈不代表長路徑也綠。有上限的東西要嘛先擋（回一個說得出原因的錯誤碼），要嘛在測試裡真的做一次那個邊界。

**影響範圍**：所有 spawn 子程序的路徑（agent 的沙箱、未來任何外部工具）、所有「資料根可以搬到任意位置」的假設

## 「重現靠某某」—— 而某某只寫進了一個沒有留下來的檔

**發生了什麼**（2026-09-29）：換嵌入模型要重量一輪，想把 09-09 那一版 Wikipedia 語料釘回去。
`embedding-choice.md` 寫著「語料不進 repo，**重現靠頁面清單 ＋ `wgCurRevisionId` ＋ SHA-256**」，
查詢集的第一行也寫「版本編號在 `sources/manifest.jsonl`」。**manifest 裡沒有版本編號** ——
抓語料那支工具只把它寫進了 `pages.json`，而 `pages.json` 跟語料一起留在暫存目錄，沒有留下來。
HTML 每次抓都不同，雜湊也比不了。**那兩句話在寫下的那一天就不成立**，而二十天裡沒有人需要重現，所以沒有人發現。

這一次的語料剛好沒有位移（50 條查詢的標準答案段落逐條讀過，全部仍然成立；對照組 `qwen3-embedding:4b` 的 MRR@10 也是 0.970，
跟 09-09 一樣）。那是運氣，不是設計。

> **通則**：**一句「靠 X 可以重現」要在寫下的那一刻就對著 X 查一次** —— X 在不在版控裡、裡面到底有沒有那一欄。
> 重現的依據跟備份一樣，**沒有演練過的就等於沒有**；而它的失敗方式是安靜的：需要它的那一天才知道它不存在。
> 修法是讓那一欄進唯一會留下來的那一份（這次是 manifest），而不是再寫一句更肯定的話。

**影響範圍**：所有「資料不進 repo、靠紀錄重現」的量測（語料、快照、外部 API 的回應）

## 一個錯誤碼寫進了規則、文件與翻譯 —— 而它從來沒有被報過

**發生了什麼**（2026-09-29）：`PROVIDER_EMBED_MODEL_MISMATCH` 從 v0.11.0 起在四個地方：錯誤碼表、`error-codes.md`、
`zh-TW.ts` 的訊息、agent 檔「不要做什麼」那一條（「不符就報 `PROVIDER_EMBED_MODEL_MISMATCH` 並停手」）。
換嵌入模型時去查它在哪裡被報 —— **零個呼叫點**。實際的行為是：比對只拿同一個模型的向量（這一半做對了），
而換了模型、還沒重算的專題，語意模式**安靜地一筆都查不到**，畫面上什麼都沒說。
錯誤碼三邊對照的守門一直是綠的 —— 它守的是「三份清單一致」，不是「每一個碼都有人報」。

> **通則**：**一個寫進規則的錯誤碼，要有一條測試走到它被報出來的那一刻**。三邊一致只證明「大家都同意有這個碼」，
> 不證明有任何一條路會用到它 —— 跟 `preferredHosts()`、`sampleExists()` 零呼叫點是同一族：
> 文件描述了一個行為，而程式裡沒有那個行為。

**影響範圍**：`codes.ts` 裡每一個碼（值得掃一次：哪幾個零呼叫點）、agent 檔裡「報某某碼」的每一句

## 修過一次的字面 `<<B>>`，其實只修了一處

**發生了什麼**（2026-09-29）：README 裡一條路徑寫成 `%LOCALAPPDATA%` 後面接著三個字面的 `<<B>>` ——
那是某次透過 shell 寫檔時反斜線被換掉留下的。**v0.19.0 的 changelog 寫著「修掉 README 的字面 `<<B>>`」**，
而 `git log -S` 顯示那次只改了出現的次數，這一處一直留著，直到這次整理公開前的 README 才看到。

> **通則**：**修一個「字面殘留」要用搜尋確認歸零，不是修掉看到的那一個**（整個 repo 搜一次，結果要是 0）。
> changelog 裡「修掉了 X」是一句會被下一個人相信的話 —— 寫之前那個 X 應該已經搜不到。

**影響範圍**：所有經過 shell 寫進檔案的反斜線路徑（早先那一條：Bash 工具會把兩個反斜線收成一個）

## Ollama 升版之後，大量嵌入在 Windows 上會撥不通它自己

**發生了什麼**（2026-09-29）：重量嵌入模型，六個候選裡四個「失敗」，錯誤是 Ollama 回 HTTP 400、內文
`dial tcp 127.0.0.1:<埠>: bind: …lacked sufficient buffer space or because a queue was full` ——
**Ollama 連不上它自己的執行程序**。實測 Ollama 0.34.4 每嵌入一段文字，就在本機迴路留下約 3 個 TIME_WAIT
（一次 16 段 → 多 50 個）；1957 段連跑幾個模型，全機一度有一萬九千個 TIME_WAIT。
**但它也會在只有兩千個的時候失敗**（`qwen3-embedding:4b` 跑到第 320～640 段之間），所以不只是埠用完 ——
比較像同一瞬間撥太多條。09-09 那一輪（Ollama 0.33.2）同樣的量測沒有這個現象。

**結果表上那個模型是「失敗」，而原因跟模型無關** —— 差一點就把一個候選當成「Ollama 跑不動」刷掉。
出貨的程式同樣會碰到：「建立語意索引」一次送幾百段，原本把這個 400 當成「連不上 Ollama」，而它明明開著。

> **通則**：**失敗的時候先分清楚是誰的失敗** —— 被量的東西、量測工具、還是中間那一層。
> 一個來自執行環境的暫時性錯誤，在結果表上長得跟「這個模型不行」一模一樣。
> 修法是只對那一種訊息退避重試、**把重試次數寫進結果**，不是對所有錯誤重試（那會把真的壞掉的也延後說）。

**影響範圍**：量測工具、`embed-ollama.ts`（已加有限次重試）、任何對本機 Ollama 連續送大量請求的路徑；
升 Ollama 之前先跑一次大批量的嵌入

## 「只綁 127.0.0.1」擋的是別台機器，不是這台機器上的網頁；「只有 .cmd 才走 shell」只擋了一半

**發生了什麼**（2026-10-02）：為模型服務改版做安全檢查（使用者要求「不要有 LLM 帳號被偷用的可能」），
回頭看現有的程式，查到兩個從第一天就在、測試全綠的洞：

1. **伺服器沒有任何來源檢查。** ADR-0002 只綁 `127.0.0.1`，大家（包括這份文件）都把那讀成「外人連不到」。
   但瀏覽器裡的每一個網頁都在本機：跨站的 `text/plain` POST 不需要預檢，Fastify 預設的解析器照收，
   `POST /api/providers` 把設定蓋成預設值；DNS rebinding 之後更是什麼都送得到 —— CLI 指令設成任意程式、
   下一次探針就執行它。修法在 ADR-0036。
2. **`needsShell` 只對 `.cmd`／`.bat` 開 shell**（2026-09-08 那一條的修法）。那一條修的是「路徑有空白會起不來」，
   而它留下的是另一件事：使用者只要把指令設成 npm 裝的 `claude.cmd`，提示詞（含專題文件的段落，可能來自
   抓回來的網頁）就會被原樣接成一個字串交給 `cmd.exe` —— 文件裡的 `&` 就是一個指令。修法是一律不經過 shell。

兩個洞的測試都是綠的，因為**測試問的是「功能對不對」，沒有一條問「誰能叫它做這件事」**。
後者的答案在每一個端點、每一次 spawn 都一樣，所以它沒有被任何一個功能的測試涵蓋到。

> **通則**：**「只有本機」是一個網路層的答案；「只有這個程式的頁面」是另一個問題**，要另外回答。
> 一個修法若是「只在某種情況下打開危險的那條路」，要問的是那種情況**誰能觸發** ——
> 設定檔裡的一個字串、一份抓回來的文件，都不是「使用者自己才會做的事」。

**影響範圍**：`server.ts`（`request-guard.ts`、`IO_REQUEST_FOREIGN`）、`spawn-piped.ts`、`agent-claude.ts`；
新守門 `no-shell-spawn`、e2e `request-origin`
