# ADR-0014：`domain/graph` 零依賴，但現在不抽成套件

**狀態**：已採用（設計決定；實作尚未開始）
**日期**：2026-09-06

## 背景

`rubricator`（隔壁的藏書管理專案）是 `domain/graph` **已知的未來消費者** ——
兩邊都需要「帶型別的節點與邊、可信度、人工裁決的狀態機」這組東西。

問題是「已知的未來消費者」很容易被當成「現在就抽套件」的理由，而那是錯的：
**「兩個專案都用到」不夠 —— 複製一份也能用到。**

這一條原本掛在 `research/open-questions.md` 的 Q5，
它問的不是「要不要抽」而是**「觸發條件是什麼」**。這份 ADR 是那個答案，
Q5 隨之從那份文件移除（那份文件的規則是「有答案就搬走並刪掉」）。

## 決定

1. **`domain/graph` 零依賴**：不 import 其他層、**也不 import 任何 npm 套件**。
   （其餘的 `domain/` 只要求零 I/O，這一塊額外要求零依賴。）
2. **現在不抽成套件。** `rubricator` 真的要用的時候，**第一步是複製一份**，
   而且要在複製的那個 commit 裡寫明它是複本。
3. **抽套件的觸發條件**：

   > **兩邊的複本已經分岔，而那個分岔造成了一個 bug。**

   不是「兩個專案都用到」、不是「程式碼超過 N 行」、也不是「感覺會重複」。
   到那天才抽，**並且把那個 bug 寫進 ADR 當證據**。

## 考慮過但沒選的

| 方案 | 為什麼不選 |
|---|---|
| **現在就發成 npm 套件** | 消費者還不存在。要先付版本管理、發佈流程、跨 repo 的 breaking change 協調 —— 全部是為一個假設的使用者付的 |
| **monorepo** | 兩個 repo 各自公開、各自的 CI 與授權檢查。合併的成本遠高於「共用一塊純函式」的收益 |
| **抽成 git submodule** | submodule 的更新流程比複製一份還容易出錯，而且 clone 的人會踩到 |
| **一開始就允許 `domain/graph` 用套件** | 那它就抽不出來了 —— 零依賴是「以後可以抽」的**前置條件**，成本現在很低 |

## 代價

- **`rubricator` 要用的時候得先複製一份，而複本會分岔。**
  這是明知並接受的：分岔的成本會在未來某天一次付清，而抽套件的成本是現在就要付。
- **分岔到造成 bug 之前沒有人會察覺。** 觸發條件本身是滯後的 ——
  緩解的辦法只有在複製時留下記號（複製的 commit 訊息、檔頭註解）。
- **零依賴是一條要一直守的紀律。** 有一天有人想在裡面用一個 `nanoid`，
  那時候要記得這一條，而它只寫在這裡與 `AGENTS.md`／`CLAUDE.md` 的分層那一節。

## 什麼情況要重新考慮

- **上面那個觸發條件成立時**：兩邊的複本已經分岔，且分岔造成了一個真實的 bug。
- **`domain/graph` 開始需要 I/O 或需要一個套件** —— 那代表邊界畫錯了，
  該問的是「這段程式碼是不是根本不屬於 `domain/graph`」。
