# ADR-0007：3D 只做瀏覽與結構感，精確操作在 2D 側欄，必須能一鍵切 2D

**狀態**：已採用。**2026-09-07（Stage 7）實作**，五條全部落地
（3D 只瀏覽、側欄做精確操作、一鍵切 2D、深度線索、`GraphView` 抽象 ＋ Worker 佈局）。
**日期**：2026-09-06

> **2026-09-07 補一條實作細節**：一鍵切 2D **沒有呼叫 `3d-force-graph` 的
> `numDimensions(2)`**。那支看起來才是正規做法，實際按下去整張圖會空白 ——
> 它會重跑一次佈局初始化，而我們已經把它自己的力全部拿掉了。
> 而且它是多餘的：位置本來就由 Worker 決定，套件那一側只負責畫。
> **切 2D ＝ 告訴 Worker 少算一個維度 ＋ 把鏡頭移到正對那個平面。**
> 資料一個位元組都沒動，符合這份決定的第 3 條。

## 背景

**3D 在 HCI 研究裡不是免費的升級。** 遮擋與深度感知讓「精確比較」與
「社群偵測」這類任務比 2D **更慢**；3D 真正的優勢在**空間記憶與整體結構感**。

而 3D 圖同時是這個工具最容易被誤用的部分 —— 它很好看，所以日後每一個新功能
都會有人想放進去。

## 決定

1. **3D 只做瀏覽與結構感。**
2. **精確操作（比對、篩選、確認邊、看引文）在側欄的 2D 面板。**
3. **必須提供一鍵切換 2D 平面佈局**，而且切換不改變資料，只改變佈局。
4. **旋轉時要給深度線索**：霧化、近大遠小、選中節點的連線高亮。
5. **`3d-force-graph` 包在自訂的 `GraphView` 介面後面**，佈局計算跑 Web Worker
   （力導向會吃滿主執行緒）。

## 考慮過但沒選的

| 方案 | 為什麼不選 |
|---|---|
| **只做 2D** | 丟掉整體結構感與空間記憶，而那是使用者面對「累積了半年的專題」時真正需要的東西 |
| **只做 3D，分析也放進去** | 研究說那些任務在 3D 裡更慢。做出來會是一個很好看而不好用的東西 —— 正是 Obsidian 圖被批評的下場 |
| **直接用 `3d-force-graph` 的 API，不包一層** | 換渲染時要改的地方散在整個前端。包一層的成本是一次性的 |
| **VR／XR** | 裝置門檻遠大於收益，而且它解的是「沉浸」不是「找得到東西」 |

## 代價

- **兩套佈局要維護、兩套互動要測。** 2D 與 3D 的選取、hover、標籤佈局規則不同。
- **側欄讓畫面更擠**，尤其在筆電螢幕上。
- **`3d-force-graph` 自己的 2D 模式與我們要的 2D 平面佈局不一定一致** ——
  可能得自己做一套，那時 `GraphView` 這層抽象會被真正考驗。
- 「3D 只做瀏覽」是一條**需要被反覆執行的紀律**，不是一次性的設計。
  每個新功能都要問一次「這個該放 3D 還是側欄」。

## 什麼情況要重新考慮

- **8k 節點時互動 fps 掉到 30 以下** → 換掉 `3d-force-graph` 改自寫渲染
  （WebGL 實例化）。**這是那層抽象存在的理由**，也是這條觸發條件要寫成數字的理由。
- **使用者實際上永遠停在 2D**（可量測：切換狀態的使用比例）→ 那要重新問的是
  「3D 值不值得維護」，而不是「怎麼讓 3D 更好用」。
- `research/open-questions.md` Q4（外語節點在圖上顯示什麼）要等 3D 真的跑起來
  才能回答 —— 標籤空間的限制只有看到實際的圖才知道。
