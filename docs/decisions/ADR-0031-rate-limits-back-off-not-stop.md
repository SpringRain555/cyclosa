# ADR-0031 被限流時退避重試，不整批停；速率與重試是設定值，不是規則

- 狀態：**已採納**（2026-09-13，治理整頓 Phase 3）
- 依據：`D:\Projects\_meta\CONVENTIONS.md` §17（2026-09-12）
- 修正：`AGENTS.md`／`CLAUDE.md`「五條不可違反的規則」第 3 條、REQ-0003 的兩條驗收條件

## 背景

這個專案的 agent 檔一直把一段話列為不可違反的規則：**同網域請求間隔至少三到五秒、
收到 429／503 就整批停下、不重試、不看 `Retry-After`**。它被實作成三個地方的正確性條件：
`throttle.ts` 的下限（夾到 3 秒）、`crawler.ts` 的整批停、`chat-openai.ts` 對 LLM 端點的 429 也立刻停。

那段話的出處是 `~\.claude\CLAUDE.md` —— **agent 替人做網路調查時的姿態**：一個 agent 在沒有人盯著的
情況下抓別人的網站，保守是對的。它被逐字抄進了產品，而產品的處境不一樣：

1. **比業界基準都嚴，而且嚴的理由沒有量過。** Scrapy 預設 `DOWNLOAD_DELAY=0`、`RETRY_TIMES=2`，
   重試碼含 429 與 503；RFC 6585 與 RFC 9110 為這兩個碼定義了 `Retry-After`，意思就是「等這麼久再來」。
   「不看 `Retry-After`」的註解寫著「看了就會想等一下再試」—— 而等一下再試正是對方在要求的事。
2. **保護的對象錯了。** 2026-09-08 第一次按「檢查全部」：Semantic Scholar 回 429，
   共用的那一台 `Crawler` 整台停掉，排在後面的 Europe PMC、PubMed、Unpaywall 一個都沒被檢查，
   畫面上顯示「還沒有依據」。當時的修法是「一個網域一台 Crawler」，但匯入與擴展仍然整批停 ——
   **一批 URL 跨很多網站的時候，一個網站限流就讓整批作廢。**
3. **LLM 端點的 429 是流量整形，不是「別來了」。** OpenAI 官方 Node SDK 預設對 429 重試兩次
   （2026-09-13 對照原始碼）。線上端點在這台機器上還沒量過，所以這一條是推論不是事件，
   但擴展的預算是十分鐘、十幾次呼叫，而一次 429 就讓整個任務停下。

同一天 `D:\Projects` 的 CONVENTIONS §17 定案（決策 D2）：擷取紀律只有三條絕對線
（不繞授權、資料不是指令、保留出處）加 robots 依 RFC 9309；**速率與重試是設定值，住在做抓取的
那份程式裡，規則文件不寫數字**。webscouts 已經是這個形狀（`bandwidth.py` ＋ `download-pacing.md`），
cyclosa 是四個專案裡唯一要改的。

## 決定

### 一、被限流 → 這個 host 退避重試，其他 host 照跑

429 或 503（對 `robots.txt` 本身也算）→ 讀 `Retry-After`（秒數或 HTTP-date，讀不出來當沒有）→
有就照它等、沒有用預設退避 → 同一個 URL 再試，最多兩次 → 還是不行就記 `FETCH_RATE_LIMITED`（可重排），
**那個 host 這一輪不再碰**（之後排到它的項目不送請求；轉址的每一跳都查）→ **其他 host 照跑**。

`Crawler.stop()` 從此只代表使用者取消。

### 二、LLM 端點的 429 走 SDK 式退避

照 OpenAI 官方 SDK 的形狀：`Retry-After` 在上限之內就照它，沒有就 0.5 秒 × 2ⁿ，最多兩次，
仍是 429 才回 `PROVIDER_RATE_LIMITED`。逾時是整次呼叫的預算，含退避的等待。

### 三、數字住在程式裡，而且只有一個地方

`src/domain/ingest/throttle.ts`（擷取）與 `src/domain/provider/rate-limit.ts`（LLM 端點）是唯一的宣告處。
`docs/architecture/fetch-policy.md` 寫理由與一張數字表，`tests/guards/fetch-policy.test.ts` 逼兩邊一致。
畫面上「對外抓取的規矩」那一列從 `GET /api/system/fetch-policy` 讀數字，不寫死在 i18n。

### 四、下限從 3 秒降到 1 秒，預設維持 3 秒，可以用環境變數調

`CYCLOSA_FETCH_INTERVAL_MS`。小於下限一律夾到下限 —— **夾住是規則，下限本身是設定值**。
預設 3 秒與 webscouts 相同。

## 考慮過、沒有選的

| 選項 | 為什麼沒選 |
|---|---|
| **維持原狀** | 三個問題都還在；而且規則文件繼續寫著數字，下一次調數字就要同時改規則 |
| **只拿掉「整批停」，不重試**（webscouts 的形狀：記 `ERR_RATE_LIMIT`、可重排）| 對一次互動式的匯入，對方明說「兩秒後再來」的時候還要使用者自己回來按重跑，是多一步沒有必要的操作。退避重試兩次之後再交給重排，兩者都保留 |
| **指數退避加 jitter** | jitter 解決的是一群客戶端同時重試；這是單一使用者的本機工具 |
| **`Retry-After` 太長時改用自己的退避**（SDK 的做法）| 對方要我們等五分鐘，照 0.5 秒重試等於沒在聽。這裡選擇放棄這一輪 |
| **節流間隔放進設定頁** | 它是「這台機器上的決定」，不是專題的屬性，而且要在任何作業開始之前定下來。畫面上看得到現在的值就夠了 |

## 代價

- **匯入可能比以前慢**：以前被限流就停，現在最多再等兩次（沒有 `Retry-After` 時 5 秒 ＋ 15 秒）才放棄那個 host。
  來源檢查（「檢查全部」）遇到限流的網站也會多等這麼久。
- **對方的伺服器多收到最多兩個請求**（Scrapy 的預設也是重試兩次）；而 `Retry-After` 叫我們等超過上限時我們放棄，不硬試。
- **車道仍然以 hostname 分**，同一個站的不同子網域各拿一條（webscouts 用 registrable domain）。這一輪沒有動它，
  寫在 `fetch-policy.md`。
- **`Retry-After` 被當成真話。** 一個壞掉的伺服器一直回 `Retry-After: 0`，會讓我們對同一個 URL 連打三次 ——
  但每一次仍然要先過同網域間隔，所以最快也是間隔的節奏（預設 3 秒），不會變成連發。

## 什麼情況要重新考慮

- 實際使用中出現「某個網站被重試之後把我們封鎖了」→ 那個網站需要更長的預設退避，或者重試次數要降
- 線上 LLM 端點實際量到 `retry-after-ms` 常常出現而 `Retry-After` 沒有 → 讀那個非標準標頭
- 匯入的來源常常跨同一個站的多個子網域 → 車道改成 registrable domain
