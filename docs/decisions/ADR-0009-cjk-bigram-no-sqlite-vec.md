# ADR-0009：中文檢索自建 bigram 索引，向量第一版不引 `sqlite-vec`

**狀態**：已採用（設計決定；實作尚未開始）
**日期**：2026-09-06

## 背景

**實測，2026-09-05，Node v24.15.0 內建的 SQLite 3.51.3：**
對同一列中文內容，FTS5 的 `trigram` tokenizer

| 查詢長度 | 命中列數 |
|---|---|
| 2 個字 | **0** |
| 3 個字 | 1 |

那是 `trigram` 的設計（少於 3 個 unicode 字元不 match），
[官方文件明寫](https://www.sqlite.org/fts5.html)，**不是 bug**。

問題是**中文查詢多半是 2 字詞**：「疫情」「台積」「戒嚴」。
一個對兩個字回 0 列的搜尋，使用者會認為是「沒有這筆資料」。

另一邊，向量檢索的現成答案 `sqlite-vec` 是**原生擴充**，
與這個專案「零原生模組、一鍵啟動」的前提（ADR-0002、`environment/versions.md`）直接衝突。

## 決定

1. **依 `item.lang` 選路**：
   - **CJK → 應用層自建的 bigram 索引**（把內容切成相鄰兩字的所有組合建表）；
   - **拉丁／西里爾等 → FTS5 `unicode61`**。
2. **`item.lang` 偵測不出來記 `und`，不猜** —— `und` 的內容兩條路都建索引。
3. **向量第一版用 BLOB 存 ＋ `Float32Array` 純 JS 暴力比對。**
   **超過 5 萬筆才重新評估。**
4. 中文標題排序自己維護 `title_rank` 欄位 ——
   `node:sqlite` **沒有 `createCollation`**（`db.function()` 有，collation 沒有），
   內容變動後用 `Intl.Collator('zh-Hant')` 重排。

## 考慮過但沒選的

| 方案 | 為什麼不選 |
|---|---|
| **FTS5 `trigram`** | 實測 2 字查詢命中 0 列。這一條是量出來的，不是推論的 |
| **FTS5 `unicode61` 給中文** | 它會把一整段沒有空白的中文當成一個 token，等於沒有索引 |
| **ICU tokenizer** | SQLite 的 ICU 支援要編譯時開啟，`node:sqlite` 的內建版沒有 |
| **結巴／中文斷詞套件** | 要帶一份字典（數 MB），而且斷詞錯誤會變成「查不到」而不是「查太多」—— bigram 的失敗方向比較安全 |
| **`sqlite-vec`** | 原生擴充 → 一鍵啟動要編譯工具鏈。這是 ADR-0002 已經付過的取捨 |

## 代價

- **bigram 索引要自己維護**：寫入變慢、索引體積約是內容長度的數倍。
- **精確率比真正的斷詞差。** bigram 會跨詞誤中（查「台積」可能命中
  「…來台積極…」），所以**結果排序變得比索引本身重要**。
- **暴力比對是 O(n)。** 5 萬筆時每次語意查詢都要掃完整個向量表 ——
  這就是那個上限的來源，不是隨手訂的。
- 兩條索引路徑意味著**同一個查詢在不同語言的內容上行為不同**，
  這件事要在 UI 上讓使用者感覺得到（見 REQ-0007）。

## 什麼情況要重新考慮

- **向量超過 5 萬筆**，或單次語意查詢在真實資料上超過 500 ms。
  那時的選項是 HNSW 的純 JS 實作，**不是**回頭引原生擴充。
- **bigram 的誤中率讓搜尋結果不可用** —— 條件是實際量測（取 30 個真實查詢
  算前 10 名的精確率），不是「感覺不太準」。
- Node 或 SQLite 換 major 版本時，**回來重跑一次那張 `trigram` 的表** ——
  這一條決定的基礎是一次實測，實測會過期。
