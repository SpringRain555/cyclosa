# ADR-0013：`AGENTS.md` 與 `CLAUDE.md` 是平級的兩份全文，不是本體加指路

**狀態**：已採用
**日期**：2026-09-06

> 這一份與 ADR-0012 一樣**已經生效**：兩份檔案 2026-09-05 就存在，
> 而標記區塊是 2026-09-06 補的（見下面「代價」）。

## 背景

兩家工具的載入規則**不一樣，而且失敗方向不對稱**：

| | Claude Code | Codex |
|---|---|---|
| 讀哪一份 | `CLAUDE.md` | `AGENTS.md` |
| 上層目錄 | **往上找並全部串接**（根在前、專案在後）| 慣例是「**最近的那一份勝出**」，且沒有規定會不會走出 repo 根 |

**失敗方向是「Codex 讀不到上游規則」。** 所以任何「一份是本體、另一份指過去」的
安排都會斷在 Codex 那一邊 —— 它只讀最近那份，而那份只有一行指路。

還有一個具體的前例：`valkona`（別人主導的 repo）的那兩份檔案在 upstream 是符號連結，
**在 Windows 上會變成 5 bytes 的純文字**，內容就是 `.rule` 三個字。
符號連結這條路在這台機器上已經被證明會壞。

## 決定

1. **兩份平級全文，內容相同** —— 差異只有標題與互相指認的那段聲明。
2. **每一份都必須自給自足**，不得假設上游的 `D:\Projects\CLAUDE.md` 會被讀到。
   上游規則以**摘要 ＋ 指路**的形式放在開頭的「上游規範」區塊
   （`<!-- upstream: D:\Projects v1 -->`），**不用 `@import` 把 53 KB 的
   CONVENTIONS 整份拉進來**。
3. **用 HTML 註解標出「合法可以不同」的區塊**：
   `<!-- agent-doc:sync-notice -->` 圈住互指聲明，
   `<!-- agent-doc:tool-specific -->` 圈住工具專屬段落（**本專案目前沒有**）。
4. 兩份由**同一份本文**產生，確保共用段落逐字相同。

## 考慮過但沒選的

| 方案 | 為什麼不選 |
|---|---|
| **一份本體 ＋ 一份指路** | Codex 只讀最近那份，指路就斷了。這是上面那張表的直接推論 |
| **符號連結** | Windows 上會變成 5 bytes 的純文字檔 —— `valkona` 已經證明過 |
| **`@import` 上游的 CONVENTIONS** | 53 KB 吃 context（官方建議每份控制在 200 行內），而且從專案目錄啟動時那是「外部 import」，會跳核准對話框 |
| **只靠人記得同步** | `agent-doc-drift` 這條檢查存在，就是因為它會漂 |
| **不放標記，靠人比對** | 那樣 `agent-doc-content-drift` 根本不會啟動（見下） |

## 代價

- **兩份檔案的內容重複**，每次改動的 diff 永遠是雙份。
- **產生器目前不在 repo 裡。** 兩份是 2026-09-05 用一支一次性腳本從單一本文產生的，
  那支腳本沒有進版控 —— 所以**現在保證平級的是驗證器，不是產生流程**。
  要把它變成流程的一部分，得先把產生器搬進 `tools\`。
- **`agent-doc-content-drift` 是 opt-in 的**：驗證器**只在兩份都帶標記時才比**
  （沒有這個前提時它對 31 個專案全部開火，等於零資訊量）。
  在 2026-09-06 補上標記之前，這個專案不在它的檢查範圍內 ——
  **一個沒有人採用的 opt-in 檢查，跟一條死掉的檢查長得一模一樣。**
- 隔壁的 `tagcor-ledger` 與 `rubricator` **目前都還沒有標記**，
  所以那兩個專案的內容比對仍然是關的（`tagcor-ledger` 排在階段 D）。

## 什麼情況要重新考慮

- **兩家工具的載入規則收斂到同一套**（例如 Codex 也明確定義往上串接）——
  那時「兩份全文」的理由就消失了。
- 若共用本文成長到讓兩份檔案都超過 200 行，要拆的是內容（把細節推到 `docs/`），
  不是拆成本體加指路。
