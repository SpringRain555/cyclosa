# ADR-0029：節點預算回答「會不會超過」，不回答「有幾個」

**狀態**：已採用。**2026-09-10（v0.12.0）實作。**
**日期**：2026-09-10

## 背景

`GET /subgraph/size` 存在的理由（ADR-0008、`graph-view.md`）是
**在使用者按下去之前就顯示代價** —— 工具列上四格跳數各自標出「會帶進幾個節點」，
超過預算的標琥珀色。roadmap 給它的預算是 **50 ms**，理由是「它在工具列上要即時」。

Stage 13 在 5 萬筆／20 萬關聯的合成資料上量它，得到：

| 焦點 | 3 跳鄰域 | 耗時 |
|---|---:|---:|
| 度數最高（1,660）| 54,318 個節點 | **4,566 ms** |
| p99（度數 31）| 24,858 | **1,470 ms** |
| **中位數（度數 3）** | **32,170** | **1,555 ms** |
| p10（度數 1）| 1 | 1.3 ms |

**中位數那一列是重點。** 一個只有三條關聯的普通節點，3 跳鄰域是 3.2 萬個 ——
因為路會穿過實體：一份文件提到一個被幾百份文件提到的機構，
那幾百份就全部在 2 跳之內。**這不是極端案例，這是一般案例。**

而 50 ms 的預算與「走到 3.2 萬個節點」之間差 30 倍。
**那個差距不是實作補得回來的** —— 走到 3.2 萬個節點這件事本身就做不到 50 ms。

## 決定

**一 · 走訪收一個上界（`stopAfter`），超過就停。**

**二 · 上界是 `RENDER_LIMIT`（8,000），不是 `NODE_BUDGET`（2,000）。**

工具列上有三個級距，而它們要靠兩條線分：

| 級距 | 條件 | 畫面 |
|---|---|---|
| 可以按 | < 2,000 | 一般 |
| 沒被驗收過 | 2,000–8,000 | 琥珀色 |
| 按了會是 413 | > 8,000 | 琥珀色 ＋「範圍太大」 |

數到 2,000 就停的話，第二與第三級距分不出來 —— 而那兩者對使用者是不同的事
（一個是「會慢」，一個是「打不開」）。所以上界是 8,000。

**三 · 超過上界之後回報的數字是下界，而且要說出它是下界。**

`HopCounts` 加一欄 `capped`（哪幾格是下界），畫面上顯示 `8000+` 而不是 `8001`。

**這一條比前兩條重要。** 只做前兩條的話，效能達標而**畫面開始說謊** ——
一個下界長得跟一個實際值一模一樣，而使用者沒有辦法分辨。
這個 repo 已經為同一種形狀修過好幾次（`und` 掉進布林的 `false`、
語意命中被標成「可能是誤中」）：**把一個「不知道」壓成一個看起來確定的值。**

**四 · 上界要在一跳之內檢查，不能等一跳做完。**

第一版寫成「每跳結束時檢查」，而量測顯示**它幾乎沒有用**：

| 焦點 | 原本 | 只在跳與跳之間檢查 | 跳內分段檢查 |
|---|---:|---:|---:|
| 度數最高 | 4,566 ms | 2,562 ms | **317 ms** |
| p99 | 1,470 ms | 2,360 ms | **937 ms** |
| 中位數 | 1,555 ms | **2,681 ms** | **283 ms** |

中位數那一格在第一版**變慢了**，而原因很清楚：第 2 跳結束時只有 1,922 個節點
（遠低於 8,000），所以檢查放行；然後第 3 跳一口氣帶進 3.2 萬個。
**爆炸整個發生在一跳之內，而跳與跳之間的檢查看不到它。**

所以前緣要分段處理（一段 400 個），每段之後檢查一次。

同一個修法也讓子圖本身快了：樞紐 2 跳從 **1,484 ms 降到 288 ms** ——
它現在一超過上界就回 `GRAPH_SUBGRAPH_TOO_LARGE`，不再走完才發現。

## 考慮過但沒選的

| | 為什麼沒選 |
|---|---|
| **把上界設成 `NODE_BUDGET`（2,000）** | 更快，但三個級距塌成兩個。「會慢」與「打不開」是不同的話 |
| **預先算好每個節點的鄰域大小** | 那是一張要跟著每次寫入維護的快取表。**關聯是機器產生而且會重算的**，維護點太多，而收益是一個只影響提示文字的數字 |
| **把預算從 50 ms 放寬** | 這一版沒有放寬 —— 見下面的代價。**做不到不是改預算的理由**，而要改要有人決定 |
| **不顯示數字，只顯示紅綠燈** | 小專題上那個數字是有用的（「2 跳 143 個」）。為了大專題把小專題的資訊拿掉是虧的 |
| **非同步逐格填** | 那把一個查詢變成四個，而且工具列會跳動。**沒有解決成本，只是把它攤開** |

## 代價

**一 · 仍然過不了 50 ms。** 283–937 ms（p95 最高 1,344 ms）。
從 4,566 ms 降到 317 ms 是 14 倍，但預算是 50 ms 而這裡是 283 ms 起跳。
**這一條沒有解決，只是變小了。** 剩下的成本在 `traverse` 自己（215 ms）
與 `mentionCounts`（101 ms，765 個實體），拆解在 `../environment/performance.md`。

**二 · 分段的粒度讓超出量不小。** 一段是 400 個前緣節點，而它們可能一口氣
帶進 16,000 個 —— 所以停下來時的 `visible.size` 是 16,272 而不是 8,001。
數字仍然是下界（畫面上是 `16272+`），只是那個下界比上界大得多。
把段調小會多付 SQL 往返，**而那個交換沒有量過**。

**三 · 停下來之後，走到的那個集合跟批次順序有關。**
同一個焦點、同一份資料，`visible` 的內容是決定性的（批次順序是決定性的），
但它**不是「前 8,000 個最近的節點」**，而是「照 id 順序掃到超過為止」。
這對 `/subgraph/size` 沒有影響（它只用數量），對 `/subgraph` 也沒有
（超過就是 413）。**但任何未來想用 `truncatedAtHop` 之後那個集合的人要知道這件事。**

## 什麼情況要重新考慮

- **`mentionCounts` 變成 O(1)**（例如實體上放一個提及數的欄位）——
  那會拿掉現在成本的五分之一，而它需要一個維護點。條件是「有人真的被這 300 ms 擋到」
- **50 ms 這個預算本身** —— 它的來源是「工具列上要即時」，而那句話沒有量過。
  如果 300 ms 的提示在真人操作下感覺不出來，那要改的是預算不是程式。
  **改之前要有一次真人操作的觀察，不是推論**
- **實體投影的門檻改了** —— 「穿過實體」是 3 跳爆炸的主因，
  而 `minToExpand` 直接控制有多少實體是可穿的
