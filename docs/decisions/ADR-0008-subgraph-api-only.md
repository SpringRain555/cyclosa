# ADR-0008：只提供子圖 API，沒有回傳整張圖的端點

**狀態**：已採用。**2026-09-07（Stage 7）實作**，而且由第五條守門測試守著
（`tests/guards/no-whole-graph.test.ts`：前後端都不得出現 `/api/**/graph` 這種字串）。
**日期**：2026-09-06

## 背景

**超過約 500 個節點的關聯圖只是變擠**（Obsidian 圖被批評的第三條）。
而一個累積半年的專題，8k 個節點是很正常的規模。

更關鍵的是介面設計的一條經驗：**有了整圖端點，前端遲早會呼叫它。**
不是因為誰粗心，而是因為它永遠是最短的那條路 —— 「先全部拿回來再過濾」
在節點數小的時候完全正常，然後在某一天不正常。

而**焦點＋脈絡與語意縮放**是這個領域的成熟解法：關注度決定顯示層級，
縮放時**改變表示型態**而不是只放大。

## 決定

1. **端點只有子圖查詢**：`focus`（從哪個節點出發）＋ `hops`（幾層）＋ `filters`（型別、狀態、時間）。
2. **沒有 `GET /graph`。** 不是「有但不建議用」，是不存在。
3. **語意縮放**：近距離顯示標題與縮圖，遠距離只顯示形狀與顏色。
4. 需要「全貌」的時候，答案是**伺服器端算完只傳結果**（統計、社群、時間軸），
   不是把圖傳給前端讓它自己算。

## 考慮過但沒選的

| 方案 | 為什麼不選 |
|---|---|
| **整圖端點 ＋ 前端過濾** | 傳輸與記憶體在 8k 節點時就炸；而且過濾邏輯會有兩份（前端一份、後端一份），兩份遲早不一致 |
| **分頁式的整圖** | 等於整圖，只是慢慢炸。而且分頁的圖沒有意義 —— 圖的價值在連通性，切一半就沒了 |
| **GraphQL** | 多一層而問題不變：使用者照樣可以寫出一個要整張圖的查詢，只是這次是動態的、更難擋 |
| **「有整圖端點，但只給 tools/ 診斷用」** | 那個端點會被前端呼叫。要診斷匯出就走 `tools/`，直接讀 SQLite |

## 代價

- **「我想看全貌」這個需求沒有直接的答案。** 要另外做概覽視圖，而那是額外的工作。
- **匯出證據包要走多次子圖查詢**再自己組起來，比一次拿整張圖麻煩。
- **除錯時想 dump 整張圖**要透過 `tools/` 的診斷匯出（直接讀 SQLite），
  而不是打一個 API —— 開發時會覺得囉嗦。
- 子圖 API 的參數空間比整圖端點大很多，**它自己會變成需要文件的東西**
  （`architecture/api-contract.md`）。

## 什麼情況要重新考慮

- 出現一個**必須一次拿到全圖**的功能（例如全域佈局預算、全圖社群偵測）。
  那時第一個要問的是「能不能改成伺服器端算完只傳結果」——
  如果可以，這條決定不變。
- 若子圖查詢本身在真實資料上變慢（例如 `hops=3` 超過 500 ms），
  那是索引問題不是這條決定的問題，先修索引。
