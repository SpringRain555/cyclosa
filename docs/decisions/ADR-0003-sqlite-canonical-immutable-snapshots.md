# ADR-0003：一個專題一個 SQLite，快照不可變，衍生物可整批重算

**狀態**：已採用（設計決定；實作尚未開始）
**日期**：2026-09-06

## 背景

三個互相拉扯的需求：

1. **抽取演算法會改版。** 正文抽取、語言偵測、實體抽取都會換版本或換模型，
   而且會**重跑既有的資料**。
2. **點註不能因為重跑而漂掉。** 使用者花時間標的東西掉一次，之後就沒有人再標
   （同 `state-machines.md` 對人工裁決的論證）。
3. **資料要能離開這個工具。** 一個把筆記鎖在自家格式裡的工具，長期累積等於長期綁架。

## 決定

**一個專題一個 `case.sqlite`**，它是那個專題的圖與中繼資料的唯一真實來源。
資料根目錄底下每個專題一個資料夾，內含：

| | 性質 |
|---|---|
| `case.sqlite` | 唯一真實來源 |
| `sources/` | 原始位元組快照 ＋ SHA-256 ＋ 抓取時間。**不可變** |
| `derived/` | 重構後的排版。**可以整批刪掉重算** |
| `notes/*.md` | 純 Markdown，**離開這個工具也讀得到** |
| `manifest.jsonl` | 這個專題抓過什麼、何時、雜湊多少 |

**點註釘在 `sources/` 的快照上**（見 ADR-0010），`derived/` 只是投影 ——
所以抽取改版時點註不會漂。

## 考慮過但沒選的

| 方案 | 為什麼不選 |
|---|---|
| **所有專題共用一個大 DB** | 備份、搬移、刪除單一專題全部變成 SQL 操作而不是搬資料夾；而且一個專題的損壞會波及全部 |
| **純檔案系統 ＋ JSON 索引** | 查詢、交易與一致性要自己重做一遍，那就是在寫一個比較差的 SQLite |
| **snapshot 存進 DB 的 BLOB 欄** | DB 檔會膨脹到備份不實際；而且外部工具（瀏覽器、diff）就打不開那些快照了 |
| **不留原始位元組，只留抽取後的正文** | 抽取改版就無法重算，而且點註沒有可以釘的不可變基準 |

## 代價

- **跨專題查詢要開多個 DB**，第一版沒有這個功能（見 ADR-0008 對「全貌」的處理）。
- **`sources/` 永遠只增不減。** 第一版沒有清理策略 —— 這是明知的缺口，
  不是忘記；清理策略要等到有真實的體積數字再訂。
- **`derived/` 與 `case.sqlite` 可能不同步**（重算到一半中斷），所以要有
  「整批重算」這個明確動作，不能只靠增量更新。
- 一個專題就是一個資料夾 → 使用者可以手動搬它、也可以手動弄壞它。

## 什麼情況要重新考慮

- 單一專題的 `case.sqlite` 超過 **2 GB**，或 `sources/` 超過使用者可接受的體積。
- **跨專題查詢變成主要使用方式**（例如「我在所有專題裡找過這個人嗎」）——
  那時要問的是「加一個跨專題索引」還是「改成單一 DB」，兩者代價不同。
