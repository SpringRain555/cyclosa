# ADR-0001：文件分六區，每份文件有一個明寫的權威範圍

**狀態**：已採用（設計決定；實作尚未開始）
**日期**：2026-09-06

## 背景

隔壁的 `rubricator` 的 `docs/index.md` 列了 **18 份文件，實際只有 4 份存在**，
而且它的 Stage 編號散在程式碼註解裡 —— 翻遍整個 repo 只找得到「Stage 2」與
「Stage 6」兩個孤立的數字，沒有任何一份文件列出完整清單。

那兩件事的後果不同但同源：**一份用權威語氣描述了不存在的世界的文件，
比沒有文件更糟** —— 照著它去讀的人（或 LLM）會撲空，而撲空之後就不再信任
其餘那些其實是真的的部分。

同時，同一個結論寫在三個地方，改的時候要記得改三個地方，漏掉的那一份
會繼續用權威的語氣講一件已經不成立的事。

## 決定

1. **採 CONVENTIONS §12 的六區骨架**：`architecture/`、`environment/`、
   `research/`、`decisions/`、`requirements/`、`operations/`，根層只留
   `index`／`roadmap`／`changelog`／`lessons` 四份跨區文件。
2. **`index.md` 是「哪份文件管哪件事」的權威**，每份文件一列，寫明
   **它是什麼的權威** 與 **不要寫在這裡的東西**。
3. **索引每一列都有現況欄**：`✅ 已經有`／`⬜ 打算有`／`❌ 刻意不做`，
   而且**逐檔確認**，不是照計畫填。
4. **一件事只有一個權威位置。** 其他地方要提到它就連結過去，不複製內容。

## 考慮過但沒選的

| 方案 | 為什麼不選 |
|---|---|
| 一份大 README | 到第 300 行就找不到東西；LLM 要嘛整份讀（貴）要嘛讀一半（錯） |
| 決定只寫在程式碼註解 | `rubricator` 的 Stage 編號就是這樣消失的 —— 註解沒有目錄，不存在的東西沒有人找得到 |
| 外部 wiki／筆記軟體 | 不進版控 → 與程式碼分岔，而且 review 時看不到它改了什麼 |
| 索引不標現況 | 那就是 `rubricator` 現在的樣子。**分不出「已經有」與「打算有」的索引比沒有索引更糟** |

## 代價

- **每次寫東西要先想「這件事的權威位置在哪」**，比隨手寫在最近的檔案裡慢。
- **改完檔案要回頭改索引的現況欄**，而那一步很容易忘 —— 忘記的話這份 ADR
  想解決的問題就原地復活。
- **第一版就有 14 份 ADR 與 8 份 REQ，其中一部分永遠不會被讀。** 這是刻意付的：
  它們的價值在「決定當時的處境被記下來了」，不在點閱率。

## 什麼情況要重新考慮

- **`index.md` 的現況欄連續兩次與實際檔案不符** —— 那代表沒有人在維護它，
  應該改成由腳本產生（掃檔案系統），而不是繼續手寫。
- 治理層的 `docs-layout-drift` 檢查（CONVENTIONS §12）對這個專案開火時，
  先確認是專案漏了一區，還是六區骨架對這個專案訂錯了。
