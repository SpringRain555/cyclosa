# REQ-0004：LLM 擴展與出處

**狀態**：**已實作（2026-09-08）** —— 八條驗收條件全部有對應的測試。
**日期**：2026-09-06

## 使用者要什麼

輸入一個主題／人物／事件，工具去找相關的東西回來，
**而且每一條關聯都看得到「憑什麼」**。

反過來說：使用者要的**不是**一張一鍵生成、看起來很有道理的圖。
那種東西這個領域已經有很多了，而它們的問題都一樣 ——
你沒辦法檢查它，所以你也不能真的用它。

## 驗收條件

- [x] 擴展前**先產生多視角子問題**，使用者**勾選要展開哪幾條**再開始 ——
      不是黑箱一次跑完。（子問題本身就是好的 UI：它讓使用者看到工具打算怎麼找。）
- [x] 每一條機器產生的邊都帶 `edge_evidence`：**引文 ＋ `char_start` ＋ `char_end`**，
      指向某個 `item`。
- [x] **沒有出處的邊只能是 `待查證`**，UI 上不得顯示成已確認。
- [x] **重跑擴展不改任何 `origin='human'` 的列**
      （可驗：跑前後對該子集做 diff，必須為空）。
- [x] provider 配不上時顯示 `PROVIDER_CAPABILITY_MISSING` 對應的繁中訊息**並停手**，
      **不自動換一個能力較弱的**（ADR-0006）。
- [x] run **可取消**；取消 = 殺子程序 ＋ 標 `已取消`，**已寫入的保留**。
- [x] `agent` 找到的 URL **一律交回主程式走擷取管線**
      （可驗：`agent` 的沙箱目錄裡不得出現任何抓取產物）。
- [x] **失敗路徑**：子程序逾時、超過請求數上限、或輸出解析失敗時，
      run 標 `部分失敗` 或 `失敗`，且**已經寫入的節點與邊保留**。

> ### 兩條實作時才補上的
>
> **1. 每一條機器產生的邊都帶引文 ＋ 字元區間 —— 而那個區間是我們自己找的。**
> 模型回的位置一律不採信；引文在正文裡找不到就**沒有這條邊**
> （`PROVIDER_QUOTE_NOT_FOUND`，ADR-0021）。
> 上面那一條驗收寫的是「帶 `char_start` ＋ `char_end`」，
> 而**它沒說那兩個數字是誰算的** —— 那正是最容易寫錯的地方。
>
> **2. 「不自動確認高信心的邊」是靠沒有那條路達成的，不是靠一個判斷。**
> 擴展的寫入路徑上沒有任何地方會設 `confirmed`：
> 機器建的邊一律 `pending`，而 `confirmed` 只從人按的那個端點來。

## 刻意不做

- **自動確認高信心的邊。** 人工裁決是這個工具與競品的**全部差別**；
  一旦機器可以自己確認，那個差別就沒了。
- **報告產生。** 只做證據包匯出（REQ-0005）。
- **讓 `agent` 自己抓網頁。**
- **把信心值顯示成小數。** 連續分數只用於排序與粗略的視覺通道。
