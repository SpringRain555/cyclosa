# ADR-0006：provider 靠能力宣告配對，配不上就停手，agent 只在沙箱裡跑

**狀態**：已採用。**2026-09-08（Stage 9）實作** —— `claude -p` 當 `agent`、
本機 Ollama 當 `chat`，配對規則在 `domain/provider/`，兩個角色的沙箱與上限都在跑。
**日期**：2026-09-06

## 背景

LLM 在這個工具裡有三種角色，**來源異質**：

| 角色 | 怎麼接 |
|---|---|
| `agent` | CLI 子程序（`claude -p --output-format stream-json`、`codex exec`）|
| `chat` | HTTP，含 Ollama、LM Studio 等 OpenAI-compatible 端點 |
| `embed` | 本地優先 |

它們的能力差很多：會不會上網、支不支援工具呼叫、能不能保證 JSON schema、
看不看得懂圖、context 多大。

**市場調查裡 NotebookLM 的第一條缺點就是「綁單一模型」** —— 所以不能只支援一家。
但支援多家的預設做法（配不上就自動換一個弱的）會產生更糟的東西：
**一份看起來正常、其實沒有出處的結果**。

## 決定

1. **provider 宣告能力**：`{browse, tools, json_schema, vision, context_tokens}`。
2. **任務宣告需求**，由配對規則（在 `domain/provider/`，純函式）決定能不能跑。
3. **配不上就報 `PROVIDER_CAPABILITY_MISSING` 並停手 —— 不靜默降級。**
   UI 要說清楚「這個任務需要 X，目前設定的 provider 沒有 X」。
4. **`agent` 子程序的工作目錄鎖在 `<資料根目錄>\cases\<專題>\agent\runs\<run-id>\`。**
5. **`agent` 找到的東西不能自己抓**，一律交回主程式走**唯一的擷取管線** ——
   節流、robots、雜湊、manifest 只存在於那一層。
6. **每個 run 有逾時、請求數上限、成本上限**，取消 = 殺子程序 ＋ 標 `已取消`，
   **已寫入的保留**。

## 考慮過但沒選的

| 方案 | 為什麼不選 |
|---|---|
| **配不上就自動 fallback 到較弱的 provider** | 這正是要避免的靜默降級。使用者拿到一份沒有出處的結果，而畫面上沒有任何地方說它降級了 |
| **只支援一家** | 綁死；而且本地模型（隱私）與雲端模型（能力）的取捨應該由使用者決定 |
| **讓 `agent` 自己抓網頁** | 節流、robots、雜湊、manifest 全部失效。開第二條路等於那一層不存在 |
| **用「模型名稱」白名單而不是能力宣告** | 名單會漂（新模型天天出），而且同一個名稱在不同 provider 上能力不同 |

## 補記（2026-09-09）：**少宣告一個任務，這條規則對它就等於不存在**

第 3 條寫著「配不上就報 `PROVIDER_CAPABILITY_MISSING` 並停手」。
上線之後才發現：**`chat` 底下有兩個任務，而只有一個宣告了需求。**

| 任務 | `TaskRequirement` | 有沒有閘門 |
|---|---|---|
| 歸納切入角度 | `TASK_ANGLES` | ✅ |
| **從正文抽實體與關係** | **沒有** | ❌ |
| 找候選來源 | `TASK_FIND_SOURCES` | ✅ |

`expand-service.ts` 直接把 `EXTRACT_SCHEMA` 送出去，前面沒有任何 `missingFor`。
勾選那一步只檢查 chat「有沒有設定」，不檢查它的能力。

**失效的方式是靜默的**，而且比自動降級更難發現：一個 8000 context 的模型
會通過角度那一關、抓完全部網址，然後在每一份文件上把 12,000 字的正文截掉一半 ——
**抽出來的關聯照樣帶引文、照樣進待查證，畫面上看不出任何異常。**
自動降級至少還有一個「降級了」的事實可以顯示；這個連事實都沒有。

補上 `TASK_EXTRACT`（`json_schema` ＋ 18000 context），閘門放在勾選那一步
（**抓之前**，不是每份文件一次）。設定頁的 `chat` 準備度也改成兩個任務都要過。

> ### context 的數字是量出來的，而它比想像中難猜
>
> 送進去的正文上限是 12,000 **字元**，而字元不等於 token。
> 拿同一段 12,000 字的中文實測三個 tokenizer 家族：
>
> | tokenizer | token 數 | 每字元 |
> |---|---|---|
> | Gemma | 8,048 | 0.67 |
> | Nemotron | 11,185 | 0.93 |
> | **OLMo** | **14,383** | **1.20** |
>
> **同一段字，最多與最少差 1.8 倍。** 「12,000 字大概就 12,000 token」
> 這個直覺對其中兩個是錯的。門檻取最壞的那一個再加提示詞與輸出。

### 順帶修掉的第二件：**context 不夠時，畫面上顯示「缺少：（空白）」**

`missingFor` 早就會回「旗標都齊、只是 context 不夠」這種結果
（`flags` 是空陣列、`context` 有 `[需要, 有的]`），而三個呼叫端**都只帶 `flags` 出去**。
於是使用者看到的是一句「這個角色要跑的任務需要：，而目前設定的模型沒有」。

**那比不報錯更糟：它說了有問題，卻沒說是什麼問題。**
現在 `detail` 帶 `needContextTokens` 與 `haveContextTokens`。

### 第三件：**閘門看的 context 跟執行時用的 context 不是同一個數字**

補完 `TASK_EXTRACT` 之後跑評測，`ollama ps` 顯示了一件對不上的事：

| 問誰 | `gemma4:31b` 的 context |
|---|---|
| `/api/tags` 的 `details.context_length`（**閘門看的**）| 262144 |
| `ollama ps`（**實際載入的**）| **32768** |

前者是模型支援的上限，後者是 Ollama 用它自己的預設載入的
（`OLLAMA_CONTEXT_LENGTH`，使用者沒設就是內建值）。**閘門看的是前一個。**

於是同一個病又出現一次，只是往下一層：閘門說可以，執行時把正文截掉，
而抽出來的關聯照樣帶引文、照樣進待查證。這一次的機器上內建值是 32768
（大於門檻 18000，所以碰巧沒事），**而「碰巧沒事」不是一個可以依賴的狀態** ——
使用者把 `OLLAMA_CONTEXT_LENGTH` 設成 4096 就會壞，而且壞得無聲。

所以請求裡明確帶 `num_ctx: REQUIRED_CONTEXT_TOKENS`（所有任務裡最大的那一個）。
**不取更大**是因為 KV 快取隨 context 線性成長 —— 開一個用不到的大 context
是在燒顯示記憶體，而這個工具跑在使用者自己的機器上。

### 這件事的通則

**一條規則只作用在「有宣告的東西」上，所以漏掉宣告等於漏掉規則。**
而漏掉宣告不會有任何症狀 —— 沒有錯誤、沒有警告，
那個任務只是靜靜地不在檢查範圍內。這跟 `lessons.md` 那條
「零命中跟零誤報長得一模一樣」是同一種病，發生在更前面一步：
**這裡連「零命中」都沒有，因為根本沒有那條檢查。**

守門測試 `tests/guards/extract-context.test.ts` 釘住
`MAX_TEXT_CHARS` 與 `TASK_EXTRACT.minContextTokens` 的關係 ——
兩個數字在不同的層，改一個很容易忘了另一個。

## 代價

- **使用者會撞到硬牆**：「你的設定跑不了這個任務」比自動跑出點什麼的體感差很多。
- **能力宣告要人工維護。** provider 改版之後宣告可能不準，而**不準的宣告比沒有宣告更糟** ——
  它會讓配對規則做出有信心的錯誤判斷。
- **成本上限的單位還沒有答案**（`research/open-questions.md` Q3）：
  token 數不等於錢，而錢要靠 provider 回報。**設一個查不到實際值的上限等於沒設。**

  > ### 後續（2026-09-06）：實測過了，Q3 有答案
  >
  > 兩個 provider 各跑一次最小請求，看它們實際回什麼：
  >
  > | provider | 回報什麼 |
  > |---|---|
  > | `claude -p --output-format stream-json` | **`total_cost_usd`（實際金額）** ＋ 每個模型的 `costUSD` ＋ token 分項（含 `cache_creation` 與 `cache_read`）＋ `duration_ms`。**但只在最後那個 `result` 事件裡** |
  > | Ollama `/api/chat` | `prompt_eval_count`／`eval_count` 與各種 duration。**沒有任何成本欄位** —— 它是本機的，金額成本真的是零 |
  >
  > **所以上限分三種，而不是一種**：
  >
  > 1. **請求數 —— 主要上限。** 每個 provider 都數得到，跨 provider 可比。
  > 2. **牆鐘逾時 —— 每個都有。**
  > 3. **金額 —— 只在 provider 回報實際值時才啟用。** 有就顯示實際花費；
  >    沒有就顯示「本機執行，無金額成本」。**不估算。**
  >
  > 選「請求數」當主要上限**不是因為它最容易，而是因為量到了一件事**：
  > 一次只回兩個 token 的 `claude -p` 呼叫花了 **0.18 美元**，
  > 其中幾乎全部來自 **29,310 tokens 的 cache creation**。
  > **每次呼叫有很大而且大致固定的開銷** —— 在這種成本結構下，
  > 「跑了幾次」比「產生了幾個 token」更接近實際花費。
  >
  > 還有一件實測順帶看到的：`stream-json` 會發 `rate_limit_event`，
  > 帶 `rateLimitType`（`five_hour`）與 `resetsAt`。
  > **那是 provider 自己的限制，不是我們設的** —— 但擴展作業撞到它的時候
  > 要能說出「是對方的用量限制，某某時間重置」，而不是一個泛泛的失敗。
  >
  > **這段是補記，不是改寫。** 上面那條代價在 2026-09-06 之前是真的。
- 沙箱是「工作目錄 ＋ 交回主程式」這種約定式的邊界，**不是作業系統層的隔離** ——
  子程序仍然是使用者權限下的完整程式。

  > ### 後續（2026-09-08，Stage 9）：真正在執行第 5 條的不是沙箱檢查，是工具清單
  >
  > 接 `claude -p` 的時候發現一件事：**它有 `--tools`。**
  > 傳 `--tools WebSearch` 之後，工具清單裡沒有 `WebFetch`、沒有 `Write`、沒有 `Bash` ——
  > 所以子程序**做不到**把一份網頁存進沙箱，而不是「約定好不要這麼做」。
  >
  > `WebFetch` 特別要點名：它會真的把頁面抓下來，而那正好繞過我們那一層。
  > **搜尋是「找到 URL」，抓取是我們的事。**
  >
  > 事後掃沙箱那條檢查仍然留著，而且**掃的時候不分成功失敗** ——
  > 只在成功時掃的話，一個「抓了一堆東西然後才失敗」的子程序就查不到了，
  > 而那正是最該被查到的情況。
  >
  > 兩層擋同一件事的理由是：第一層是我們傳給別人程式的參數，
  > 而**參數會被改版、被忽略、被拼錯**。
  >
  > 白名單的形狀寫在 ADR-0021。

- **能力宣告能問就問，不要自己填**（2026-09-08 補）。
  Ollama 的 `/api/tags` 每個模型帶一個 `capabilities` 陣列與 `details.context_length` ——
  **那是 provider 自己說的，比我們填的準**，而上面那條代價（「不準的宣告比沒有宣告更糟」）
  的代價就是這樣壓到最小的。`chat` 只有 `json_schema` 是我們填的，
  因為它是**伺服器的功能不是模型的功能**（`format` 參數收整份 schema 並用受限解碼保證它）。

- **`context_tokens: 0` 當成「不知道」而放行**（2026-09-08 補）。
  兩種錯法的代價不對稱：擋掉一個其實跑得動的 provider，
  **使用者無從得知要去改什麼**（能力宣告是我們寫的，不是他改得到的）；
  放行一個其實不夠大的，會在真的跑的時候拿到一個**來自 provider 自己**的明確錯誤。

## 什麼情況要重新考慮

- **Q3**：接第一個 `agent` provider 時，先看它的 `stream-json` 實際回什麼欄位，
  再決定成本上限用什麼單位。
- **某個能力欄位連續三個 provider 都填不出來** → 那個欄位是錯的抽象，該拿掉。
- 若「配不上」在實際使用中頻繁到變成主要摩擦，要考慮的是**任務降級**
  （把任務拆成不需要那個能力的版本，並明確標示）而不是**provider 降級**。
