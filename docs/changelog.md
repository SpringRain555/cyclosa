## v0.26.0 —— 2026-10-03　把還沒抽過的資料抽進圖、畫面不顯示花費金額

**整理（Stage 24）的第一片。** 匯入的資料原本只能等研究找到同一份才進圖 —— 彩排時 28 章匯入之後，圖上只畫得出焦點那一份。

### 抽進圖（ADR-0033 S24-1～S24-5）

- 「匯入與研究」的匯入卡片下面多一塊**「把還沒抽過的資料抽進圖」**：列出專題裡還沒抽過、有正文的資料，
  逐份勾（**預設不勾**、有「全選」），按下去開一筆標籤「抽進圖」的作業，畫面跳到它的進度
- 規則跟研究建圖同一套（`callExtract` → `applyExtraction`）：實體對齊、引文位置由程式自己找、找不到就沒有那一條，
  建出來的都是待查證。一份抽壞不影響其餘；暫停、取消、復原都走作業那一套；跑完「在關聯圖上看這一次抽出來的」
- **每一份只讀正文開頭約 12,000 字**（抽取本來就是這樣）：書的一章只會抽到開頭那一段，清單上標「只讀開頭」
- 「還沒抽過」＝`extracted_at` 是空的、**沒有機器建的關聯拿它當出處**、有正文。v12 以前抽過的資料那一欄是空的，
  只看它的話會把抽過的又列出來
- 同一個專題同時只有一次研究或抽進圖沒結束（D4）：抽進圖不開研究的殼，改成兩邊互查。新錯誤碼
  `CONSOLIDATE_RESEARCH_OPEN`、`CONSOLIDATE_RUNNING`、`CONSOLIDATE_SELECTION_INVALID`、`CONSOLIDATE_UNEXPECTED`
- **復原一筆作業時，把那一筆寫的「抽過了」清回去**（研究建圖也適用）：不清的話關聯被復原掉，那一份卻再也不會出現在清單上
- 還沒做的：完整的整理（模型讀專題、提「合併實體／補關聯／改型別／補繁中名」的操作清單）仍待做

## v0.25.0 —— 2026-10-03　研究從規劃走到建圖、建議模型換來源、舊擴展退場

**Stage 19–22 一次交付**：不是把「擴展」改名，而是先規劃、再蒐集與初讀、逐筆確認，最後才把選定的資料抽成關聯。

### 研究：花錢之前先問，確認之後才建圖

- **規劃**：用對話整理方向；相關性命中走全文檢索，不花模型費用。閘門一「照這份規劃開始」之前先檢查需要的模型能力。
- **蒐集與初讀**：逐方向找來源，同一網址只留一列；模型只搜尋，正文仍走唯一的擷取管線。拿不到的可以逐列上傳對回候選，或記下原因。
  初讀一次回有沒有關、繁中標題與摘要；這是模型的建議，不是人的決定。完成蒐集是閘門二。
- **逐筆確認**：分清「依預設」與「人改過」。選進圖、只留書目或丟掉；已有正文的中間選項叫「只留著，不抽」，不另建書目節點。
  閘門三看的是每列最後生效的決定，不要求每列都手動選一次。
- **建圖**：每份選進圖的資料都走共用的 `callExtract`／`applyExtraction`，包含對回候選的上傳。
  引文位置由程式自己找，找不到就沒有那條邊；機器不覆寫人的裁決。**單純匯入仍不自動抽關聯**。
- **書目節點**：拿不到正文也能留下書目，以虛線稜線與淡填表示、圖例分開說明。人指定的引用在建圖時才寫成已確認的人工關聯，不冒充模型找到的引文。
- **中斷與收尾**：取消或關程式保留已寫入結果，繼續建圖只做未完成的候選；取消後才有「到此為止」。可以看這一次新增的部分，缺口評估是另按的模型意見、不給工具。
  花費逐任務列出，未知不當成零；刪研究先預覽刪掉與留下的清單，只刪研究與模型呼叫紀錄，不刪圖、資料與作業。

### 匯入頁與閱讀器

- **一批檔案一筆作業**：等不到下一個檔案五分鐘自動收尾，回 `FETCH_UPLOAD_TIMEOUT`，不一直掛著。
  節流狀態列只在擷取時出現，完整說明在設定頁「狀態說明」；窄畫面收成下拉選單，紀錄入口改叫「歷次紀錄」，相關提示改指向「匯入與研究」。
  「重算全部正文」留在原處。
- **原文／繁中**：閱讀器與節點面板預設原文，可切換初讀產生的標題與摘要；譯文有標示。**正文不翻譯**，原文與快照不被覆寫；還沒有初讀結果就不假裝有譯文。

### 建議模型只從非中國來源挑（ADR-0035）

**永久規則，底座與蒸餾來源也算；查不清楚的不當建議值。** 管的是建議值與推薦文字，不限制使用者自己選模型。
本機嵌入改為 `hf.co/mykor/granite-embedding-311m-multilingual-r2-GGUF:BF16`，抽取改為 `granite4.2:8b`；記憶體夠可選 `gemma4:12b`。

**品質代價不是零。** ADR-0035 同一份語料的重測：嵌入跨語言 MRR@10 從對照組的 **0.940 降到 0.766**，繁中查英文原文變差；
本機抽取每份平均 **4.8 條關係、引文 93%、14 秒**，對照組是 **8.2 條、100%、7 秒**。大一級的 `gemma4:12b` 是 **12.0 條、93%、15 秒、7.6 GB**。
這些是既有量測，不是每份資料的保證；**初讀暫用 `granite4.2:8b`，初讀建議值的同語料實測仍待補**。
換嵌入模型不會把舊向量當成新向量：既有專題要在搜尋面板按「建立語意索引」，重算前模型不符會明說。

### 升級會清什麼、留什麼

**舊擴展流程與「角度」（`angles`）任務退場。** 既有專題開啟資料庫升到 schema v13 時，先把資料庫複本放進資料根的 `backups/`；
沒有指定備份位置或備份失敗就不升級。**清除不是一個能按「復原」撤回的作業，退路是升級前的備份。**

| 清除 | 保留 |
|---|---|
| 非手動的舊 `expand` 作業與舊角度表 `run_angle` | 手動抽取作業改記為 `extract`；匯入與研究作業不因這次清除刪掉 |
| 舊擴展產生、沒有人裁決過的機器關聯 | 人建立或裁決過的關聯 |
| 舊擴展帶入、未讀／未點註／未排除，且沒有被留下的關聯引用或用作端點的資料 | 讀過、點註過、排除過的資料；留下的關聯仍用到的出處與端點，**包含其他作業的關聯** |
| 被刪資料的全文索引、向量與各版正文衍生物；清理後的孤立實體 | 不可變快照 `sources/` 不動；保留資料與關聯解除對已刪作業的參照 |

有清掉舊擴展作業的專題會留一則**「專題升級通知」**，在**「匯入與研究」頁最上方**看（「歷次紀錄」也在同一頁）：刪了幾筆作業、幾份資料、幾條關聯，留下多少與原因；
保留原因可能重疊，不能直接相加。按「知道了」後不再顯示，不是每次啟動重複通知。
**升級前一定先確定備份是最近的**：D17 的清除對每個專題只做一次、做完寫通知，再開不會重做。

### 本機伺服器只收自己頁面的請求、子程序不經過 cmd.exe（ADR-0036）

**「只綁 127.0.0.1」擋的是別台機器，不是這台機器上的網頁。** 2026-10-02 查到兩條路，都不需要使用者做任何事：
跨站的 `text/plain` POST 不需要預檢，會把模型設定整份蓋成預設值；DNS rebinding 之後什麼請求都送得到 ——
把 CLI 指令設成任意程式、下一次探針就執行它，或把任一個環境變數的值送到別人的網址。

- 每個請求進路由之前檢查：`Host` 的主機名只准 `127.0.0.1`／`localhost`／`[::1]`；會改東西的請求帶了 `Origin`
  就必須等於 `http://` ＋ 自己的 Host（同一台機器別的埠也擋）、帶了 `Sec-Fetch-Site` 只准 `same-origin`／`none`；
  `text/plain` 解析器拿掉。被擋的回新碼 `IO_REQUEST_FOREIGN`（403／415）。啟動器、`curl` 不帶 `Origin`，照常
- **子程序一律不經過 `cmd.exe`**：設定裡的 CLI 指令是 `.cmd`／`.bat`（npm 裝的 Claude Code）時直接說不支援、
  請改用原生安裝的 `claude.exe`。原本那條路會把提示詞（含專題文件的段落）原樣接成一個字串交給 `cmd.exe`。
  新守門 `no-shell-spawn`

## v0.24.3 —— 2026-09-19　伺服器自己停的時候留得下紀錄

**使用者開 v0.24.2 起來看**：把找來源改到 OpenAI 相容 API（`codex/gpt-5.6-luna`）、按「儲存並測試」——
四個任務都測過了（找來源 7.9 秒、量到會搜尋），畫面上卻多了一塊「出了問題：發生了未知的錯誤。請把下面的識別碼交出來。」
而下面沒有識別碼；重新整理是「127.0.0.1 拒絕連線」。**伺服器在測完的那一刻不見了，而 `server.log` 的最後一行是啟動的那一行。**

### 查了什麼

- **沒重現**：同一份設定（複本）上同一個流程跑了 16 次 —— 模型冷的、熱的都有，也照啟動器的起法起過 —— 伺服器一次都沒停。
- **Node／libuv 在 Windows 上有一個已知的當機**（`UV_HANDLE_CLOSING` 的 assert，結束碼 0xC0000409，
  [nodejs/node#56645](https://github.com/nodejs/node/issues/56645)）：用過 `fetch` 之後**結束行程**時會撞到。
  v0.24.2 收尾時 vitest 的一個工作行程就是這個碼死的，那一次多半是它；但伺服器沒有在結束，這個 bug 解釋不了使用者那一次。
- 記憶體不是：31 GB、三個模型在 32 GB 的顯示卡上放得下；這一條路上也沒有沒人等的 promise。
- **真正的問題是它死得一個字都沒留下**：`log.ts` 寫著日誌檔存在的理由是「讓它自己死掉了留得下線索」，
  而那只對經過 logger 的那幾行成立。沒接住的錯誤（含沒接住的 rejection）與原生層的中止，Node 都只印到 stderr ——
  而一鍵啟動的伺服器沒有主控台，stderr 沒有去處。

### 改了什麼

- **`shared/crash-trace.ts`**（`main.ts` 最先裝上）：沒接住的錯誤經過 `uncaughtExceptionMonitor` 寫一行到 `server.log`
  （origin、名字、訊息、堆疊前 12 行；**不改 Node 的預設行為**，程式照樣結束）；`exit` 寫一行結束碼；
  V8 的 fatal error 由 Node 寫一份診斷報告到日誌旁邊 —— **不含環境變數**（金鑰在那裡）、不含網路介面。
  「沒接住的 rejection 也會觸發那個監聽」是這個設計的前提，**對著真的 Node 跑了一次**（測試裡一支子程序）
- **`tools/Launch.ps1`**：伺服器的 stderr 導到 `server.err.log`（輪替留上一份 `server.err.prev.log`）——
  原生層的 assert 繞過 Node，只有那裡看得到；啟動失敗時連它的最後幾行一起顯示。**stdout 導到 NUL**：只導 stderr 的話，
  node 的 stdout 會指著啟動器那個等一下就關掉的主控台（實測時伺服器的日誌行直接印進了起它的那個行程）。
  導向之後仍然是自己的（隱藏的）主控台：實測 node 底下有自己的 `conhost.exe`，起它的那個行程走了它還在
- **新錯誤碼 `IO_SERVER_UNREACHABLE`**（只有前端會產生：`fetch` 本身失敗）。原本借用 `IO_UNEXPECTED` 的訊息，
  叫人交出一個不存在的識別碼；現在說「連不到 Cyclosa 的伺服器 —— 它可能已經結束了」、怎麼重開、紀錄在哪

### 怎麼驗的

`Verify.ps1` 全綠。照啟動器的新起法起建置好的伺服器（scratch 設定）：打開設定頁 → 關掉伺服器 → 按「儲存並檢查」，

`server.err.log` 是空的。另一支故意當掉的程式照同一種起法起：堆疊寫進了 err 檔，起它的行程先走了它還在跑。
**啟動器本身沒有整支跑過**（它會開瀏覽器）—— 起法是逐行照抄去測的。

## v0.22.1 —— 2026-09-18　送出去的 schema 少一欄，而線上端點一律 400

**使用者給了一把第三方代理（OpenAI 相容）的金鑰要我測。** 那是這台機器上
**第一次**有線上端點可以打，而它當場抓到一個從 v0.18.0 活到現在的洞。

### 症狀是兩句互相矛盾的話

設定頁「實際打一次」回 `PROVIDER_JSON_UNSUPPORTED`，
而**同一次的格式量測寫著「這個端點支援 `json_schema`」**。直接對端點打一次就看到原因：

```
HTTP 400 invalid_json_schema
'additionalProperties' is required to be supplied and to be false.
```

OpenAI 的嚴格模式對**每一個物件節點**要求 `additionalProperties: false`
（`required` 也要列全，而我們的三份本來就列全了）。
**格式量測用的探針 schema 寫了那一欄，三份真的 schema 一份都沒寫。**

所以：量測永遠綠、真的呼叫永遠 400。而 v0.18.0 宣稱的「可以接任何 OpenAI 相容端點」，
**對嚴格模式的端點從來沒有成立過** —— 沒被發現的原因就寫在當時的文件第一段：
「這台機器上沒有任何線上服務的金鑰，所以一個線上端點都沒有量。」

**更糟的是它說錯了誰的錯**：程式對「`schema` 模式下被 400」的解釋是
「量測舊了，端點大概改了規格」。使用者照著去按重新檢查，而那一按又是綠的。

### 修法：在邊界上補，不動那三份 schema

`strictify()`（`domain/provider/schema-check.ts`）在送出去之前遞迴補上那兩條。
**不寫進三份 schema**，因為那是某個端點的要求不是我們的規則 ——
寫進去會連帶讓 `conformsTo` 對本機 Ollama 那條路收緊（多一個欄位就整份判不過），
而那是沒有人要求過的行為改變。

### 驗證（對著真的端點）

| | |
|---|---|
| `GET /openai/v1/models` | 200，5 個模型 |
| 三份真的 schema（strictify 之後）直接送 | 角度／抽取／找來源都 **HTTP 200** |
| 設定頁「實際打一次」 | **通過**，5.1 秒；`provider-checks.json` 記下 `schema` ＋ 時間 |
| 拿掉 `strictify` 的那一行 | `tests/domain/schema-strict.test.ts` 14 條裡 6 條紅（同一種改法改回去）|

量測寫進 `research/openai-compat-json-schema.md` 的「結果三」與 `query-log.md`；
教訓（全域）進 `lessons.md`：**一個「支援某某協定」的宣稱，只有對著那個協定的
真實端點跑過才成立** —— 自家的相容實作證明的是「我們的程式會動」。

## v0.21.0 —— 2026-09-18　回 200 的驗證頁不再被當成內容（Q7 的答案）

**v0.20.1 留下的問題，使用者要求去查別人怎麼做之後回答的。** 判斷在

### 三層，由強到弱

| 層 | 依據 | 結論 |
|---|---|---|
| 1 | **要的型別與拿到的型別矛盾**：探測問的是一支 API，回來的是 `text/html` | 驗證頁 |
| 2 | **廠商自己宣告的信號**：`cf-mitigated: challenge`（Cloudflare 官方文件）、頁面裡的 Anubis 標記 | 驗證頁 |
| 3 | HTML ＋ 自稱 `noindex` ＋ 小於 20 KB ＋ `no-store`，**四個同時成立** | 不確定（照樣不存）|

Cloudflare 的 JS Detection 會把 `__CF$cv$params` 注入**正常內容頁**，所以刻意不收那個字串。
**第三層永遠不下定論**，只說「看起來不像內容，你自己看一眼」。

- **401／403 現在有兩種**：帶廠商標頭的是驗證頁，其餘仍然是「要登入」。**沒有依據就不猜。**

**這一版最值得記的一句**：走 `Crawler` 實跑 dblp 的探針，回的不是驗證頁而是

### 一、dblp 的探針「回 200」，而那一頁是反爬蟲驗證頁

v0.20.0 寫進去之前打過一次：200、`text/html`。文件寫「內容是 JSON」—— **沒有看內容**。
重打一次，`<title>` 是 `Making sure you're not a bot!`（Anubis），網頁版也是。
`probeOne` 只看錯誤碼，所以「檢查全部」會把它判成「讀得到」，而 v0.20.0 同一版把清單接進了 agent 的提示詞。

現在 dblp 沒有探針、改成**預設關掉**的人手入口；Google Scholar（robots 不准）同樣預設關掉。
新欄位 `CatalogEntry.enabledByDefault`：那兩列留在清單上讓人看得到原因，但不進提示詞。
**驗證頁怎麼認**是 `research/open-questions.md` 的新條目 **Q7** —— 不順手列標記清單（Q2 的教訓）。
教訓在 `lessons.md`。

### 二、提示詞的段落標題跟裡面放的東西不一致

v0.20.0 照 `preferenceOf` 分三段，而「降權」包含 robots 不准、要跑 JS、連不到 ——
它們全被放在標題寫著「**多半要登入**」的那一段；「還沒抓過」的標題寫「**使用者列出的**」，而裡面大半是內建的列。
兩句都是送給模型的話。現在照實分四段：

| 段 | 放什麼 |
|---|---|
| 依紀錄讀得到 | 紀錄或探測是「讀得到」|
| 還沒有紀錄 | 沒有紀錄，一般而言也不是要登入的 |
| 多半要登入 | 紀錄說要登入；**或**沒有紀錄而 `expected` 是要登入／看單篇（v0.20.0 沒用到這一欄）|
| 主程式抓不到 | 紀錄是 robots 不准、要跑 JavaScript、連不到、常被限流 |

同一類裡有紀錄的排在沒有紀錄的前面。

### 三、編輯一列預設關著的入口，會把它打開

編輯表單不送 `enabled`，而 `saveSource` 在沒帶的時候最後一段是無條件的 `true`。
改個備註，dblp 就被打開、進了提示詞。現在沒帶就是「不改」，退到那一列的預設值。

### 四、內建的列按「刪除」，畫面說「只會關掉」，然後什麼都沒關

v0.20.0 對內建的列只跳一句話就結束。現在先問「刪不掉、只會關掉，要關掉嗎？」，確認之後真的關掉
（後端 `removeSource` 本來就是這麼做的）；已經關著的就直說。

### 兩處過期的事實（`catalog.ts` 的備註與 `expected`）

- **ACSAC 2024 起是 IEEE**：acsac.org 的 2024 論文集連結轉到 IEEE 的 DOI。v0.20.0 寫在 ACM 那一列。
- **ACM 從 2026-01-01 起全部開放取用**：`dl.acm.org` 的 `expected` 從「要訂閱」改成「開放」——
  那個值從這一版起會決定沒有紀錄的列落在提示詞的哪一段。**依據是 B 級**：ACM 的頁面對自動化存取回 403。
  那個 403 會被 `fetcher.ts` 記成「要登入」—— 方向安全、說法不對，也寫進 Q7。
- NVD 的「每 30 秒 5 次」是憑記憶寫的，原文在 JS 渲染的頁上取不到，**拿掉數字**。

查證的過程與級別在 `research/security-sources.md` 的「更正」與 `research/query-log.md`。

### 兩處沒回寫的文件

- **`ui-workflows.md` 從來沒有「來源網站」這一節**（v0.7.0 起就少），而 v0.20.0 重排了那一頁、
  `security-sources.md` 還引用了它。現在補上：兩條軸、編輯與刪除、預設關著的兩列、怎麼進提示詞、已知的洞。

### 測試

新檔 `tests/application/source-defaults.test.ts`（6 條）：預設關著的只有那兩列、它們沒有探針、

## v0.19.0 —— 2026-09-13　被限流時退避重試，不再整批停；骨架對齊 D:\Projects

**不是新的 Stage。** 這一版對齊 `D:\Projects` 的共同慣例（四個專案同一天做），
而這個專案有一件不只是搬檔案的事：**擷取紀律裡的數字，從規則搬回設定值**（CONVENTIONS §17、ADR-0031）。

### 被限流之後：這個網站退避，其他網站照跑

以前對方回 429／503 就**整批**停、不重試、不看 `Retry-After`。那段話是 agent 替人做調查時的姿態，
被抄成了產品的正確性條件 —— 而一批網址常常跨很多網站，一個網站限流就讓整批作廢
（2026-09-08「檢查全部」實際踩過：Semantic Scholar 回 429，後面三個來源一個都沒被檢查）。

現在：讀 `Retry-After`（秒數或 HTTP-date，讀不出來當沒有）→ 照它等，沒有就 5 秒、15 秒 →
同一個網址最多再試兩次 → 還是不行就記 `FETCH_RATE_LIMITED`（可重排），**那個網站這一輪不再碰**
（之後排到它的項目不送請求；**轉址的每一跳都查**，短網址繞不過去）→ **其他網站照跑**。
`Crawler.stop()` 從此只代表使用者取消，退避中按取消每 250 毫秒就聽得到。
`robots.txt` 本身被限流也走同一條路，而且那個結果**不進快取**（進了的話退避重試就是假的）。

LLM 端點（OpenAI 相容）的 429 改成 SDK 式退避：照 OpenAI 官方 Node SDK 的形狀
（2026-09-13 對照原始碼：預設重試兩次、0.5 秒 × 2ⁿ），`Retry-After` 太長時放棄而不是改用自己的退避。
逾時是整次呼叫的預算，含退避的等待。

### 第一條收尾條件是 🟡，而那改變了設計

收尾條件寫「**動手前先量**目標端點的 `json_schema` 支援程度」。
**這台機器上沒有任何線上服務的金鑰**，所以一個線上端點都沒量 ——
量到的是唯一一個 OpenAI 相容端點：本機 Ollama 0.33.2 的 `/v1`。

**量不到使用者會接的那一個端點，程式就不能帶一張「哪家支援什麼」的表。**
所以支援度改成**每個「端點＋模型」各量一次**，帶著時間存在
`%LOCALAPPDATA%\Cyclosa\provider-checks.json`。沒量過就在第一次真的跑任務之前量；
設定頁的「實際打一次」會重量。有金鑰的人要事先量，用

量測題目設計成**只有照做才答得出來**：一份模型不可能自己猜到的 schema

`chat-ollama.ts` 的檔頭寫著「OpenAI 相容那條路的 `response_format` **只到 `json_object`**」，

6/6 符合，對照組 0/6 是 JSON。roadmap 早就警告過那句話「是一個實測結果，不是一條通則」——

**`/v1` 送不了 `think: false`**。同一題 `qwen3.5:4b` 走 `/v1` 是 4.1 秒、2,935 字的思考，

### 第二半比第一半糟：它會悄悄建一個空資料庫

**從一個唯讀的畫面裡。**

所以 `openCaseDatabase` 現在**預設不建檔**，要建的那一條（建立專題）明確說
`create: true`。兩個型別重載把「`create: true` 不會回 `missing`」交給編譯器，
建立專題那一條就不用寫一個永遠走不到的分支。

> 反過來的預設（「預設會建，要擋的人自己說」）會讓每一個新呼叫端都繼承那個副作用，

| `#161a21` | `--bg-panel: #171a21`（差一個位元組）|
| `#232833` | `--bg-hover: #252a35` |

症狀是九張已提交的 SVG 全部用一組這個 app 不再使用的顏色畫成，
**而沒有任何東西會說** —— 色碼是合法的顏色，圖看起來也很正常。
那兩個差一個位元組的更不可能用眼睛發現。

### 過期檢查本來抓不到這件事

`manifest.json` 只雜湊**每一段 mermaid 原始碼**，不雜湊配色檔 ——
所以改完 `mermaid-config.json` 之後 `-Check` 照樣回「所有圖都是最新的」。
**一張用錯顏色的圖跟一張用對顏色的圖，在過期檢查上長得一模一樣。**

現在 manifest 多一個 `theme` 欄位（配色檔的 SHA-256），對不上就整批重算。
行尾先正規化再雜湊 —— 否則同一份設定在兩台機器上會得到兩個 hash。

### 守門

`tests/guards/diagram-colors.test.ts` 驗**包含關係**：宣告的每個色碼都要在
`tokens.css` 裡存在。**不驗哪個 token 對應到哪個 `themeVariable`** ——
那是設計判斷，而且 mermaid 的 primary／secondary／tertiary 跟這個 app 的

## v0.17.1 —— 2026-09-11　版面自適應

使用者回報「有些地方沒有自適應長寬」。用無頭瀏覽器量過
**5 個頁面 × 8 種長寬**（含直立的 900×1440、768×1024）之後找到三件事。

### 捲動與行長寫在同一個元素上

```css
.settings {
  overflow-y: auto;     /* 我是捲動容器 */
  max-width: 760px;     /* 我也是行長限制 */
  margin-inline: auto;  /* 我還負責置中 */
}
```

**`margin-inline: auto` 會把 flex 子項的 `stretch` 取消掉** ——
它不再是「填滿再置中」，而是「由內容決定寬度」。
量出來：模型分頁 760px、來源網站分頁 785px，**同一頁的寬度跟著內容跳**，
而捲軸也跟著跑到畫面中間、右邊留一大片空白。

拆成兩層：外層填滿並捲動（捲軸回到視窗邊緣），內層負責行長與置中。

### 頂列沒有任何縮排控制

flex 子項預設 `min-width: auto`，所以**一個長專題名會把「設定」與
「結束 Cyclosa」推出畫面** —— 而那兩顆是那一列上最不能不見的
（一個是出口，一個是關機）。

現在每一格 `flex: none`，只有專題名可縮並加刪節號。
結束鍵加 `white-space: nowrap`（768px 寬時它原本會換成兩行、
變得比 44px 的頂列還高）。

### 一張永遠塞不進去的表

各任務模型那張表四欄的最小寬度加起來 728px，而那一頁的內容寬只有 712px ——
**它在任何視窗寬度下都塞不進去**，症狀是整個設定頁固定橫向溢出 31px。

包一個橫捲容器，並把那一欄的 `max-width` 從 34ch 收到 26ch，
讓它在常見寬度下根本不用捲。

### 驗證與守門

修之前設定頁在每一個寬度都溢出 31px；**修之後 40 種組合全過**
（判準：整頁不橫捲、沒有元素右緣超出視窗、結束鍵的右緣在畫面內）。

新增 `tests/guards/layout-responsive.test.ts`，守的是**寫法**不是數字：
捲動容器不要同時負責行長、頂列只有名稱可縮、寬表格要有自己的捲動容器。
**那條規則對現況是零命中**，而零命中跟規則壞掉長得一樣 ——
所以測試裡把修掉的那個寫法原封不動餵回去，確認判準認得出來。

量測的做法寫進發版檢查表的 **D10**。

> **截圖不是量測。** 截圖會被視窗邊緣裁掉，而「被裁掉」跟「真的溢出」
> 在圖上長得一模一樣 —— 一開始差點照著截圖去改關聯圖左欄的內距，
> 而那裡量出來根本沒有問題。

## v0.17.0 —— 2026-09-11　範例專案（Stage 15 收尾）

第一次啟動之後，清單上有一份**範例專案**。

### 它是什麼

八條中華民國法律的**條文原文**（著作權法六條、政府資訊公開法兩條），
六個實體、十二條關聯 —— 其中八條待查證，可以直接拿來裁決。
專題的問題是「一份政府公開的資料，我可以重製、改寫、再散布嗎？」，
也就是**這個專案自己在做這一件事時問過的問題**。

**每一份都指得回它自己那一條的網址**（`…&flno=9`），不是整部法規的。
語料走真的匯入管線 —— 寫快照、抽正文、寫全文索引 ——
所以閱讀器讀得到、中文兩個字搜尋得到。
唯一沒走的是向量：那需要嵌入模型，而**第一次啟動不該打網路**。

### 授權是查過的，而查的結果改掉了做法

兩個獨立的依據都成立：**著作權法第 9 條**（憲法、法律、命令或公文
**不得為著作權之標的**）與**政府資料開放授權條款第 1 版**
（無償、可再授權、不限時間地域、**不會嗣後撤回**，義務是註明出處）。

> **`law.moj.gov.tw/robots.txt` 是 `Disallow: /`** —— 整個站不准爬。
> 而 Cyclosa 自己就有一個會讀 robots.txt 並照做的爬蟲
> （`FETCH_ROBOTS_BLOCKED` 就是為它存在的）——
> **用爬來的語料當它的範例專案，方向剛好是反的。**
>
> 所以改走 data.gov.tw 上公告的**官方大量下載端點**。
> 教訓寫成一句順序：**先問「這個站有沒有給一條正式的路」，沒有再問能不能爬。**

完整查證在 `research/sample-corpus-licence.md`，
查詢紀錄在 `research/query-log.md`。

### 引文的位置是產生器自己找的

語料檔裡只寫 `quote`，**不寫字元位置** —— 位置由產生器在抽出來的正文裡找
（ADR-0021 那條「模型給的位置一律不採信」的同一個判準）。
`derived/` 可以整批重算，而重算之後字元位移會平移；
寫死的位置會產生一種特別糟的錯：**每一條看起來都完整，而區間指到別的地方。**

測試照 Stage 11 匯出時的做法驗一次：**拿區間去切正文，切出來的必須一字不差。**

> 語料檔的組裝腳本當場抓到兩個錯：`cr52 → cr64` 與 `cr44 → cr64` 這兩條
> 「受限於」的出處**不在來源那一份上**，在 `cr64` 的條文裡（是 §64 列舉了 §52）。
> 所以語料格式多了一個 `evidenceFrom` —— **出處不必長在邊的來源節點上。**

### 「刪掉之後不會自己回來」沒有用到旗標

收尾條件原本寫「一個旗標記住使用者刪過了」，而實作時發現
**「資料根存不存在」已經是那個旗標**：放範例只發生在資料根是這一次
才建出來的時候。刪掉重啟不會回來、搬資料根也不會，
而整個 `%LOCALAPPDATA%\Cyclosa` 被清掉時它該回來 —— 那是一次全新安裝。

**一個少一份狀態的設計比一個記得住狀態的設計好** ——
後者多出一種「旗標與現實對不上」的壞法，而那種壞法沒有症狀。

設定頁的「資料位置」分頁多一顆**重建範例專案**，
旁邊寫著「標成已確認的關聯是示範資料，不是任何人真的裁決過的紀錄」。

**測試 828 → 841。**

## v0.16.0 —— 2026-09-11　開箱即用（Stage 15 的前兩件）

**這一版動的三個東西裡，有兩個是查下去才發現的真缺陷。**

### 第一次啟動不問任何問題

指標檔不存在時自動建 `%LOCALAPPDATA%\Cyclosa\data`，五個頂層資料夾一起建好。
設定頁多一個「資料位置」分頁：**先告訴你它在哪**（連同指標檔的位置），
其次才是換一個地方 —— 方便的代價不該是「我不知道我的東西在哪個資料夾」。

換位置會**把既有的東西一起搬過去**。只重指指標檔的話，使用者按下確定
之後會看到一個空的清單，而他的專題還在舊資料夾裡 ——
那正是 REQ-0001 要擋的畫面，只是換成我們自己造的。

> **只有「指標檔不存在」走自動建立**，另外三種失敗一律照原樣回。
> 指標檔指到 `E:\…` 而隨身碟沒插的時候自動頂替一個空資料夾，
> 使用者會看到一個乾淨的空清單、一個字都沒說 ——
> 而他上一次關掉程式的時候那裡有 20 個專題。
> `tests/e2e/case-flow.test.ts` 有一條專門守這個邊的測試。

搬家的守門：有作業在跑就擋（會把 `case.sqlite` 從一個正在寫它的行程底下抽走）、
目標不能是現在這個／現在這個的子孫／已經有東西的資料夾。
**搬完才寫指標檔** —— 失敗時舊的地方原封不動。

### 刪除專題，以及終於接上按鈕的封存

刪除要求**逐字打對專題名稱**，而那個比對在伺服器端。按之前看得到會失去什麼
（幾份資料／幾則筆記／幾個實體／幾條關聯）與**整個資料夾佔幾 MB**（含 `sources\`）。

**刪除是「搬」不是「刪」**：資料夾搬進 `backups\deleted-<slug>-<時間戳>\`。
同磁碟區的 `rename` 是瞬間的、不多佔一份空間 —— 而**磁碟空間也因此不會變多**，
那句話印在對話框上。

> **`backups\` 到底是不是回收桶，兩份文件原本說法相反。** REQ-0001 寫
> 「備份是 `backups\` 的事」，`storage-layout.md` 寫它「不是回收桶」。
> 挑了 REQ-0001，並把 `storage-layout.md` 改成那句話真正想擋的事：
> **app 永遠不讀那個資料夾** —— 沒有清單、沒有還原鍵。那裡是留給檔案總管的。
>
> 曾經考慮過的「只備份 `case.sqlite`」被否決了：那會得到一份
> **圖還在、而每一條引文都驗不回去**的東西（`sources\` 的快照不在資料庫裡）。
> 一個名字叫備份、而內容缺了證據的檔案，比沒有備份更糟。

### 兩個查下去才發現的真缺陷

封存的 API 從 Stage 5 就在，而**在這一版之前零個呼叫點**。一接上按鈕就撞到兩件事：

1. **`新建` 狀態封存不了** —— 轉移表上只有 `已就緒 → 已封存`，
   於是一個建了才發現不需要的專題**只剩下刪除這一條路**。補了 `新建 → 已封存`。
2. **被強制關掉的專題永遠卡在 `蒐集中`**，而 `蒐集中` 封存不了 ——
   也就是一個**永遠封存不了、也說不出為什麼**的專題。

第二個是 v0.14.0 那次修復漏掉的另一半：那一次修的是 `run.status`，
而**專題狀態是另一個欄位、另一條路**。更糟的是正常關閉會把作業寫成 `已取消`，
於是孤兒掃描找不到東西可掃、直接早退 —— **那條修好的路反而繞過了這個修復。**
`run-sweep.ts` 現在在掃完之後把卡住的 `蒐集中` 放回 `已就緒`。

還有一個**會說謊的錯誤碼**：狀態轉移不合法時一律回 `CASE_ARCHIVED`，
所以「作業還在跑的時候按封存」會得到「這個專題已封存」—— 而它明明沒有。
拆成 `CASE_ARCHIVED`（真的已封存）與 `CASE_STATUS_INVALID`（其餘）。

### 順帶更正兩處文件

`api-contract.md` 的專題端點表寫著 `POST /api/cases/:id/archive ／ /reopen`
（實作一直是一支 `/status` 帶 `action`），以及 **`POST /api/cases/open`
—— 那一支從來沒有被實作過**。後者正是 ADR-0001 寫下來要防的東西：
一份用權威語氣描述了不存在世界的文件。

`--ui-danger` 的宣告意思原本是「真的壞掉的東西 …… 它留給失敗」，
而刪除鍵不是失敗。改成「失敗，以及按下去就回不來的動作」——
**那份說明分頁的意義就是它得跟畫面一致**（v0.15.0 才剛為此建了守門測試）。

## v0.14.0 —— 2026-09-10　關閉這件事，從頭到尾

從一個問題開始：「當前如何正常開啟與關閉專案？」把那條線畫出來之後
找到三個缺口，而**三個都落在兩份文件的交界處** —— 生命週期原本散在
ADR-0020、ADR-0025、README 的指令表與 `Launch.ps1` 的註解，四份各自都對，
而沒有一份的範圍涵蓋「結束」與「進度通道」的交界。

新增 `docs/architecture/app-lifecycle.md`：那個範圍現在有一份文件。

### 一、「結束 Cyclosa」在你正看著一個執行中的作業時關不掉

進度通道走 `reply.hijack()`，而 Fastify 的 `forceCloseConnections` 預設是
`'idle'` —— **收得掉閒置連線，收不掉進行中的請求**。用本專案自己的 fastify
實測：閒置 keep-alive 的 `close()` 1 ms resolve，開著的 hijack SSE
**3000 ms 還沒 resolve**。於是掛在它後面的 `process.exit(0)` 永遠不跑，
而畫面已經顯示「Cyclosa 已經關掉了」。

**這正是二次確認對話框在講的那個情境**（有 N 個作業在跑）。

修法：關閉序列抽成 `interface/http/shutdown.ts` 的一個**不碰 process 的函式** ——
叫作業停 → 等回應送出去 → 有上限地等收尾 → **收掉所有連線** → `close()`
也有上限，逾時直接離開。**一個關不掉的結束鍵比沒有結束鍵糟。**

測試抓不到是有原因的：`app.inject` 不開真的 socket，而 `force: true` 那條路
一條測試都沒有（它會 `process.exit`）。新的測試開一條**真的** hijack 連線，
拿掉收連線那一步會紅 —— 注入驗過。

### 二、被關掉的作業永遠停在「執行中」

關閉不碰記憶體裡的執行表，資料庫那一列還是 `running`。兩個症狀都不像 bug：
徽章永遠寫「執行中」而且**沒有取消鍵**（那顆按鈕問的是記憶體）、
`hasRunningRun()` 讓**之後每一次搜尋**都掛一句「有作業還在跑」。

兩層修法：關閉時先取消（走既有的取消路徑，語意與 ADR-0023 一致）、
啟動後第一次打開某個專題時掃掉孤兒。加一欄 `run.ended_reason`（schema v8）
分辨三種「已取消」——**沒有新增第七個狀態**。

> **第一版連 `排隊中` 一起掃，而那是錯的。** 擴展的「排隊」的意思是
> **「在等你勾」**，那個狀態撐得過重新啟動（`chooseAngles` 只看資料庫）。
> 一條既有的 e2e 當場變紅 —— 而且那個錯誤不只在重啟時發作，
> 它在同一個行程裡就會把使用者還沒回答的問題丟掉。

### 三、五條啟動路徑只有一條擋得住第二個實例

判斷「已經在跑」的依據只在 `Launch.ps1` 裡。`npm start` 撞埠得到的是一段
`EADDRINUSE` 堆疊 —— 而公開之後那是別人最可能打的指令。

現在 `main.ts` 的 `listen` 失敗時會先問 `/healthz`：是自己就印出網址並
`exit 0`，不是就說清楚是別的程式佔用。**`Launch.ps1` 那一份保留** ——
它要在啟動**之前**就決定要不要開瀏覽器。

> `tagcor-ledger` 的守門在 `main.py` 裡而不是啟動器裡，所以不管怎麼啟動都成立。
> **位置比機制重要。**

### 實際跑一次才看到的一句錯話

端對端驗收（真的作業 ＋ 真的 SSE ＋ 真的按結束）通過之後，**訊息本身是錯的**：
按了結束、作業卡在一次抓取的節流裡沒趕上收尾、於是被下一次的掃描標成 `stale` ——
而那句話寫的是「上一次**沒有正常關閉**」。**我明明正常關閉了。**

掃描能知道的只有「上一次結束時它還沒收尾」，**分不出**那次結束是按了結束鍵
還是被強制結束的。改成「上一次結束的時候，這次作業還沒跑完」。

> 這是 `lessons.md` 那條「**一個下界長得跟一個實際值一模一樣**」的第五次 ——
> 把一個「不知道」壓成一個看起來確定的說法。這一次它出現在一句給人看的話裡。

### 測試

**54 檔 / 788 個測試**（v0.13.0 是 52 / 775）。

**另外實際跑了一次**：真的作業（6 個同網域網址、每個回應 2 秒 ＋ 3 秒節流）、
真的 SSE 連線開著、`activeRuns = 1` 的時候按結束 —— **1,851 ms 之後 server 不再回應**。
重開之後那一列是 `已取消 / stale`，搜尋不再掛「有作業還在跑」，
而**先前寫進去的那一份資料還在**（ADR-0023）。

## v0.13.0 —— 2026-09-10　Stage 14：每一件事各挑一個模型

**設定頁的「模型」分頁分成兩段。**

| 段 | 回答什麼 |
|---|---|
| **可調用模型** | 每個角色連到哪裡、目前有哪些模型可以用、金鑰讀不讀得到 |
| **各任務模型** | 一張四列的表，**每一件事各自跑哪一個** |

在這之前逐任務覆寫**只在 `chat` 那一區底下**，於是「找來源」與「嵌入」
永遠不會出現在它旁邊 —— 而使用者問的是「我能不能替每一件事各挑一個模型」，
那需要一份完整清單。

### 跟著改的四件

- **`agent` 多一個模型欄位**，走 CLI 的 `--model`。
  **空字串 ＝ 不帶這個旗標**，用 CLI 自己的預設 —— 那是一個有效的選擇，
  不是沒設定。在這之前「找來源」根本沒有模型欄位。
- **`chatReadiness` → `taskReadiness`**，涵蓋四個任務，每一列帶 `role`。
  角色層那一格仍然是它底下所有任務的合併。
- **沒設定的角色不再宣稱缺什麼。** 一個完全沒設定的角色能力宣告當然全空，
  所以配對一定回「缺 X」—— 而畫面上那句是「這個角色要跑的任務需要 X，
  **而目前設定的模型沒有**」。那句話對它是錯的：問題不是模型不夠好，是還沒選。
  這是既有行為，而擴成四列之後**四列會同時說同一句錯話**。
- **金鑰讀不到的時候，畫面說得出怎麼設。** 填的仍然只有**環境變數的名字**
  （金鑰不進任何一個檔，2026-09-08 的決定沒有變）——
  但讀不到時多一段可以整行複製的 `setx`、一句「要重開才讀得到」、
  以及一顆「我設好了，重新偵測」。**最常見的原因不是打錯字，是沒有重開**：
  環境變數是行程啟動時繼承的一份拷貝。

## v0.12.0 —— 2026-09-10　Stage 13：把六項預算量出來，而四項沒過

**這一版最重要的產出是四個「沒過」，不是兩個修好的東西。**

語料：`tools/dev/seed-scale.ts` 產生 5 萬資料節點 ＋ 1.2 萬實體 ＋ 20 萬關聯、
6,993 萬字、3,221 萬列 bigram、18.5 萬條向量。種子固定，**同一個種子產生同一份語料**。

| 預算 | 目標 | 修之前 | 修之後 | |
|---|---:|---:|---:|:--:|
| 子圖查詢 `hops≤2` | 200 ms | 1,484 ms | 583 ms | ❌ |
| 節點預算估算 | 50 ms | 4,566 ms | 937 ms | ❌ |
| 全文檢索（中文 2 字詞）| 300 ms | 61 ms | 42 ms | ✅ |
| 語意檢索（5 萬筆）| 500 ms | 48,456 ms | 2,176 ms | ❌ |
| 2k／8k 節點 fps | ≥ 30 | —— | 待人工 | ⬜ |

完整條件與拆解在 `environment/performance.md`。

### 兩個真的缺陷，修掉了

**一 · 向量表少一個索引（schema v7）。** `listVectors` 是游標分頁，
而 `(model, dim)` 這個索引滿足得了篩選、滿足不了 `ORDER BY id` ——
查詢計畫是 `USE TEMP B-TREE FOR ORDER BY`，**每取 2000 列就把 18 萬列排一次序**，
而 10 KB 的 BLOB 跟著流過那個排序，做 93 次。補上 `(model, dim, id)`：
一批 554 ms → 20 ms，全掃 **48,456 ms → 2,176 ms**。

**它不會有任何症狀。** 小專題上兩者都是幾毫秒，測試全綠，功能完全正確。

**二 · 圖走訪沒有上界。** 超過 8,000 個節點的子圖一律回 413，
所以走到 5.4 萬個節點是白走的。加上界之後 **4,566 → 317 ms**。

而**第一版的上界量出來幾乎沒有用**：它放在跳與跳之間，而中位數度數的焦點
第 2 跳結束時只有 1,922 個節點（遠低於 8,000），第 3 跳一口氣帶進 3.2 萬個 ——
**爆炸在一跳之內，跳間檢查看不到。** 改成跳內每 400 個檢查一次。

回報的數字因此變成**下界**，所以 `HopCounts` 多一欄 `capped`，畫面上顯示 `16272+`。
**這一半比效能那一半重要**：只做效能的話，數字達標而畫面開始說謊。

### 兩個是實際極限，沒修

**語意檢索**：2560 維每條 10 KB，5 萬筆文件**連每份只留一段（5 萬條）都要 840 ms**。
段數這個旋鈕轉到底都沒有用 —— 這回答了 ADR-0026 留下的問題，
也讓 ADR-0009 那條「超過 5 萬筆重新評估」成立。處方照 ADR-0009 自己預先寫下的：
**純 JS 的近似最近鄰，不引原生擴充** —— 那是另一個階段。**ADR-0028。**

**子圖 2 跳**：1,922 個節點 ＋ 7,703 條線本身就要 500 ms
（`traverse` 215、`loadEdgesAmong` 115、`mentionCounts` 101）。
沒有一段是壞掉的查詢計畫。**ADR-0029。**

新增 `score-quotes.ts`（**不需要 GPU**：引文原文存在結果檔裡）。150 條真實引文：

| 放寬什麼 | `qwen3.5:4b` |
|---|---|
| 嚴格 | 73% |
| ＋全形半形標點 | **73%（0 條）** |
| ＋**CJK 旁邊的空白** | **98%（10 條）** |

模型寫「中本聰在 2008 年」，原文是「中本聰在2008年」——
中文排版有「中英文之間加空格」的慣例，而字完全一樣。
**不整個刪空白**（拉丁文的空格有意義），測試釘著 `the rapist` 對 `therapist`。

> **標點那一項是我修錯的地方。** 看到兩條引文差在標點就去做了標點正規化，
> 而那兩條同時也差空格 —— **我沒有把變因分開。**

### 五 · 兩個被思考灌水的數字

- `prompt_eval_count` 在思考開著時**把思考的 token 也算進去**。

## v0.10.4 —— 2026-09-09　受限解碼守的是形狀，不是長度

**v0.10.3 留了一個「成因不明」，這一版把它挖出來了。** 那一版寫著
「一次 55,467 個字元的非 JSON —— `format` 帶了整份 schema，而受限解碼沒有守住」。

成因是 **`EXTRACT_SCHEMA` 的兩個陣列沒有 `maxItems`**。
受限解碼保證的是形狀，而**沒有上界的陣列在任何長度都是合法形狀** ——
文法從來沒有被要求管長度。

而 `normalizeExtraction` 一直都有上限（實體 20、關係 20、名稱 80 字、
關係詞 40 字、引文 500 字），**只是那些丟棄發生在模型生完之後**。
機械上的原因只有四個字：`MAX_ANGLES` 是 `export` 的，所以 `ANGLES_SCHEMA`
一直帶著 `maxItems`、**角度那一步從來沒失控過**；`MAX_ENTITIES` 那幾個是私有的。

同一個模型、同一份正文、同一個 `num_ctx`，冷啟動各兩次：

| schema | 輸出 token | 視窗用掉 | `done_reason` | 秒 | 結果 |
|---|---|---|---|---|---|
| 沒有上界 | 11,474 | **101%** | `length` | 97.0 / 92.6 | 24,930 字非 JSON |
| 有上界 | **1,627** | 46% | `stop` | **16.4 / 16.4** | 20 實體、20 關係 |

### 二 · `num_ctx` 取了門檻，而門檻不是視窗

v0.10.3 的 `0c37ced` 把 `num_ctx` 設成 `REQUIRED_CONTEXT_TOKENS`＝18,000，
而那是**閘門的門檻**。這台機器上 Ollama 的預設是 32768 ——
**那個改動實際上把視窗縮小了**，再配上沒有上界的 schema，
就是上表裡那個 101%。門檻回答「夠不夠格」，視窗回答「這次配置多大」，
把後者設成前者等於把餘裕設成零。

現在是 **24,000**：15,000（輸入上界 ＝ 12,000 字 × 最壞的 1.2 token／字元 ＋ 提示）
＋ 8,000（輸出預算，約實測 1,627 的五倍）。兩側的取法不同是刻意的 ——
**輸入超過會安靜截斷，輸出超過看得見**（空回應 ＋ `done_reason=length`）。

### 三 · 一個寫錯的觀察擴散到了四個檔

v0.10.3 記「`/api/tags` 對 `gemma4:31b` 回 `context_length: 262144`」。
**那是 `nemotron-cascade-2:30b` 的。** `gemma4:31b` 與 `translategemma:12b`
**根本沒有那一欄** —— 宣告是 0，而 0 是「不知道」，閘門直接放行。

錯誤來自沒有回去看 `/api/tags` 的原始回應，然後它被抄進了
`capabilities.ts`、`chat-ollama.ts`、守門測試與 ADR-0006。四處都改了。

### 四 · 「0 個字元」這句話把兩件事講成同一件

受限解碼撞到視窗上緣時，Ollama 回的是空字串加 `done_reason: "length"`。
原本 `PROVIDER_OUTPUT_UNPARSEABLE` 的 `detail` 只寫「0 個字元」，
那聽起來像模型壞了，其實是**我們送進去的加上它要吐的塞不下** ——
下一步完全不同。現在把 provider 自己說的理由帶出去。

### 五 · 量測工具本身的三個修正

**v0.10.3 那張表的秒數不能再用**，理由都在這裡：

- `eval-chat.ts` **沒有送 `num_ctx`**，而出貨的送了 —— 量測與出貨跑在不同設定上
- **三次重複送同一份正文**，於是第二、三次大量命中 KV 快取。
  實測後果：同一個請求連跑三次，`prompt_eval_count` 是 13,296 / 10,186 / 6,702，
  輸出在溫度 0 之下也跟著變。**那不是三個樣本。** 改成每次換一篇
- 新增 `score-chat.ts`：記分線從出貨的 `CHAT_TIMEOUT_MS` **import**，不再手算；
  而且**逾時與吐不出東西分開數**（處方相反）
- 新增 `probe-num-ctx.ts`：每次量測前把模型卸掉（冷啟動），
  並帶 `--unbounded` 讓「加上界比較好」這句話**可以被反駁**

## v0.10.3 —— 2026-09-09　`chat` 角色的第一輪實測

**這一版沒有出貨的程式改動。** 量了一件從來沒被驗證過的宣告。

`capabilitiesOf` 對**每一個** Ollama 模型都回 `json_schema: true`，
而 ADR-0006 的閘門就是靠它決定要不要停手。四個本機模型、兩個任務、各三次，

### 一 · 兩個模型的 `json_schema: true` 是錯的

| 模型 | 角度 | **抽取** |
|---|---|---|
| `translategemma:12b` | 3/3 | **5/6** |
| `gemma4:31b` | 3/3 | 3/6 |
| `olmo-3:32b-think` | 2/3 | **0/6**（每次 278–292 秒）|

> **這一段當時給的解釋（「受限解碼在 `nemotron_h_moe` 架構上沒有被完整支援」）是錯的。**
> v0.10.5 量到：送 `think: false` 之後同一支探針 200–2000 字全部正常，
> 抽取從 0/6 變成 6/6。斷掉的是思考。

### 二 · 我為引文命中率設計的那個風險沒有發生

引文命中率跨全部模型是 **49/50**，兩個主要候選都是 100%。**模型不會捏造引文。**
真正的失敗模式是**根本沒有輸出** —— 逾時、空回應、或者一次 55,467 字的非 JSON
（`format` 帶了整份 schema，而受限解碼沒有守住）。

**如果只量了引文命中率一欄，四個模型會全部拿到 86–100% 的漂亮分數，
然後我們會選一個六次裡有四次交不出東西的模型。**

### 三 · 12B 打贏三個 30B，而沒有一個模型兩件事都好

`nemotron` 的角度最不重複（相似度 0.689）而抽取完全不能用；
`translategemma` 抽取最可靠而角度最重複（0.802）。
**「`chat` 底下留逐任務覆寫欄位」那個建議，量完之後不是選配，是必要條件。**

### 四 · 一個結論被自己的探針推翻

第一版寫「`translategemma` 的 `seeds` 一個都沒對」（評測那輪 0/18）。
換一組素材標題重跑，同一個模型吐出 `[3] [] [] [0] [2] [4]` —— 三個是對的。
結論因此改成**「這一欄四個都不能信，而且同一個模型換個輸入就變一種樣子」**。
兩支探針（`probe-schema-limit.ts`、`probe-angle-seeds.ts`）留在 repo 裡當證據。

### 結論

**本機這四個都不夠好，所以這一版不訂 `chat` 的預設模型。**
完整設計與數字在 `docs/research/chat-choice.md`。

## v0.10.2 —— 2026-09-09　補上抽取的能力閘門，以及嵌入模型的設定欄位

使用者問「四項任務會建議各自有一個負責的模型嗎」「有設定模型的分頁嗎」。
查的時候發現任務其實有**五**項，而其中一項不在任何檢查範圍內。

### 一 · `chat` 底下有兩個任務，而只有一個有閘門

ADR-0006 第 3 條是這個專案對 provider 最重要的規則 ——「配不上就停手，不靜默降級」。
`TASK_ANGLES` 有閘門、`TASK_FIND_SOURCES` 有閘門，
而**「從抓回來的正文抽實體與關係」連 `TaskRequirement` 都沒有**。

失效的方式是靜默的：一個 8000 context 的模型會通過角度那一關、抓完全部網址，
然後在每一份文件上把 12,000 字的正文截掉一半 ——
**抽出來的關聯照樣帶引文、照樣進待查證，畫面上看不出任何異常。**

補上 `TASK_EXTRACT`（`json_schema` ＋ 18000 context），閘門放在勾選那一步
（**抓之前**）。設定頁的 `chat` 準備度也改成兩個任務都要過。

**那個 18000 是量出來的。** 12,000 字元不等於 12,000 token，
而差多少取決於 tokenizer：同一段中文在 Gemma 是 8,048、Nemotron 是 11,185、
**OLMo 是 14,383 —— 差 1.8 倍**。門檻取最壞的那一個再加提示詞與輸出。

### 二 · context 不夠時，畫面上原本顯示「缺少：（空白）」

`missingFor` 早就會回「旗標齊了、只是 context 不夠」（`flags` 是空陣列、
`context` 有 `[需要, 有的]`），而**三個呼叫端都只帶 `flags` 出去**。
**它說了有問題，卻沒說是什麼問題。** 現在 `detail` 帶
`needContextTokens` 與 `haveContextTokens`。

### 三 · 設定頁補上 `embed` 的欄位

`/settings` 的「模型」分頁本來就列三個角色，但 `embed` 那一格只有標題、
沒有任何輸入欄位，說明還寫著「還沒有做」。v0.10.1 選定模型之後那句話過期了。

現在有位址、模型下拉、以及一顆「建議 `qwen3-embedding:4b`」。三件事跟另外兩個角色不同：

- **沒有金鑰欄位** —— 嵌入只接本機端點。雲端端點隨時可能換掉背後的權重，
  而那不會報錯，只會讓已經存下來的向量安靜地變爛。
- **「換掉要全部重算」那一句在選單上面。** 印在下面的話，看到的時候已經選完了。
- **那一句不給顏色**（ADR-0018 第 1 條：每個顏色一個意思）。琥珀是待查證、
  紅是真的壞掉了，而這一句兩者都不是 —— 靠字重與一條左邊界。

**綠勾的意思是「模型選好了，而且它真的在 Ollama 上」，不是「語意檢索可以用了」**，
所以欄位底下有一句明說。舊的設定檔沒有 `embed` 欄位，缺就退回預設
（位址有、模型空），不是 `null`。

### 四 · 兩條進 `lessons.md`

- **一個沒有宣告需求的任務，「配不上就停手」對它等於不存在** —— 而漏掉宣告
  沒有任何症狀。要抓這種漏，需要一條從**另一個方向**數的檢查。
- **字元不是 token，而差多少取決於哪一個 tokenizer**（實測 1.8 倍）。

43 個測試檔 / 689 個測試（本來 41 / 675）。

## v0.10.0 —— 2026-09-09　Stage 12 前半：全文檢索

**索引從 Stage 6 就一直在寫，這一版接的是查詢那一半。**
所以這裡沒有任何「建索引」的動作 —— 那正是當初把索引提前到匯入時做的理由。

### 一 · 中文兩個字查得到

那是 `trigram` 命中 0 列那個實測反例的驗收句（ADR-0009）。
關聯圖工具列最左邊多了一顆「搜尋」，開的是左欄的面板 ——
跟匯出同一個做法，理由不同：**搜尋的用途是「找到某個東西附近有什麼」**，
而那件事要看得到圖。點一筆結果，焦點就移過去。

**路由的依據換了一個**：索引依 `item.lang` 建（我們知道那份東西是什麼語言），
而查詢**依查詢字串本身**選路 —— 查的時候不知道要找的是什麼語言。
中英混合的查詢兩條路都走，而送進 FTS5 `MATCH` 的只有非 CJK 的那幾段。

### 二 · 索引找候選，**正文確認**

ADR-0009 的代價那一節寫著「bigram 會跨詞誤中，所以結果排序變得比索引本身重要」，
但沒有寫排序要靠什麼。實作時才看清楚：**索引裡沒有任何欄位分得出誤中** ——
`bigram` 表只有 gram、owner 與次數，沒有位置。
查「台積電」切出「台積」與「積電」，而一份寫著「來台積極…累積電力」的文件
**兩個 gram 都有**。

所以候選拿到之後回去讀 `derived/` 找那串字。**這跟 Stage 11 匯出時重新驗引文
是同一個判斷 —— 第四次了**（Stage 9 不採信模型給的位置、Stage 10 不採信前端送來的引文）。

驗不過的**留在清單裡並標示**，不丟掉。三種狀態，跟 Stage 11 的引文同一個形狀：

| | 意思 | 畫面上 |
|---|---|---|
| `hit` | 正文裡真的有這串字 | 摘要裡把它標起來 |
| `miss` | 正文讀得到，裡面沒有 | **「可能是誤中」** |
| `no-text` | 正文讀不到，沒驗 | 「正文不在，這一筆沒驗過」 |

合成一個布林值，就會把「正文被清掉了」說成「這一筆是誤中」。

**成本有上界**：最多 400 個候選、最多讀 60 份正文 ——
不設上界的話，搜尋的成本會跟著專題長大，而那正是 Stage 13 要量的東西。

### 三 · 量出一個索引缺口：中文頁面裡的拉丁字

`bigrams()` 只收 CJK 的連續段落，而 CJK 內容原本完全不進 FTS ——
於是一篇中文論文裡的 `Cyclosa formosana`**兩個索引都進不去**。
**那正是這個工具自己的資料長的樣子。**

「`unicode61` 會把一整段沒有空白的中文當成一個 token」對中文成立，
**對夾在裡面的拉丁字不成立**。量過三種做法（22,862 字的中文正文）：

| 做法 | 索引大小 | 查得到 `cyclosa` |
|---|---|---|
| 只有 bigram（原本）| 28 KB | **0 列** |
| 整段進 FTS | 92 KB（＋229%）| 1 列 |
| **只有非 CJK 的片段進 FTS** | **32 KB（＋14%）** | 1 列 |

選第三種。**既有的專題要跑一次 `rebuild` 才會有這些列。**

### 四 · 順手修掉一個 404 說成 500

`new DatabaseSync(path)` 對一個不存在的目錄會丟例外，
所以打錯一個 slug 拿到的是「伺服器內部錯誤」。搜尋這一支先看資料夾在不在。
**同一個問題在另外五支上也成立**（子圖、關聯、實體、匯出、點註）——
`case-service` 早就這樣擋，其餘幾支還沒有。

## v0.9.1 —— 2026-09-09　第三輪人工驗收

看畫面看出來的五件，其中兩件推翻了寫下來的決定。

### 一 · 焦點環：圓管 → 一條站著繞的緞帶

`TorusGeometry` 換成 `LatheGeometry`（長方形截面繞 Y 軸轉一圈）。
它一出生就躺在 XZ 平面上，所以原本那行 `rotation.x = -Math.PI / 2` 沒有了。

**跟選取環的差別現在是形狀，不是顏色**（ADR-0018 規則 2）：
選取環是永遠正對鏡頭的 sprite，從哪個角度看都是一圈正圓的細線；
焦點環是真的幾何，方形截面讓「它在轉」看得出來。

第一版是**躺著繞**的（截面 2.9 寬 × 1.1 厚），而正對它看是一片很寬的實心圓環，
蓋住的正好是節點四周要讀的東西。改成**站著繞**（1.1 沿半徑 × 2.2 沿軸）之後
兩個方向都在 1.1 到 2.2 之間 —— **沒有一個角度它會胖到擋路，也沒有一個角度它會消失。**

### 二 · 已讀不再是一個環（ADR-0024）

使用者看著截圖問「為什麼資料的正方體周圍有白色的環」。
**一個記號要人回頭問它是什麼意思，它就已經失敗了** —— 而查下去發現它畫錯位置：
環的中心線在半徑 4.76，方塊的側影邊緣在 4.95（正對著面）到 5.71（角對著你）之間，
所以**方塊永遠吃掉它一部分，吃掉多少還隨著轉動在變**。

改成**未讀粗體（700）、已讀正常（400）**，就是收件匣那個做法。
**粗的是未讀** —— 要跳出來的是還沒看的那些。
實體一律正常字重：它不是一份可以讀的東西。

使用者原本提的是「顏色變淡」，而那條路走不通：**明暗在這張圖上的意思是遠近**
（ADR-0018 規則 3），不透明度又拿去做一跳鄰域的提亮（0.72 ／ 1.0）——
同一個通道再擠第三個意思，就分不出「這個讀過了」與「這個比較遠」。
字重是還沒有人用的通道。

代價：**標籤不在的時候已讀就看不見了**（遠距離、或超過 300 個標籤上限）。

### 三 · 專題清單：點第二下直接進關聯圖

那是這一頁最常見的下一步，而它原本要走兩步。
**名字不再是連結** —— 一列上有兩個目的地（名字連閱讀器、列本身是選取），
按下去之前分不出會去哪一個。進閱讀器改走頂列的分頁。
「取消選取」變成操作列左邊一顆很輕的小按鈕。

### 四 · 「結束 Cyclosa」順手關掉分頁

**但不能假設關得成**：瀏覽器只允許腳本關掉「腳本自己開的」分頁，
而這一個是啟動器用網址開的。所以畫面上那句話是後路，
而且它要說出**為什麼要你自己關** —— 不然看起來像這顆按鈕沒做完事。

### 五 · 啟動器做完就退場，不再留一個黑框（ADR-0025）

使用者的原話是「我不想讓 cmd 一直在背景」，並要求參考 `webscouts` 與 `tagcor-ledger`。

**啟動器是一張檢查清單，不是一個開關。** 檢查完、等到 server 真的接受連線、
開好瀏覽器、印三行，然後 `exit 0`。server 用 `-WindowStyle Hidden`
起在自己的（隱藏的）主控台上 —— 走 ShellExecute 的不繼承啟動器的主控台，
所以啟動器可以先走。

這推翻了 ADR-0020 §3（「關掉啟動器視窗就結束」）。**前提在 v0.9.0 就變了**：
畫面上有了一顆真正的結束鍵之後，那個視窗唯一的功能就只剩「當開關」。

沒有主控台，所以 server 的輸出要有去處：`CYCLOSA_LOG_FILE` 指到
`%LOCALAPPDATA%\Cyclosa\logs\server.log`，每次啟動輪替一份 `server.prev.log`。
**放在指標檔旁邊而不是資料根底下** —— 「資料根讀不到」正是最需要看日誌的那一種故障。
`-Foreground` 留給「它為什麼開不起來」。

代價：**關掉分頁而不按結束，就會留下一個看不見的 server**（下次啟動的埠檢查認得出它）。

### 六 · 一個只在「被別人呼叫」時才出現的啟動失敗

實跑新啟動器時它停在「建置失敗」，而 `npm run build` 手動跑是成功的。
`vite build` 成功時也會往 stderr 印一段「chunk 大於 500 kB」的警告，
而 PowerShell 5.1 在輸出被導向時會把原生指令的 stderr 每一行包成 `ErrorRecord` ——
`$ErrorActionPreference = 'Stop'` 之下那是終止性錯誤。

原生指令改走 `Invoke-Native`：裡面把 `$ErrorActionPreference` 暫時放回 `Continue`，
**判準只有離開碼一個**。記進 `lessons.md`。

### 測試

`tests/shared/log.test.ts`（4 條：沒設定不寫檔、一行一個 JSON、
**檔案不是另一條規則比較鬆的路**（內容欄位一樣被遮）、寫不出去不丟例外）、
`render-rules` 的已讀字重 4 條。**640 個測試 / 39 個檔案。**

## v0.9.0 —— 2026-09-08　作業的控制與收尾

第二輪人工驗收的六件。**最大的一件是「取消」與「復原」原來是兩件事。**

### 一 · 三顆按鈕，三件事（ADR-0023）

使用者要的是「中止運行（整個回到進行前）」，而這個工具從 Stage 6 起有一條
**取消不回滾**的規則 —— 40 個網址抓到第 38 個才按取消，前面 37 份不該跟著消失。

兩者都對，因為**它們發生在不同的時刻**：取消是「別再做下去了」（跑到一半），
復原是「剛剛那一整批，當作沒發生」（跑完之後）。合成一顆按鈕，
就等於**逼使用者在按取消的那一刻決定一件他還不知道的事** —— 他還沒看過結果。

| 按鈕 | 何時 | 做什麼 |
|---|---|---|
| 暫停／繼續 | 執行中 | 停在**項與項之間**，正在做的那一項會做完 |
| 取消 | 執行中 | 不再往下做，**已寫入的保留** |
| 復原這次作業 | 跑完之後 | 刪掉這次寫的，**而你動過的一條都不動** |

**復原不碰兩樣東西 —— 跟 `POST …/rebuild` 是同一句話**：`sources\` 一個位元組都不動，
人的判定一條都不動。留下來的還有第四種，而它不是「人動過」是**一致性**：
留下來的邊的出處所在的那一份也要留 —— `edge_evidence` 有外鍵而且會連帶刪除，
刪掉它那條邊就變成**一條已確認、卻沒有任何出處的關聯**。

規則是純函式（`domain/run/undo.ts`），所以「哪些會被留下來」測得起來，
不用先跑一次真的擴展。

**暫停只活在記憶體裡**，不寫進 `run.status`：「等一下會接著跑」這個承諾
只有這個行程活著才成立，寫進資料庫會做出一個關掉程式之後恢復不了的「暫停中」。

### 二 · 頂列多一顆「結束 Cyclosa」

**在 cmd 視窗上關掉不是一個介面。** 一律二次確認，而有作業在跑的時候
那句話要說出有幾個在跑。

**那道門在伺服器端**：不帶 `force` 的呼叫什麼都不做，只回現在有幾個作業在跑。
只做在畫面上的話它是一個繞得過的提醒 —— 而這顆按鈕會讓正在跑的抓取中斷。
**沒有 `GET` 版本**，也**不掛 `beforeunload`**（關掉分頁不該關掉伺服器）。

### 三 · 單一專題的操作集中在表格上方

點一列選取，上方那一條的按鈕就亮起來。散在每一列的版本
**每加一個功能就多一欄**，而且每一列都重複一排按鈕。
沒選的時候那一條還在（按鈕是關的）—— 整條消失的話，使用者不會知道有這些操作。

### 四 · 設定頁置中，而且兩個分頁不同寬

`.settings` 有 `max-width` 卻沒有 `margin: auto`，於是在寬螢幕上整頁擠在左邊，
**而隔壁的專題清單是置中的** —— 同一個 app 的兩頁對「寬螢幕怎麼辦」給了不同答案。
順帶把「來源網站」那個分頁加寬到 1180px：它是一張表，塞在 760px 裡每一格都在換行。

### 五 · 圖例改回「實體」，焦點旁邊不寫「（紫環）」

上面三行沒有寫「（實心方塊）」「（空心方塊）」，那第四行也不該寫「（紫環）」——
**圖例的工作是把記號與名字擺在一起，不是用文字描述那個記號。**

「文獻」考慮過而且沒選：`item` 包含圖片與純文字，**一張 PNG 不是文獻** ——
那正是 glossary 當初歸掉 `document` 的同一個理由。

焦點環加粗（管徑 0.42 → 0.95）：細環在 3D 裡側看幾乎會消失，
而**一個時有時無的記號比一個大記號更難讀**。

### 六 · 來源清單上又是一堆星號，而守門測試看不到

七條，在 `catalog.ts` 的 `noteZh` 裡。**而我當天稍早才為同一個錯加過一條守門測試** ——
它寫的是「`zh-TW.ts` 裡沒有星號」，而規則本來是「會被印到畫面上的中文字串是純文字」。
**兩者不一樣，而測試守的是後者。**

那條測試現在掃一份名單，名單的判準寫在檔頭；`domain/export/pack.ts` 不在名單上，
因為它產生的是 Markdown 檔案，`**…**` 在那裡是正確的輸出。

## v0.8.1 —— 2026-09-08　人工驗收的六件

Stage 11 收尾之後使用者實際跑了一遍，六件回饋。**其中兩件查出來的東西
跟問題本身不一樣**，而那兩件才是這一版真正修掉的。

### 一 · 一鍵啟動只剩一個視窗，而那句話現在是真的

問的是「兩個視窗要不要關掉」。查下去發現的是：
`Launch.ps1` 用 `Start-Process -WindowStyle Minimized`，
而**那樣起的子程序在父程序死掉之後還活著**（實測過）。

所以畫面上那句「關掉這個視窗（或按 Enter）就會結束 Cyclosa」——
**只有按 Enter 那半是真的。** 按 X 關掉的話 server 還在跑、7433 還被佔著，
而那個視窗是最小化的，你不會注意到它。

改成 `-NoNewWindow`：子程序共用同一個主控台，關掉視窗時 Windows 會把
`CTRL_CLOSE_EVENT` 送給掛在上面的每一個程序 —— **一個視窗，兩條路都真的會結束。**

### 二 · 專題改名：名稱與資料夾一起改

「一個專題是一個資料夾。整個搬走、備份、丟給別人，都是搬那一個資料夾」
是這個工具寫在清單頁上的承諾。**只改資料庫裡的名字，那句話就不成立了** ——
資料夾會停在一個沒有人記得的舊名字上，而使用者是在檔案總管裡找它的。

順序是**先搬資料夾再改名字**：搬資料夾是唯一會因為外部原因失敗的那一步
（有東西開著它），排在前面的話失敗時什麼都還沒動。改名字那一步失敗就搬回去。

`exports\<舊 slug>\` **刻意不動**：一份已經匯出的證據包裡面寫著當時那個名字，
而那份檔案可能已經寄出去了。**舊的匯出屬於舊的名字。**

新錯誤碼 `CASE_RENAME_BLOCKED` —— 資料夾搬不動。
**不是 `IO_UNEXPECTED`**：我們知道發生了什麼事（有東西開著它），
而使用者做得到那件事（關掉再試）。

### 三 · 圖例：資料 · 筆記 · 人事物

原本是「抓回來的／你寫的／實體（空心）」。它讀起來怪的一半原因是
**詞性不一致**：前兩個是動詞短語，第三個是名詞加括號註解。

「人事物」比「實體」好懂的理由很具體：實體的六個型別
（人／組織／地點／事件／作品／概念）合起來就是那三個字。

### 四 · 焦點改用紫色的一個環（ADR-0022 推翻 ADR-0018）

使用者說「兩圈白圈太干擾閱讀」，而且要顏色不要變淡。

**先量再改。** ADR-0018 用 OKLab ΔE ×100 訂了正常視覺 ≥ 15 的硬底線，
本文重跑同一把尺（四個校準點全部吻合），掃 1071 個在色域內的候選：

> **零個通過。最好的一個只有 12.5。** 顏色預算是滿的。

所以放寬的是**比對集合，而且理由寫下來**：焦點的記號是一個**環**，
而圖上另外只有兩個環 —— 節點是實心方塊、關聯是線，**形狀本身就是第二重編碼**。
對兩個環要 ≥ 15／色盲 ≥ 10，對節點與線照樣量但不當門檻。
284 個通過，選 `#c68bff`。

**最弱的一對寫在 ADR 裡**：色盲下對資料藍只有 6.4。撐住它的是形狀與位置。

同時**兩個記號併成一個**：平面準星與傾斜環講的是同一件事，
而它們一起把標籤夾在中間。留傾斜環 ——「轉動時看到它在轉」
正是「這裡是轉動中心」這個資訊本身，平面準星給不出那個資訊。
標籤從 1.1 倍節點高度移到 2.2 倍，**那個數字被環的半徑決定**。

### 五 · 實心節點加黑色描邊

**不是為了跟背景分開**（背景本來就接近黑）—— 是為了讓方塊的稜線讀得出來。
空心實體不描邊：它本來就是線框。

### 六 · 2D 不是「差異不大」，是旋轉沒有被鎖住

問的是「2D／3D 差異不大，要不要刪掉這個切換」。**答案是不刪**（ADR-0007：
3D 只做瀏覽，精確操作必須能切 2D），但那個感覺是對的，而原因有兩個：

1. **切到 2D 之後旋轉沒關掉** —— 只把鏡頭移到正對平面，隨手一拖就又是斜的
2. 那張圖只有 4 個節點，而**一個四點的星形在 2D 與 3D 本來就長得一樣**

第一個是缺陷，修掉了（縮放與平移留著，它們不會把平面轉歪）。

### 順帶回答的一件

**根目錄的檔案數量是正常的。** 21 個追蹤檔逐個看下來，
只有 `Launch.ps1` 與 `Verify.ps1` 能搬進 `tools\` ——
其餘不是工具只認根目錄（`package.json`、四個 `tsconfig`、各家 config），
就是 `D:\Projects` 的成文慣例（README／AGENTS／CLAUDE）。
`ls` 看起來多是因為 `dist\` 與 `node_modules\` 也在那裡，而它們沒進版控。

## v0.8.0 —— 2026-09-08　Stage 11：證據包匯出

選一塊子圖按下去，得到三個檔：一份關聯與引文、一份來源清單、
**一份每條引文一列的 JSONL**。而驗收條件只有一句話：
**匯出的每條引文都能回溯到 `item` 與字元區間。**

### 一 · 引文是匯出時重新驗過的，不是抄出來的

直覺的做法是把 `edge_evidence` 那三欄（`quote`、`char_start`、`char_end`）
抄進檔案裡。**那樣做會產生一種特別糟的錯。**

`derived/` 是可以整批重算的（`POST …/rebuild`）。重算之後正文的字元位移會變 ——
抽取器改了一行、多留一個換行，整份文件後面每一個位移就全部平移。
於是抄出來的證據包裡**每一條看起來都完整（有引文、有 id、有區間），而區間指到別的地方**。
而證據包正是拿去給別人驗的那一份東西。

所以匯出時每一條都重新對一次，結果分三種：

| 結果 | 意思 | 檔案裡怎麼寫 |
|---|---|---|
| 已核對 | 那一段字現在就在記著的位置上 | 引文 ＋ id ＋ 區間 |
| 位置已移動 | 引文還在，位置變了 | **兩組數字都寫**，並說明引文一字不差 |
| 回溯不到 | 正文裡找不到，或那一份的 `derived/` 不在了 | **照樣寫出來並標明**，不省略 |

同一個判準這是第三次出現：**Stage 9 不採信模型給的字元位置，
Stage 10 不採信前端送來的引文，而這一版不採信自己資料庫裡存的位置。**
三次的理由相同 —— 一個指錯位置的引用比沒有引用更糟，因為它看起來已經驗過了。

**回溯不到的那幾條為什麼要留在檔案裡**：省略它們會讓這份檔案看起來比實際上乾淨，
而沒有任何一條測試會因此變紅。`error-codes.md` 從 Stage 5 就這樣寫著
（`EXPORT_EVIDENCE_MISSING`，級別 `notice`），這一版只是讓那句話成真。

### 二 · 匯出是唯讀的

位置變了也不去更新 `edge_evidence`，點註的 `anchor_ok` 也不重寫。
**一個會在你按下匯出時偷偷改掉紀錄的工具，它的紀錄就不再是紀錄。**
把位置對回去是 `rebuild` 的事。

### 三 · 「選一塊子圖」的意思是「你現在看到的那一塊」

所以匯出**呼叫 `graph-service` 的 `subgraph()`，不自己走一次圖**。
自己走的話會多一份遍歷實作，而兩份遍歷遲早不一致 ——
那時匯出的東西跟畫面上的對不起來，**而使用者沒有辦法發現**：兩份都看起來很正常。
代價是資料庫多開一次，換一份不會分岔的實作。

兩件跟著出來的事：

- **出處那一份不一定在選取範圍裡。** 一條兩端都是實體的邊，
  它的引文可能出自一份離焦點三跳的文件。**證據包必須自帶它**，
  否則回溯的終點會落在這份檔案外面
- **投影出來的共同提及線不匯出**（它們不在資料庫裡，沒有出處可以附），
  **而且要說出來** —— 使用者剛剛在畫面上看見它們，不說一聲就少掉會像資料掉了

### 四 · 「這一塊有幾條開放問題」不能靠數列數

四層裡**只有具名關係進人工裁決**（ADR-0015）。第一版照狀態分組，
於是一個只有一條開放問題的專題，在證據包裡看起來像有九條 ——
而那八條**永遠不會被查證**，因為它們不是主張，是機器算出來的結構。

現在具名關係按狀態分三組，其餘三層列成一張表並說明它們可以重算。
**已否決的也列出來**（只列一行、不附引文）：一份只列成立的關聯的證據包，
會讓人以為每一條都成立。

### 五 · 匯出到資料根底下的 `exports\`，不在專題資料夾裡

專題資料夾的規矩是「整個複製走，在另一台機器上打得開」（REQ-0001），
而證據包是**要拿出去的東西** —— 放進去只會讓要複製的東西隨每次匯出變大，
而且下一次匯出還會把上一次的一起帶走。

**一次匯出一個帶時間戳的資料夾，不覆寫上一次**（時間戳帶 `Z`）——
「我上禮拜寄出去的那一份」必須還在原地。

### 順帶：一份新的文件

`docs/architecture/walkthrough.md` —— **從一堆沒整理的東西到跑完一輪，
順序是什麼、每一步用不用模型。** 它不重複任何一條規則（每一段都連到規則的權威那一份），
而它自己是一件事的權威：**十步裡只有一步用到模型** ——
那句話在這之前沒有任何一份文件寫著。

### 人工驗收抓到的四個

跑起來、按下去、把產生的檔案讀完，抓到四個測試抓不到的錯（`lessons.md`）：

1. **「這一條沒有引文 —— 它是人直接建立的主張」被無條件印出來**，
   而畫面上那八條全是機器提出的。「沒有引文」的原因有兩種，**而它們的意思相反**
2. 待查證那一組的結語寫著「它們帶著引文」，**而那八條一條引文都沒有**
3. 沒有快照的時候印出 `` `（沒有快照）` `` —— 一個包在程式碼標記裡的括號，看起來像壞掉的雜湊
4. 「紀錄裡是 字元 0–30」多一個空格

前兩個是同一族：**把一句話寫死在一個它只在某些情況下為真的位置。**

## v0.7.0 —— 2026-09-08　Stage 10.5：來源與模型設定

**這一階段的起點是一個量到的數字**：2026-09-08 第一次真的跑一次擴展，
agent 找到 6 個學術來源，**5 個是付費牆**。成功率 17%，
而每一次無效的嘗試都花了時間與錢。

### 一 · 來源網站清單，而判斷來自你自己的紀錄

直覺的做法是「先探測一下這個站活不活著」。**那個做法對出版社幾乎沒有用** ——
首頁一律回 200，文章回 403。「這個站活著」與「這個站的內容我讀得到」
是兩個問題，而使用者要的是第二個。

真正的答案早就在手上：**每一次擷取都寫進 `run_item`**（網域、結果、錯誤碼）。
「這個網域你抓過 12 次，9 次要登入」比任何探測都準，
**而且不花任何一個請求**。所以：

- 判斷**優先看你自己的紀錄**（跨專題聚合），探測只補沒抓過的那些
- 每一格都帶「依據是什麼」與時間 —— 「依你抓過的 3 次」與「依一次檢查」
  是兩件可信度差很多的事，**它們長得一樣的話使用者就會把後者當成前者**
- 內建 22 個來源，最上面那幾個是**把付費牆變成一個讀得到的網址**的那些
  （OpenAlex、Crossref、Unpaywall、Europe PMC、arXiv…）
- **出版社那幾列刻意沒有探針**：給不出一個長期穩定又有代表性的文章網址，
  就留空讓判斷完全依賴紀錄 —— 憑空編一個看起來合理的網址比沒有探針糟得多
- 清單**不擋任何東西**，只影響排序與給 agent 的建議。
  一篇讀不到的重要論文仍然值得出現在清單上

### 二 · 金鑰只讀環境變數，一個字都不存

接雲端端點需要一把金鑰，而這個工具到此為止**一個機密都不存**。
改變那件事的代價不只是「多一個欄位」：**設定檔會被備份、會被同步、
會在求助的時候被整份貼出來。**

所以設定裡存的是**環境變數的名字**，值只在送出請求的那一刻讀一次。
形狀不像環境變數名的（含 `-`、`.`、小寫）一律當成沒設定，
所以一把不小心貼進來的金鑰不會被寫進檔案。

畫面上分得出「沒設定金鑰」與「設了一個環境變數但那個變數是空的」——
**它們的症狀（打不通）一模一樣。**

### 三 · 現在用的是哪個模型

**沒有開新分頁。** 頂列那三格是「目的地」，而模型是一個**狀態** ——
狀態該常駐，不該佔一個目的地。所以：常駐在設定連結旁邊，
名稱／版本／用途三欄在設定頁裡，而**每一次作業用了哪些模型早就記著了**。

版本這一欄是新的：agent 是 CLI 的版本號，chat 是**參數量與量化格式** ——
`qwen3:8b` 的 Q4 與 Q8 是同一個名字、不同的東西，
而**兩者抽出來的關聯不一樣**。兩個都問不到就說問不到，不編一個看起來像版本號的東西。

### 四 · 實體對齊：「規範化」該發生在哪一端

問題是「要不要規範使用者放進來的資料」，而答案是**不要規範輸入，
規範抽取的產物** —— 而那件事一直缺的不是格式，是**同一個東西的不同叫法**。

`entity-repo.ts` 從 Stage 9 就寫著這個問題與它的取捨
（「多一個節點比錯一個節點好」）。**那個取捨漏算了一個後果**：
投影門檻是「被 ≥3 份提到才畫」，所以一個被 9 份文件提到、
但拆成三種叫法的實體，**三個都低於門檻，一個都不會出現在圖上** ——
那不是「多一個節點」，那是少了唯一那一個。

- 抽取時就用**本名、別名、括號裡的**去對，對上就重用並記下新的寫法
- 已經分開的那些列成建議，**每一條帶理由**，而且要人按
- 合併**不刪任何一列**：被吸收的那個留著並指向留下來的那個，
  而**動了哪幾條邊記在 `entity_merge` 裡** —— 取消就是照那份紀錄動回去
- 併完可能出現平行線。**刻意不自動合併它們** —— 合併兩條邊要決定出處、
  狀態與裁決歷史怎麼處理，而那些決定沒有一個可以自動做對。
  看得見的冗餘比看不見的資料遺失好

同一段註解裡的「合錯了沒有工具可以拆開」，這一版把它變成假的。

### 按下去才看到的兩個錯

1. **一次 429 停掉了整批檢查。** Semantic Scholar 對沒有金鑰的呼叫限流很緊，
   而共用一台 `Crawler` 的話那一下把整台停掉 —— 排在後面的 Europe PMC、
   PubMed、Unpaywall **一個都沒被檢查**，而畫面上它們寫著「還沒有依據」，
   **看起來像沒事**。
   「收到 429 立刻停」保護的是那一台伺服器，而這個批次裡每一個目標
   都是不同的伺服器 —— 一台停掉別台，那條規則就從「不要打擾對方」
   變成了「懲罰自己」。改成一個網域一台。
2. **畫面上一堆星號。** 這個 repo 到處用 `**…**` 強調，而那是寫給讀原始碼的人看的。
   漏進 i18n 的字串值就會被原樣印出來 —— 而**其中一條從 Stage 6 就在那裡**，
   沒人發現是因為那條訊息只在掃描版 PDF 上出現。

### 順帶擋住的兩件事

- **migration 檔數要等於 `SUPPORTED_SCHEMA_VERSION`。** 加 006 時忘了改常數，
  而症狀不是「新的沒跑」—— 迴圈照樣跑到 6，然後**下一次開檔會判定
  「這個資料庫比程式新」而拒絕開啟它自己剛升級的資料庫**。
- **i18n 的字串值不得有 Markdown 標記。**

真的按下「檢查全部」跑了一次，內建清單裡有探針的 9 個都拿到答案，
其中兩個是實測才知道的：**NCBI 的 robots.txt 不准抓 E-utilities 那條路徑**，
以及 Semantic Scholar 對沒有金鑰的呼叫回 429。兩個都照規則如實回報。

## v0.6.0 —— 2026-09-08　Stage 10：筆記與點註

**你自己寫的東西第一次進到圖裡。** 在閱讀器裡選一段文字（或在圖片上框一塊），
它變成圖上的一個節點 —— 而**那個節點是暖色的，因為它是你寫的，不是抓回來的**。

### 這一階段真正在守的那條線

**錨點釘在不可變的快照上，而不是釘在重構後的排版上**（ADR-0010）。
兩者的差別只有在抽取器換版的那一天才看得到，而那一天使用者標的每一段
都可能一起漂掉 —— **點註漂掉一次，之後就不會再有人標**。

實作之後才看清楚一件原本以為是平列的事：

> **位置選擇器是快取，引文選擇器才是錨點。**

ADR-0010 的表把兩個選擇器並排（快的那個 ＋ 抗漂移的那個），
而它們其實不對等。直接的後果是**沒有引文的錨點一律算失敗** ——
只有位置的話我們沒有辦法知道那個位置對不對，
而**一個沒驗過的位置長得跟驗過的一模一樣**。
同一個判準 Stage 9 已經用過一次（模型給的字元位置一律丟掉，自己找）。

### 加了什麼

- **`domain/annotation/`**（純函式）：W3C 選擇器的建立、讀回（**壞掉的當作沒有**）、
  以及三種來源三條解析路徑。
- **重複的引文靠前後文分辨。** 一篇裡出現兩次的同一句話，
  標第二次那一個，重抽之後仍然錨在第二次 ——
  沒有這一層的話它會永遠跳回第一次，而**使用者看不出差別**：
  被標起來的字是對的，位置是錯的。
- **PDF 用頁碼 ＋ 頁內字元區間**（`#page=N` `refinedBy` 位置），
  對不上時只擴大到**相鄰頁**，不掃整份文件 ——
  300 頁的 PDF 裡「本研究指出」每一頁都找得到。
- **圖片用 `#xywh=pixel:`**，框到圖外面**直接拒絕**，不夾進邊界。
- **`notes\*.md`**：離開這個工具用任何編輯器都讀得到（ADR-0010 第 3 條）。
- **`POST …/rebuild`**：`derived/` 整批重算。它回的三個數字
  （對得上／位移／對不上）**就是這一階段的驗收條件本身**。
- **schema v5**：`note.snapshot_sha256` ＋ 一條 trigger。前者讓
  「錨在快照上」在資料庫裡**第一次有了對應物**；後者把
  「一則點註就是一個 `kind='note'` 的 `item`，兩者同一個 id」
  從一段註解變成一條約束 —— **註解攔不住 INSERT**。

### 三個只有把畫面開起來才看得到的錯

1. **右邊那一欄永遠停在「從左邊選一份來讀」。** 一個 `immediate` 的 watch
   宣告在它用到的那幾個 `ref` 上面 —— **暫時死區**。
   Vue 把 watcher 裡的例外吞掉並記到 console，
   而畫面上完全看不出有東西壞了。
2. **點註淹掉了資料清單。** 「一則點註是一個 `item`」對圖是對的，
   對閱讀器左邊那一欄是錯的：一份文件標了 30 則之後，
   清單上有 30 列點註跟 1 列文件，**而那 30 列點開來都是「沒有重構後的正文」**。
   同一個數字兩種問法 —— 「有幾份資料」不算它，「圖上有幾個節點」要算它。
3. **「存成點註」是一個藍底藍字的空白按鈕。** 側欄的按鈕比全域的小一號，
   所以整組要重寫一次，而**重寫的時候只改了一半**。

### 一個只有想清楚模型才看得到的錯

**一則沒有線的點註「在圖上是一個節點」這句話字面上為真、實際上為假。**
圖的導覽是「焦點 ＋ 幾跳」（ADR-0008），所以零度數的節點只有在你
已經知道它的 id 的時候才看得到。
建立點註現在會同時建一條**「註於」**的線，`origin='human'` ＋ 已確認 ——
那正是 Stage 8 對手動建立的邊定的規矩，而選一段文字就是那個手動動作。

### 順手清掉的

- **`domain/text/offsets.ts`**：空白正規化的比對與索引對照表本來要寫第二次
  （Stage 9 的引文定位有一份），**一份演算法寫兩次就是兩個各自會漂的地方**。
- `isValidThresholds` 收到 `undefined` 會當場丟例外 —— 一支驗證器不該這樣。
- `derived/` 重算走 `markReextracted` 而不是 `markParsed`：兩者只差一個
  `status` 欄，而**那一欄的差別是「重算會不會把使用者排除掉的那幾份靜默地還原」**。

## v0.5.0 —— 2026-09-08　Stage 9：LLM 擴展

**機器第一次往圖裡寫東西。** 而 Stage 8 建好的四條規則
（不覆寫人工判定、墓碑、每條邊帶出處、agent 不自己抓）在這一階段第一次真的被走到。

- **兩階段，中間有一個人**：`POST …/runs` 產生**多視角子問題**（切入角度）而
  **不會開始抓**；`POST …/runs/:id/angles` 勾選之後才真的開始。
  那一步是 REQ-0004 的驗收條件，不是可以省略的 UI 糖
- **視角是從既有的東西歸納出來的**（STORM 的做法，`market-scan.md` 發現 ⑥）——
  每條角度帶 `seeds`：**它是從你已有的哪幾份長出來的**
- **`claude -p --output-format stream-json` 當 `agent`**，`--tools WebSearch` ——
  工具清單裡沒有 `WebFetch`、沒有 `Write`，所以它**做不到**把網頁存進沙箱。
  另外三個旗標：`--no-session-persistence`（專題內容不留在對話歷史裡）、
  `--system-prompt`、`--disable-slash-commands`
- **本機 Ollama 當 `chat`**：能力宣告去問 `/api/tags`（**provider 自己說的比我們填的準**），
  結構化輸出用 `format` 收整份 JSON Schema
- **`domain/provider/`**：能力配對（**回缺哪幾樣，不回布林**）、三種上限、
  模型輸出的正規化、**引文定位**
- **引文的位置一律自己找**（ADR-0021）。模型給的數字不採信；
  在原文裡找不到就**沒有這條邊**（`PROVIDER_QUOTE_NOT_FOUND`）——
  一個指不到原文的出處，比沒有出處更糟
- **可信度是數出來的**：`scoreFor` 只吃獨立來源數與有沒有直接引文。
  **三個獨立來源才叫「強」**，而互為轉載的三份只算一個
- **設定頁**（`/settings`）：三個角色、能力宣告攤開、「實際打一次」。
  **打開這一頁不產生費用**，而那個會花錢的按鈕旁邊先講了這件事
- **schema v4**：`run` 補四欄（`topic`／`providers_json`／`requests`／`cost_usd`）、
  新增 `run_angle`、一條 trigger（**長度為 0 的引文不是出處**）、一個索引
- **423 個測試**（+66）。擴展的端對端測試**只假造兩個 provider 本身** ——
  `providers.json` 真的被讀、子程序真的被 spawn、擷取管線真的抓
- **版本號守門測試**：`package.json`、`changelog.md`、`README.md` 四邊比對。
  它來自一個真的發生過的落差 —— **Stage 8 的文件全部寫著 v0.4.0，
  而 `package.json` 停在 0.3.0**，活了一整個階段，

### 回答了 open-questions 的 Q6

**非 `named` 層的邊，`status` 欄該寫什麼？**

**不加第四個值。** `DEFAULT_FILTERS.statuses` 是 `['pending','confirmed']`，
多一個值會讓全部的共同提及與相似度線在預設篩選下整批消失。
改成一條 trigger：**機器建的非 `named` 邊只能是 `pending`** ——
於是那一欄在那些列上永遠是同一個值，**它不帶資訊，也就不會誤導**。

而「能不能裁決」是另一件事，**判準不是層別，是「這條邊會不會被重算蓋掉」**：
機器建的非 `named` 會被重算蓋掉，所以不可裁決；
**人建的每一層都可以**，因為重算永遠不碰人建的列 ——
人建錯一條轉載要拿得掉，而 api-contract 沒有刪除端點。

### 三個文件與實作的落差，全部是對照文件時才發現的

1. **校準比例寫成了全域的**，而 ADR-0017 的「考慮過但沒選的」
   **明確否決過那個做法**。改成分段（`rel` × 等級）。
   **測試沒有抓到** —— 餵進去的 30 條剛好各有各的 `rel`
2. **api-contract 的動作清單漏了 `reclassify`**，而那一格旁邊就寫著
   「六條轉移都走這一個端點」——**一張自己跟自己矛盾的表**
3. **已否決的線在圖上沒有打叉**（Stage 7 留下的洞）。那時沒有任何路徑
   可以否決一條邊，所以圖例上那一行是空頭支票

## v0.2.0 —— 2026-09-07　Stage 6：匯入與閱讀器

**貼一個網址或拖一個檔案進去，在閱讀器裡讀到抽出來的正文。**

- **`部分失敗` 從一個型別變成一個迴圈**：4 個輸入（1 個 404、1 個被 robots 擋、

### 量測推翻了兩條憑感覺寫下來的規則

open-questions **Q2** 的回答時機被指定成「動手寫 `extract` 的那一天」。
那一天量了 **34 個真實頁面**（走正式管線），結果：

- **「段落數太少」這條規則被刪掉** —— 它唯一的獨立貢獻是唯一的一次誤報
- **JS-only 的判斷方式整條改寫** —— 原本那張單頁應用骨架標記的清單
