# ADR-0016：已否決是墓碑，機器不得重提；狀態轉換全部寫稽核紀錄

稽核紀錄三件都在寫入路徑上，`edge_audit` 的只增不刪由 trigger 守著。

> 同一份設計稿還把關聯狀態機從 5 條轉移擴到 6 條 —— 那一條與這一條互相依賴，

## 背景

ADR-0005 與 `state-machines.md` 訂了「機器永遠不得覆寫人工判定，重跑擴展只新增、不推翻」。
那條規則擋住了**最明顯**的傷害（確認過的邊變回待查證），但它沒有擋住另一種：

> **重跑擴展會把使用者否決過的東西，原封不動再提一次。**

「只新增不推翻」在字面上是被遵守的 —— 機器沒有動任何已否決的列，
它只是新增了一條一模一樣的待查證邊。**裁決佇列因此永遠清不完**，
而使用者第三次看到同一條自己已經否決過的關聯時，就不會再認真裁決了。

**人工裁決是這個工具與競品的全部差別。** 一個會讓人放棄裁決的機制，
比沒有裁決功能更糟 —— 它讓圖看起來被審查過。

第二件事：設計稿同時發現原本的狀態機**沒有回頭路**。已確認是終點，
而「先確認、後來把出處讀完才發現判斷錯了」很常發生。加上撤回與改判之後，
「這條邊現在是什麼狀態」不再等於「使用者對它的判斷」——
**要算「使用者過去確認了幾成」就必須知道每一次轉換，不只是最後的狀態。**

## 決定

### 1. 已否決是墓碑

**比對鍵 ＝（來源, 目標, 關係型別）。** 被否決過的組合，
**機器不得再提出為 `待查證`**。

**唯一的例外**：帶著**先前沒有的出處**重新提出。
那時它進 `待查證`，並**標記「曾被否決」** —— 使用者一眼看得出這是舊帳重提，
而不是一條新發現。

「先前沒有的出處」的定義要明確，否則這個例外會變成漏洞：
**引文所在的 `item` 不同於這條邊已有的任何一筆 `edge_evidence` 的 `item`。**
換句話說，同一份文件裡換一段話重講一次，**不算新出處**。

### 2. 節點的「已排除」是另一種墓碑

| | 意思 | 誰設定 |
|---|---|---|
| 邊的 `已否決` | **這條關係不是真的** | 只有人 |
| 節點的 `已排除` | **這份資料對這個專題沒用** | 只有人 |

兩者**都是墓碑、都可復原、在圖上共用同一套畫法（打叉）、預設都隱藏**。
但它們是不同的判斷，不可以互推 —— 一份被排除的文件裡提到的關係，
不會因此變成假的。

### 3. 每次狀態轉換寫一列稽核紀錄

`edge_audit`：哪條邊、從什麼到什麼、誰（`human`／`machine`）、什麼時候、哪一次 run。

- **校準比例只採計每條邊的最新判定** —— 一條邊被改判三次，它只算一票。
- 稽核紀錄**只增不刪**。改判不是把舊紀錄改掉，是再寫一列。

## 考慮過但沒選的

| 方案 | 為什麼不選 |
|---|---|
| **不做墓碑，靠使用者忍耐** | 裁決佇列永遠清不完。這一條的代價不是「有點煩」，是**整個人工裁決機制會被放棄** |
| **否決就把列刪掉** | 那就沒有東西可以比對，下次重跑照樣提。而且復原不了 —— 使用者按錯一次就永久失去那條邊 |
| **墓碑不留例外，永久封死** | 比較安靜，但**新證據出現時使用者永遠不會知道**。而這個工具的整個價值就在於「出處會累積」 |
| **例外放寬成「有任何新引文就重提」** | 同一份文件裡換一段話就能繞過去。那等於沒有墓碑 —— **例外的門檻要用 `item` 算，不能用引文字串算** |
| **只存最新狀態，不寫稽核** | 校準比例（ADR-0017）算不出來，而且改判之後「使用者原本判什麼」永遠消失 |
| **稽核紀錄存在同一列的 JSON 欄位裡** | 查詢要解 JSON，而校準比例是一個會被頻繁算的聚合。**一個要被聚合的東西不該埋在 JSON 裡** |

## 代價

- **擴展的寫入路徑多一次查詢**（查這個三元組有沒有墓碑）。在 20 萬邊的規模下，
  這需要 `(source, target, rel)` 的索引 —— 那個索引本身也有寫入成本。
- **「曾被否決」這個標記要一路帶到 UI**，否則墓碑例外形同虛設：
  使用者會以為那是新發現的關聯。
- **`edge_audit` 只增不刪，會長。** 一個裁決很多的專題，稽核列數會超過邊數好幾倍。
  第一版**沒有清理策略** —— 這是明知的缺口，不是忘記；要等有真實體積再訂。
- **改判讓「這條邊的狀態」與「使用者對它的判斷歷史」變成兩件事**，
  而 UI 只顯示前者。要看歷史得另外開一個地方，那是額外的畫面。

## 2026-09-08 的實作補記（Stage 8）

**三件事在動手寫寫入路徑那一天才浮出來。**

### 兩支守門函式看起來都像是全部的答案，而它們必須照順序問

`machineMayUpdateStatus`（狀態機規則 1）說：**被人碰過的邊，狀態不准動。**
一條已否決的邊當然被人碰過 —— 照它問，這份 ADR 的墓碑例外就永遠不會發生。

`evaluateProposal`（這一份）說：**帶著新出處的話，已否決的邊要復活。**
照它問，一條被人確認過的邊也會被機器動到 —— 而那是規則 1 要擋的。

**兩支都不是全部的答案，它們管的是不相交的兩條路：**
既有那一列是 `rejected` 就走 `evaluateProposal`（這是墓碑，而墓碑有明文例外），
其餘走 `machineMayUpdateStatus`（這是重跑，而重跑只附加出處）。

**先問錯那一支，症狀是安靜的** —— 不是報錯，是墓碑例外從此不觸發，
或者反過來，是使用者確認過的邊被機器改掉。
判別方式與理由寫在 `infrastructure/db/repositories/edge-repo.ts` 的 `applyProposal`。

### `edge_audit` 記什麼、不記什麼

**只記「狀態被改變」，不記「邊被建立」。**
建立這件事 `edge` 自己就記著了（`created_at`、`origin`、`run_id`），
而 20 萬條機器邊各寫一列建立紀錄，會讓稽核表比它要稽核的東西還大。

**`actor='machine'` 只有一種情形**：就是這一份的墓碑例外。
那一列存在是為了回答「這條邊為什麼從否決區跑回佇列」。
**它不算進校準比例** —— 那不是使用者的判斷。
（`origin='human'` 的邊也不算，理由見 ADR-0017 的補記。）

### 上面「代價」預言的那個缺口補上了

那一節寫著「UI 只顯示前者，要看歷史得另外開一個地方，**那是額外的畫面**」——
結果不必是額外的畫面：**裁決歷史就在關聯面板的最下面一段**，
每一列寫「誰 · 做了什麼 · 從什麼到什麼」。
它跟出處與構成事實在同一屏，因為它們回答的是同一個問題
（「這條邊憑什麼是現在這個樣子」）。

## 什麼情況要重新考慮

- **墓碑例外的觸發率高到使用者覺得吵**（可量測：帶「曾被否決」標記的邊佔佇列的比例）——
  那時要調的是「新出處」的定義，不是拿掉例外。
- **`edge_audit` 的體積影響到備份或查詢** —— 那時的問題是清理策略，不是要不要寫稽核。
- 若實際使用中**從來沒有人用過改判**，那要問的是「撤回確認這條轉移是不是多餘的」——
  但要先確認不是因為 UI 藏太深。
